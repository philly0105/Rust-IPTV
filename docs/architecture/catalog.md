# Catalog

Code: `crates/iptv-core/src/catalog/`. Tests: `crates/iptv-core/tests/catalog_query.rs`, `catalog_perf.rs` and `l2_query_perf.rs` (read budgets), `l2_query_english.rs` (stored English-only verdicts), `l2_cross_bulk_write.rs` (index rebuild, declared categories, rollback), `l3_search_perf.rs` (search, filtered VOD pages and parental hide mode on 215k items, with results checked against single-list searches), `catalog_items.rs` (`catalog.items` answers ref for ref like `catalog.item`, across sources), `quality_storage.rs` (stored channel quality and its backfill) plus unit tests in `mod.rs`, `title.rs`, `language.rs` and `quality.rs`.

The catalog is the `items` and `categories` tables (C3) for every source kind. Importers write it; the UI reads it through `catalog.*` rpc. One row shape (`ItemRow`) serves live, radio, movie and series items.

## Writing

Two entry points, both one write transaction per call:

- `replace_catalog(conn, source_id, content_type, categories, &mut items)` replaces one `(source, content type)`. Only tests call it now.
- `CatalogWriter` is for writers that replace several content types in one transaction: the m3u importer, and `xtream::sync::replace_catalogs`, which the Xtream and Stalker importers use for every type they write (xtream.md, stalker.md). Open a transaction first, then:

```rust
let tx = conn.transaction_with_behavior(TransactionBehavior::Immediate)?;
let mut w = CatalogWriter::begin(&tx, source_id, &[ContentType::Live, ContentType::Movie], cancel)?;
w.declare_categories(ContentType::Live, &live_cats);   // optional: final verdicts on insert
w.declare_categories(ContentType::Movie, &movie_cats);
for row in rows { w.insert(&row)?; }          // returns false for a duplicate id
w.finish(&[(ContentType::Live, live_cats), (ContentType::Movie, movie_cats)])?;
tx.commit()?;
```

`begin` refuses to run outside a transaction. `cancel` is the import run's token, taken before waiting for the write lock; `None` looks up the source's writer token instead (`sources::writer_cancel_token`), for writers outside an import run. `begin` saves the hidden category ids, then deletes the old items and categories of those types. `finish` inserts categories with their hidden flag restored, adds an "Uncategorized" category for any `category_id` used by items but not declared, corrects the English-only verdicts (below), recomputes `item_count`, and refreshes `source_counts`. If anything fails, the caller drops the transaction and the previous catalog stays. After the commit, the m3u, Xtream and Stalker importers run `db::checkpoint_truncate` on the same connection: a catalog rewrite grows the WAL by about the catalog's size, and the TRUNCATE checkpoint folds it back and empties the WAL. It never waits on a busy reader; a later checkpoint finishes the job. An XMLTV ingest does the same (epg.md).

Duplicate `(content_type, item_id)` rows keep the first one (`INSERT OR IGNORE`). Movie and series rows without `title_base` get it, and `year` when missing, from `title_base(title)`.

### English-only verdict

Migration 0018 stores the English-only verdict with each item: `items.non_english` is 1 when the item is clearly in another language (the rule in `language.rs`, which mirrors `src/features/vod/lib/language.ts`). The title decides when it carries a language tag; otherwise the category name does.

- `declare_categories(ct, &categories)` gives the writer the categories of a type before their rows; it computes `category_verdict` of each name as it will be stored (the first category with an id wins, as in `finish`, which must get the same categories). An untagged row in a declared category then gets its final verdict on insert, `combine(title_verdict, category_verdict)`, and `finish` never touches it. The m3u importer declares each group before that group's first row, and `xtream::sync::replace_catalogs` declares every type's categories before any row, so Xtream, Stalker and m3u imports store final verdicts on insert.
- Otherwise `insert` stores the title's guess, `language::title_guess(title_verdict(title))`: the verdict for a category whose name says nothing. It also records, per category, the rowids of titles without a tag (`TITLE_UNDECIDED`) and of untagged titles in a foreign script (`TITLE_UNDECIDED_FOREIGN`). This covers rows whose `category_id` no declared category has, and writers that declare nothing (`replace_catalog`).
- For those rows, `finish` computes `category_verdict(name)` for each category as stored (an undeclared id uses the "Uncategorized" name) and, where `category_changes(verdict)` says the category overturns the guess, rewrites just those rows with `UPDATE items SET non_english = ? WHERE rowid = ?`: untagged titles become hidden, foreign-script titles become shown. Titles with their own tag never change. It then deletes the `english_pending` rows of its types.

`english_pending(source_id, content_type)` lists the catalogs whose rows were written before migration 0018 and still hold the column default 0. The migration seeds it with every `(source_id, content_type)` in `items`, and its rows go when the source is removed (`ON DELETE CASCADE`). At boot `catalog::init` spawns `language::backfill_pending`, which takes one Immediate transaction per pair, so user writes interleave: it re-checks that the pair is still pending (a rewrite since may have stored the verdicts), sets `non_english = 1` on the rows the rule hides, and deletes the pair. Until then readers fall back to the per-row rule for that pair:

- Readers of one source and type (`english_scoped`: `query_named` pages and counts, VOD year facets, `filtered_categories`, `neighbors`, `all_live_channels`) add `AND i.non_english = 0` (`language::STORED_SQL`). For a pending pair they use `language::hidden_rowids`, a per-connection `temp.english_hidden` set rebuilt after any write.
- Readers across sources (`english_clause`: search, `recently_added`) use `STORED_SQL` when no pair is pending, and the SQL function `non_english(i.title, c.name)` (`ENGLISH_ONLY_SQL`) while any pair is.

Any new code that writes `items` must keep the column right. Go through `CatalogWriter` (or `replace_catalog`), or set `non_english` from the `language.rs` rule yourself, or insert an `english_pending` row for the pair so the readers fall back and the next boot backfills it. The same holds for code that later changes a title or a category name: the stored verdict does not follow. Today only `CatalogWriter`, `backfill_pending` and `quality::backfill` (below) write items.

Migration 0018 also narrows the `items_au` trigger to `AFTER UPDATE OF title`, so writing the verdict (or any other column) leaves `items_fts` alone.

### Channel quality

Migration 0022 stores the picture quality a live channel's name marks with each item, for the Live TV quality filter (`liveMinQuality`, `liveHideUntagged`; settings.md). `items.quality` is -1 (`quality::UNSET`, not computed yet), 0 (`quality::UNTAGGED`, no quality tag) or 1 SD, 2 HD, 3 FHD, 4 UHD (`quality::code`). The markers are the failover matcher's (`live::matcher::quality`, which shares its code with `signature`, so the filter and `live.alternates` never disagree; failover.md), and `Full HD` and `Ultra HD` written as two words count as FHD and UHD, while `8K EXCLUSIVE`, which one provider writes on every event channel, counts as no tag. They are read from the provider's name, `items.title`, a country or group tag in front of it included, word by word (`4K-DE - Das Erste` is UHD, `UK HD | Sky` is HD). A rename lives in `channel_edits` and does not change the quality, as with the English-only verdict.

- `insert` stores the code of the title for live rows and 0 for every other type. It depends on the title alone, so it is final on insert and `finish` never corrects it. `finish` copies it into `items_rank` with the other ranking columns.
- Rows written before the migration hold -1. At boot `catalog::init` spawns `quality::backfill` after the English-only pass. For each source it reads the live rows still at -1 and computes their codes outside the write lock, then stores them in Immediate transactions of 5,000 rows (`BACKFILL_BATCH`), so user writes interleave. It holds `db::long_write()` while it runs, as an import does. A row a rewrite has replaced since is skipped (`AND quality = -1`). Radio, movie and series rows keep -1 until their next rewrite; no reader filters them.
- Readers treat -1 as untagged and need no fallback: the two settings are new in the same release, so the filter is off when the first backfill starts.

Code that writes live rows outside `CatalogWriter` must store the code itself; a row left at -1 reads as untagged until the next boot's backfill.

### FTS during bulk writes

`items_fts` is an external-content FTS5 table kept in step by triggers. Per-row trigger updates made a 50k import take about 2 s on their own. Migration 0002 adds `fts_suspend(source_id)` and makes `items_ai` and `items_ad` skip rows whose source has a row there. `CatalogWriter` inserts that row in `begin`, deletes the old FTS entries with one `INSERT ... SELECT 'delete'`, and in `finish` indexes the new rows with one `INSERT ... SELECT` before removing the suspend row. The suspend row never outlives the transaction. Any other code that inserts or deletes items keeps the normal per-row triggers.

A rewrite that deletes more rows than the other sources and types keep (they are counted only once the rewrite touches `BULK_MIN_ROWS`, below; a single-source library's every changed refresh is one) skips the per-row `'delete'`, which tokenizes every old title and writes a delete marker per word: `begin` runs FTS `'rebuild'` (`rebuild_search_index`) right after its deletes, the one point where `items` holds exactly the kept rows, and `finish` adds the new rows as before. `begin` of a 250k-row refresh next to 40k kept rows went from 1.1 s to 0.45 s (dev profile). `sources::store::delete` follows the same rules for a removed source (Index rebuild below).

`items_rank` (migration 0020, see Reading) follows the same contract. Its insert and delete triggers skip a suspended source; `begin` deletes the rewritten types' rows with one `DELETE ... WHERE id IN (SELECT rowid FROM items ...)` next to the FTS delete, and `finish` copies the new rows with one `INSERT ... SELECT` after the verdict updates, next to the FTS insert (about 0.11 s per 100k rewritten rows, where per-row triggers cost about 0.65 s per 50k). Its update trigger is unconditional: a verdict update in `finish` touches a row that is not in `items_rank` yet, and `language::backfill_pending`, `quality::backfill` (since 0022 the trigger also fires on `quality`) and any other update keep it in step. Code that writes `items` while its source sits in `fts_suspend` must update `items_rank` the way it updates `items_fts`; `crates/iptv-core/tests/m3u_support.rs` has `assert_items_rank`, which the import, bulk-rewrite and search-rank tests run after each kind of write.

`db::configure` also sets `temp_store=MEMORY`. Without it, statement journals for `INSERT OR IGNORE` with triggers went to temp files and tripled insert time.

### Index rebuild for large rewrites

A rewrite that touches at least `BULK_MIN_ROWS` (20,000) rows, counting the rows `begin` deletes and every row offered to `insert` (duplicates included), and at least as many as it leaves in `items` (other sources and types), drops every secondary index of `items` (`maybe_go_bulk` through `drop_item_indexes`; names and `CREATE` statements from `sqlite_master`, the primary key stays). `finish` runs those statements again (`create_item_indexes`) before it writes the categories and counts, in the order the indexes were created (`ORDER BY rowid` in `sqlite_master`). The order matters: without statistics SQLite picks the covering index created last among those of equal cost, and migrations 0022 and 0024 create the narrow `idx_items_cat` last so counts read it, not the wide `idx_items_title` or `idx_items_cat_added`. Building each index once from sorted rows replaces updating all twelve secondary indexes (as of migration 0024) on every row. `items_rank` has no secondary index, so bulk mode leaves it alone; its rows are deleted and copied by the set-based statements above. The check runs in `begin`, before the deletes, and again every `WRITE_BATCH` (1000) rows. Either way it weighs the rewrite only against the rows of other sources and of the source's other types: `count(*)` of `items` minus the rows `begin` is about to delete, and after the deletes (`replaced_gone`) minus the rows inserted so far. That number cannot change inside the writer's transaction, so it is counted once, the first time the check needs it (`kept`), not on every batch.

All of it happens inside the import transaction: readers keep the previous catalog and its indexes until the commit, and a rollback restores them. The costs:

- The drop and the rebuild change the database schema once per large import, so every pooled connection re-reads the schema and re-prepares its cached statements once, on its next use.
- The rebuild sorts each index through temp storage, which `db::configure` keeps in memory (`temp_store=MEMORY`), so peak memory rises by about the size of the largest `items` index while it is built. Migrations, by contrast, sort on disk (`db::migrate` sets `temp_store=FILE`).
- Nothing runs `ANALYZE` or `PRAGMA optimize`, so there are no index statistics to lose. If `ANALYZE` is ever added, a bulk rewrite drops the statistics of those indexes until it runs again.

Removing a source (`sources::store::delete`, one Immediate transaction) applies the same rules. It counts the source's rows and the rest first. A source of at least `BULK_MIN_ROWS` rows and at least as many as the others keep has its indexes dropped before the `sources` cascade deletes its items and built again after it; when it outnumbers the kept rows, the search index is rebuilt from them after the cascade instead of losing its entries one by one. Removing a 250k-row source next to 40k kept rows held the write lock 3.0-3.7 s before the commit (per-row FTS deletes 0.85-1.5 s, the cascade through twelve indexes 2.0-2.2 s), now 1.1-1.4 s (dev profile; `l2_cross_bulk_write.rs` checks search, counts, `items_rank`, FTS integrity and index order after both kinds of removal).

## extra_json keys

`ItemRow.extra` is stored as `items.extra_json`. The readers (`From<NamedRow>` for `Channel`, `VodItem`, `SeriesItem`) understand these camelCase keys; B3/B4 importers should use the same names:

| Key | Type | Used for |
| --- | --- | --- |
| `plot` | string | `VodItem.plot`, `SeriesItem.plot` |
| `genres` | string array (a comma string is split) | `genres` |
| `durationSeconds` | number | `VodItem.durationSeconds` |
| `tmdbId` | number | `tmdbId` |
| `catchup` | object `{type, days?, source?}` | `Channel.catchup`; turns on `Channel.archive` when the type is usable (`catchup_usable`, case-insensitive: default, append, shift, xc and flussonic, plus the aliases in `CATCHUP_TYPES` in `catchup/m3u.rs`: timeshift is handled as shift; flussonic-hls, flussonic-ts and fs as flussonic), as does `archive_hours > 0` |
| `headers` | object `{userAgent?, referrer?, origin?}` | `Channel.headers` (blank values dropped), and `VodItem.headers` of an M3U movie in `catalog.item` and `catalog.items`; the player merges them over the source-level headers |

The m3u importer also stores `tvgName`, `tvgShift`, `vlcOpts` and `kodiProps`, and on the series rows it groups from playlist episodes `episodes`, the stored episode list that `m3u.seriesDetail` and `m3u.streamUrl` read (m3u.md, Series). Readers pass unknown keys through untouched, except that one: `read_named` (`parse_extra`) leaves `episodes` out of a series row's `extra`. When the text holds the needle `"episodes"` (one `memchr` scan; a quote inside another value is escaped), the object is parsed by a visitor that skips that key's value with `IgnoredAny` and builds every other key as a full parse does; any other row keeps the plain parse, and junk still gives an empty object. A 60-row page of 20-episode shows took 0.85 ms and 14,760 allocations with the list parsed and dropped, 0.1 ms and 120 without it (8.6 ms against 1.35 ms at 200 episodes). Code that needs the list reads it straight from the text with `m3u::series::stored_episodes_of`.

An importer may hand the writer `extra` already serialized (`ItemRow::extra_json`, with `extra` left `Null`; readers never set it), and `CatalogWriter::insert` binds that text as is inside the write transaction. The Xtream mapping and the M3U row builder do so: they serialize small borrowing structs whose fields are declared in key order, so the stored bytes are the ones a `serde_json::Map` writes (equivalence tests cover every key combination). A `Map` is a BTreeMap whose first insert allocates a 632-byte leaf, and the rows wait under the save slot from decode to write: a mapped Xtream row now retains 534-791 B instead of 1,162-1,566 B, about 160 MB less at 50k channels, 180k movies and 20k series. M3U series rows carry their episode list the same way (m3u.md, Series); its keys are not in `Map` order, which no reader depends on.

## Reading

- `query` / `query_named(conn, &CatalogQuery)` returns a `Page`. Limit is capped at 1000. Without a `category_id`, items in hidden categories are left out unless `include_hidden`; with one, that category is listed even if hidden. Sort keys: `name`, `number`, `added`, `rating`, `year`; NULLs sort last. Default direction is ascending for name and number, descending for added, rating and year. Without a sort key the order is item position (playlist order). `min_rating` (the `minRating` arg of `catalog.movies`/`catalog.series`) adds `rating >= ?` to the WHERE clause, so the count and paging cover only items rated at least that.
- A page is read in two statements. The count runs on `items` alone, without the category join. The page then picks its rowids from the sort's index and joins only those: `SELECT_NAMED WHERE i.rowid IN (SELECT i.rowid FROM items i WHERE ... ORDER BY ... LIMIT <n> OFFSET ?) ORDER BY ...`. OFFSET is a bound parameter, so every page of one list shape reuses a single cached statement; LIMIT stays literal because SQLite uses it in its row estimate. The 0018 indexes hold the category, position and verdict, and 0019 adds the rating and year to the sort indexes, so a deep OFFSET skips index entries instead of reading and joining every skipped row (100 to 900 ms near the end of a 100k list without them). In the page statement a rating or year filter on another sort key is written `+i.rating` / `+i.year`, which keeps it out of SQLite's index choice: the sort's index answers the page in order, where the filter's own index would sort every match in a temp b-tree (100 to 340 ms a page on 60k movies). The count keeps the plain columns, where the filter's index helps, except in a category: there the filter's index read the filter's range across the whole source (with the page's walk, 11-12 ms for a 199-title category on 182k movies with a rating floor or a decade, 0.1-0.2 ms now), so the count writes `+i.rating` / `+i.year` too and reads the category's range. A page whose offset is at or past the total returns no rows without running the page statement.
- A category page on the date-added sort (the default: category grids, the landing's category rails, the "More in" rail of a detail page) reads its category's range of `idx_items_cat_added` (migration 0024) in order. Before, SQLite walked the source's `idx_items_added_src` and tested each entry's category: without statistics two equalities on an ordered, covering index cost about as much as three on `idx_items_cat`, which can neither order nor cover the page. A category smaller than a page, the last page of any category and a category of old titles read every title of the source (6.5-9.5 ms on 182k movies in release; 0.1-0.4 ms now, `l2_query_perf.rs`).
- An unfiltered list takes its total from the stored counts: All movies, All series, Top rated, All channels, the guide's All list and radio, when nothing narrows the list (no category, search, minimum rating, year range, Hide watched, parental hide clause, English-only or Live TV quality filter). `stored_total` adds up `item_count` over the source's categories of that type, the hidden ones left out unless `include_hidden`. Every item has a category row (`CatalogWriter::finish` adds Uncategorized ones), and `item_count` leaves out the channels a channel edit hides: `finish`, `channels.reset` and a backup import count without them (`recount_categories`), and `channels.setHidden` moves the counts by the channels it changes (channel-edits.md). So the sum equals what `count(*)` returns with the hidden-category and hidden-channel filters (`catalog_query::unfiltered_channel_totals_match_a_count_without_hidden_channels` checks live and radio through hidden groups, hidden channels, a smaller re-import and `channels.reset`). The count walked every row of the source on every page: about 5 ms on 182k movies, 20 ms with 60 of 444 categories hidden, as each title probes the hidden set (release, `l2_query_perf.rs`), and 4.4 ms, 95% of a first page, on 200k live channels, where a guide search hit's locate reads up to 12 pages; the page now costs 0.3-0.4 ms, hidden categories or not. Every other shape keeps `count(*)`.
- A short list that the sort's own index holds spread through the whole source is read from another index and sorted (`sorted_read_index`), when the count says it has at most `SORTED_READ_MAX` (3,000) rows: a category sorted by rating or year from `idx_items_cat_added` (index-only), by name from `idx_items_cat` (one table row per title, for the title), and an All page with a year range or a minimum rating, sorted by another key, from `idx_items_year` or `idx_items_rating`, with the plain column in the page. The statement names the index with `INDEXED BY`, a fixed plan where a unary `+` only tips a cost tie. Walking the sort's index found such a list's rows only near its end: a 30 to 2,000-title category sorted by rating or name, or a decade with 46 titles, took 8-11 ms on 182k movies, now under 1 ms. Above 3,000 rows the walk stays, since it finds a page's rows early; the last pages of a large category sorted by rating or name still walk the whole index (8-10 ms for 8,883 titles).
- Search tries FTS5 first. Each word becomes a quoted prefix term, so user input cannot inject FTS syntax. When FTS returns nothing, a `LIKE '%text%'` substring search runs instead. `PageQuery.search` filters the page and keeps the page's sort.
- A list's own search (`PageQuery.search` in `query_named`) first counts the word-prefix matches in the whole library, reading at most 2,001 of them (`fts_matches_at_most`). With at most `FTS_DRIVEN_MAX` (2,000), the count and the page write the scope as `+i.source_id`, `+i.content_type` and `+i.category_id`, so the matched rowids are the only way into `items` and the page sorts at most 2,000 rows. Without statistics SQLite rated the match list at 25 rows and the source's index range at about 9, so it walked every title of the source and probed the list, for the count and again for the page: 22-24 ms for a 37-title search on 182k movies, 0.4 ms now (release, `l2_query_perf.rs`). A broad term keeps that walk, which finds a page's rows early; it pays for the capped count on top (about 1-3 ms: "a", with 50,380 matches, went from 30.5 to 31.8 ms). When the substring search runs instead on All, with at most 3,000 matches, its page reads `idx_items_title` (`sorted_read_index`): walking the date-added index read a table row per title to test it (a 37-match substring took 78 ms on 182k movies, 33 ms now; 1,598 matches, 54 ms and 34 ms).
- `catalog.search` and `search` / `search_named` go through `search_groups`, which answers several groups of types in one pass; `catalog.search` passes three (live and radio, movies, series). One FTS statement ranks the matches on `items_rank`, a narrow copy of the columns ranking and filtering need (rowid, source, type, category, verdict, `length(title)` as `title_len`, position; migration 0020; and the channel quality since 0022), instead of each match's wide `items` row with its URLs and JSON. It collects the matches once (`WITH m AS MATERIALIZED`, `items_fts CROSS JOIN items_rank` so the FTS index drives), keeps each group's best `limit` with a bounded `ORDER BY rank, title_len, position, rowid LIMIT limit` per group (`UNION ALL` of one per non-empty group), and then reads the full rows of those winners only. Ties end on the rowid. On 215k items "th" has 56k matches; the rank, the narrow rows and the per-group top-N keep it at 61-64 ms at p95 in a release build, where a `ROW_NUMBER()` window over every match's `items` row took 155 ms. Its filters test columns of `items_rank` alone (they are written against `items i` and name only columns both tables have), so ranking reads no category row per match: hidden categories are checked only when there are any (in the searched source, or in any source when the search spans them all), as a set of hidden category ids plus an exact key probe for the rows whose id is in it, and the categories join is added only while the per-row English-only rule applies (a pending pair, above). That rule reads the title and the category name, so while it applies the FTS pass ranks on `items` with the `ROW_NUMBER()` window instead, with the same order. When FTS finds nothing in any group, every group falls back together in one substring statement over `idx_items_title` (`rowid IN (SELECT rowid FROM items WHERE title LIKE ?)`), ordered by title length, then title. A group without word-prefix hits next to groups that have some stays empty: filling it would scan every title of the library for a few in-word matches (50 to 120 ms on 220k items). Without a source the inner statement filters on `+content_type`, which keeps SQLite off `idx_items_added`, and the outer pass writes the type and source as `+i.content_type` / `+i.source_id`, so the matched rowids drive it. Channels whose custom name matches come first (channel-edits.md). A group with word-prefix hits answers as a search of its own would. The substring fallback runs only when the caller sets `substring`: `catalog.search`, `search` and `search_named` do, `match_titles` does not.
- `match_titles` (`catalog.matchTitles`) finds, for each TMDB title of a "More like this" rail or an actor's "Known for", the rows of one source and type the UI picks its match from (`matchBrief`). It first probes the base title: `content_type = ? AND title_base = ? COLLATE NOCASE AND +i.source_id = ?` outside hidden categories, up to 8 rows (`MATCH_TITLE_HITS`) ordered by `length(title)` and position. The `+` keeps the indexes that start with source and type from driving, so `idx_items_title_base` answers in a fraction of a millisecond (a unit test pins the plan under three filter shapes). Only when no probed row may be the title (`may_be`: the same TMDB id when both have one, else years at most one apart or unknown) does the word-prefix pass of `search_groups` add its best 8 rows after them, without duplicates and without the substring pass; that finds accents, punctuation the tokenizer drops, and a remake under another base title by its TMDB id. The filters are `catalog.search`'s: hidden categories, English-only (`english_clause`) and parental hide (`item_row` in the probe, `item_set` in the ranked pass). The UI sent one ranked `catalog.search` per title instead, 20 to 40 per page at 10-60 ms each plus a 50-120 ms substring pass for each title with no word-prefix hit; `catalog_query::match_titles_picks_what_the_search_lookup_picked` checks that both lookups pick the same title for 16 briefs.
- `channel_by_number(conn, source, number, content_type)` skips hidden categories. `content_type` `Some(Live)` / `Some(Radio)` restricts the lookup (any other type is Invalid); `None` checks live before radio. `neighbors` wraps around within the category (or the whole visible list). `recently_added` needs `added` set. `same_title` matches other sources by `title_base` (case-insensitive) with a compatible year, up to 50 rows. `all_live_channels` is capped at 20,000.
- The Live TV quality filter (Channel quality above; `rpc::quality_filter`, `None` while `liveMinQuality` is null) applies to live rows only. With a minimum whose code is m, a reader keeps `quality NOT BETWEEN 1 AND m-1`, so untagged channels and rows the backfill has not reached yet stay; with `liveHideUntagged` it keeps `quality >= m`. A minimum of SD that keeps untagged channels adds no clause. The thresholds are integer literals, so each setting is one cached statement, and the live page, count and guide indexes end in `quality` (0022), so those statements stay index-only.
  - Statements over live rows alone append `quality::live_clause`: `query_named` (count and page; `CatalogQuery.quality` is set for live only), the category re-count (`filtered_categories`, taken when English-only or the quality filter is on; groups the filters empty are dropped), `neighbors` (the current channel may itself fail the filter), `all_live_channels` (and so the phone remote's list) and the channel walk of `epg.search`.
  - `search_groups` (for `catalog.search`) and `channel_by_number` append `quality::mixed_clause` (`AND (i.content_type <> 'live' OR ...)`), so radio rows stay. Without a content type, `channel_by_number` checks live and radio together, and a live channel the filter hides falls through to a radio station with the same number. `search` and `search_named` pass no filter (`None`). In `search_groups` the clause goes into the filter that radio, movies and series share. `items_rank` has the column, so the ranked pass still reads `items_rank` alone. The clause stays out of the English-only value that `ranking_join` compares with `ENGLISH_ONLY_SQL`.
  - The parental count corrections (`parental::filter::locked_item_counts`, `locked_hidden_counts`) test the same condition, so a locked or hidden channel the filter already removed is not subtracted twice.
  - Favorites, recently watched and custom lists (`favorites.list`, `recent.list`, the favorites order, `lists.items` and `itemCount`, `lists.neighbors`) drop a live entry whose catalog row exists and fails the filter (`NOT EXISTS (SELECT 1 FROM items q WHERE ... AND NOT (<condition on q>))`). An entry whose row is gone stays and shows as unavailable.
  - `live.alternates` drops the candidates `QualityFilter::keeps` rejects, never the channel being played (failover.md).
  - Not filtered: `catalog.item` and `catalog.items`, `source_counts` and the stored `item_count`, `channels.edits`, continue watching, stats and recordings.

## Counts

`source_counts(source_id, channel_count, movie_count, series_count)` is a cache refreshed by `update_counts` after every write. `channel_count` is live channels only. The radio count is not cached: `radio_count` and the source readers count `items` rows of type radio (an index range scan on the primary key). `sources.list` reads it with a join instead of counting large catalogs on every call.

Stalker sources are the exception: their VOD and series are not stored, so `update_counts` leaves their `movie_count` and `series_count` alone, and `set_remote_counts(conn, source_id, movies, series)` records the portal totals (called by `sources::run_import` from the stalker `ImportSummary`).

## Migrations

- 0001: the C3 schema.
- 0002: `source_counts`, `idx_items_title_base`, `idx_sources_position`, `fts_suspend` and the suspend-aware FTS triggers.
- 0003: `idx_epg_programs_url` on `epg_programs(epg_url)`. The EPG store replaces a feed with `DELETE FROM epg_programs WHERE epg_url = ?`, renames staging rows by `epg_url`, and removing an `epg_sources` row cascades by `epg_url`; without the index each of those scans every programme. Lookups by channel already use `idx_epg_programs_chan`.
- 0018 (`0018_catalog_query_speed.sql`): `items.non_english`, `english_pending` and the title-only `items_au` trigger (see English-only verdict), and the page indexes. Each one leads with `(source_id, content_type)`, then the sort key, then `position` (the tie-break of every sort), the category and the verdict, so pages and counts of one source and type are index-only scans:
  - `idx_items_cat(source_id, content_type, category_id, position, non_english, year)`, which also serves a category's year facets;
  - `idx_items_title(source_id, content_type, title COLLATE NOCASE, position, category_id, non_english)`, for the name sort and the substring search;
  - `idx_items_pos(source_id, content_type, position, category_id, non_english)`;
  - `idx_items_year(source_id, content_type, year DESC, position, category_id, non_english)`;
  - `idx_items_rating(source_id, content_type, rating DESC, position, category_id, non_english)`, new;
  - `idx_items_added_src(source_id, content_type, added DESC, position, category_id, non_english)`, new.

  The first four replace the indexes of the same name from 0001, 0006 and 0013. Rating, year and added sort descending by default with NULLs last, the natural order of a DESC index. Since 2026-10-19 the file itself creates only `idx_items_cat` and drops the old `idx_items_title`, `idx_items_pos` and `idx_items_year`; the five sort indexes are built once, by 0019 (an upgrade from schema 17 used to build each twice, DB-6 in the performance audit). Migrations are tracked by version, never re-run or hashed, so a database that ran the old file is unaffected.
- 0019 (`0019_guide_search_speed.sql`): recreates the five sort indexes with the rating and the year after the verdict (`idx_items_added_src`, `idx_items_title` and `idx_items_pos` gain both, `idx_items_rating` gains the year, `idx_items_year` the rating), so a page with a minimum rating or a year range reads index entries, not table rows (about 12 ms or less in every measured case, against up to 140 ms on a deep page of 100k movies). It also adds `idx_items_guide` and `epg_search_rows` for the guide search (guide-search.md).
- 0020 (`0020_search_rank.sql`): `items_rank`, one narrow row per item (`id` is the item's rowid) with `source_id`, `content_type`, `category_id`, `non_english`, `title_len` (`length(title)`) and `position`, filled from `items` in the migration and kept in step by suspend-aware insert and delete triggers and an update trigger on the copied columns (see FTS during bulk writes). The search ranks on it (see Reading). It adds about 15 MB per 220k items; the upgrade copies 220k rows in about 0.14 s (`migration_perf.rs`).
- 0021 (`0021_epg_channel_shift.sql`): `epg_channel_shift`, a channel's own guide shift in minutes, keyed like `epg_channel_map` (epg.md).
- 0022 (`0022_channel_quality.sql`): `items.quality INTEGER NOT NULL DEFAULT -1` (see Channel quality) and the same column in `items_rank`. It recreates the `items_rank` insert and update triggers to carry it; the update trigger now fires on `UPDATE OF source_id, content_type, category_id, non_english, title, position, quality`. It rebuilds `idx_items_title`, `idx_items_guide`, `idx_items_pos` and `idx_items_cat`, in that order, with `quality` appended as the last column and the other columns unchanged, so live pages, counts and the guide search's channel walk stay index-only with the filter on. The rating, year and added indexes serve movies and series, which are never filtered, and keep their columns. Every row starts at -1; the migration calls no app SQL function, and the boot backfill computes the live codes.
- 0024 (`0024_category_added_index.sql`): `idx_items_cat_added(source_id, content_type, category_id, added DESC, position, non_english, rating, year)`, so a category page on the date-added sort, with English-only, a minimum rating or a decade, reads its category's range in order and index-only, and a category's count with a minimum rating reads it too (see Reading). It then drops and creates `idx_items_cat` again, unchanged, so the narrow index stays the newest and plain counts keep reading it. The index adds about 11 MB at 182k movies; the upgrade builds both, about 0.3 s more on 220k items in a release build (0.8 to 1.1 s) (`migration_perf.rs`), and every bulk rewrite builds one index more.

## rpc

`catalog.categories` (`includeHidden?` for category management, `includeLocked?` for the parental Lock groups dialog, see parental.md), `setCategoryHidden` (NotFound for an unknown id), `setCategoriesHidden` (the list replaces the hidden set; for live groups both refill the phone remote's channel list, see remote-control.md), `channels` (`radio: true` lists radio), `movies`, `series`, `item` (shape follows the content type; an M3U movie also carries its stream `url` and own `headers`, see m3u.md, Movies), `items` (`{refs}`, at most 500, else invalid: one answer per ref in order, `{item}` with exactly what `item` returns or `{error}` with the error it fails with, `not_found` with `details.parentalLocked` included; every lookup runs in one `db_read_call`, so Live's Favorites and Recently watched, the guide's Favorites, the channel pickers, the hidden-channels dialog and My Videos' recording logos ask for the rows on screen in one call instead of one per row; the source kind is read once per source, and the M3U catch-up overrides and custom names are applied once over every channel of the batch (`finish_channels`), where 42 favourite channels cost about 150 statements and 42 config parses one ref at a time), `channelByNumber` (`contentType?: 'live' | 'radio'`; null when none), `neighbors`, `search` (default 30 per type, max 1001 so the UI can probe its 1000-row step with one extra row; radio is returned in `live`), `recentlyAdded` (movie or series only), `matchTitles` (`{sourceId, contentType: 'movie' | 'series', titles: {title, year?, tmdbId?}[]}`, at most 40 titles (`MAX_MATCH_TITLES`), else invalid, as is any other content type: one list of candidate rows per title in order, from one `db_read_call` with one settings and parental read; see Reading), `sameTitle`, `allLiveChannels`.

Every reader here (and `catalog.yearFacets`, vod-browsing.md) runs on the read-only pool through `AppState::db_read_call`, so writers waiting out an import's save never hold the connections these reads need (userstate.md, Pools and write gates). `setCategoryHidden` and `setCategoriesHidden` write through the user-write gate (`db_write`).

`live.alternates {ref}` (module `live`, failover slice) reads the catalog too: the same live or radio channel on other sources (and duplicates in the same one), found through `idx_items_epg`, `epg_channel_map` and `items_fts`. See `failover.md`.
