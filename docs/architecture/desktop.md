# Desktop shell: boot, loopback media proxy and memory trimming

Code: `crates/iptv-tauri/src/boot.rs`, `crates/iptv-tauri/src/early_boot.rs`, `crates/iptv-tauri/src/helper_windows.rs`, `crates/iptv-tauri/src/proxy.rs` and `crates/iptv-tauri/src/memory.rs`, wired up in `crates/iptv-tauri/src/lib.rs` (`run`, `setup`, `open_state`, `boot_state`, `reveal_window` and `on_window_event`). RPC: `app.info` reports `proxyBase`. The rest of the shell (plugins, tray, the `rpc` command, event bridge, deep links, exit cleanup) is in `lib.rs`, and the embedded mpv child window is in `mpv_window.rs` ([players.md](players.md)).

| File | Role |
| --- | --- |
| `boot.rs` | `BootGate`: holds `AppState` once boot has built it; IPC calls and deep links wait on it |
| `early_boot.rs` | Windows only: starts opening the database before Tauri builds the main window |
| `helper_windows.rs` | Windows only: a `WM_CLOSE` sent to the hidden helper windows quits the app |
| `proxy.rs` | Loopback HTTP listener that serves `iptv-server`'s `/api/proxy` route inside the app process |
| `memory.rs` | Windows only: WebView2 memory target level, page visibility while minimized, and working-set trim |

## Boot (`early_boot.rs`, `boot.rs`)

`run` calls `early_boot::start` before the Tauri builder runs, so the database opens while Tauri builds the main window and WebView2. Only the first instance does this: it must create the `<identifier>-boot` named mutex, held until exit, and find no single-instance window. A second launch hands over to the running app and never opens the database on the way. `early_boot` resolves the data folder itself (the roaming app-data known folder joined with the identifier, the folder Tauri's `app_data_dir` gives), starts logging, and spawns `open_state` on the async runtime: `AppState::new` opens and migrates the database, then the loopback proxy starts and `DesktopInfo` is set. Its events go to a `LateSink`, which `setup` connects to the webview; nothing emits before the core modules start.

`setup` takes over that handle when its own `app_data_dir` is the same folder, and otherwise (another folder, no early start, other OSes) spawns `open_state` itself. It does not wait for the database. It manages a `BootGate<Arc<AppState>>` (`StateGate`), the RPC router and the other shell state, then spawns `boot_state`, which awaits `open_state`, registers the mpv window factory, manages the state for `shutdown`, delivers the launch deep links, opens the gate, and runs `init_all`. If opening fails, it logs the error, shows a fatal dialog naming the data folder, and exits with code 1.

The main window is created hidden (`visible: false` in `tauri.conf.json`; the window-state plugin restores its geometry but not its visibility), so `setup` can correct the geometry first. React's first mount invokes `reveal_window` (`RevealWindow` in `src/main.tsx`), so the window opens on the painted shell. Showing it from the page-load event would put the show and focus (about 30 ms on the event-loop thread) where the page's first IPC calls wait for that thread. A page that never renders is shown 1.5 s after it finishes loading (`PAGE_REVEAL_FALLBACK`), and one that never loads 4 s after `setup` (`SHOW_FALLBACK`). Only the first reveal shows the window, so a reload never steals focus.

- `rpc` awaits the gate, so a call made while the database is still opening waits for it. It fails with an `Internal` error ("Tsrust IPTV did not finish starting.") only when the gate is dropped before it opens.
- Deep links from `on_open_url` wait on a `BootWaiter` before they are delivered. Launch links, read with `get_current()` in `setup`, are delivered by `boot_state` just before the gate opens.

Measured from process spawn on a debug build over six warm relaunches: the state is ready at about 85 to 135 ms, and the medians are 684 ms to first paint, 687 ms to the window showing (already painted), 825 ms to the first rows and 872 ms to the first image. Cold launches were not measured.

## Closing from outside (`helper_windows.rs`, Windows)

Closing the app from outside (`taskkill` without `/F`, an installer, the Restart Manager) posts `WM_CLOSE` to every top-level window of the process, not only the main one. The single-instance plugin's window (class `<identifier>-sic`), tao's event target (`Tao Thread Event Target`) and the tray icon's message window (`tray_icon_app`) would hand it to `DefWindowProc`, which destroys them. `setup` subclasses those three on the event-loop thread (`helper_windows::install`), so a `WM_CLOSE` to any of them hides the main window and quits through `quit_flush::quit`, the same save-then-exit path as the window's X. A close while the main window is minimized therefore quits cleanly, and the next launch still finds the single-instance window to hand over to. The subclass removes itself on `WM_NCDESTROY`.

## Exit (`shutdown` in `lib.rs`)

On the first `ExitRequested` or `Exit` event, `shutdown` cancels every running import (`sources::cancel_all_imports`; each keeps its previous catalog and a catalog save rolls back), stops recordings (`recording::shutdown`), kills embedded mpv, gives the remote control server up to 2 s to stop, folds the WAL back into the database (`db::checkpoint_truncate`, which runs `wal_checkpoint(TRUNCATE)` without the busy handler, so a writer still holding the lock makes it do what it can instead of waiting up to 10 minutes), and last calls `db::note_clean_shutdown`. All of it runs on the event-loop thread within `SHUTDOWN_BUDGET` (5 s): the recording stop, the remote stop and the wait for a pooled connection each get what is left of it. Before, quitting during a catalog save left a hidden process waiting for the save to commit, and a relaunch in that window was handed to it, so no window appeared. That removes `iptv.db.running`, so the next start skips the background `quick_check` of a database over 32 MiB when a check passed within 7 days (`iptv.db.checked`; SPEC C3). A crash or a forced kill (`taskkill /F`) leaves the marker, and the next start checks again.

## Loopback media proxy (`proxy.rs`)

### Why it exists

On desktop the webview fetches streams itself (hls.js, Shaka, mpegts.js, `<video>`). A browser cannot set `User-Agent` or `Referer` on those requests, so per-playlist and per-channel headers (`#EXTVLCOPT`, `url|User-Agent=...`, the source's header fields) would never reach the provider. Many providers refuse a stream without them. The proxy fetches the stream on the app's behalf with those headers added. Because every remote stream goes through it, it also lets the inline players read providers that send no CORS headers.

### What it serves

`proxy::start` binds two listeners on `127.0.0.1:0` (random free ports on the IPv4 loopback interface only, never `0.0.0.0`) and serves the same router on both on the Tauri async runtime:

```
GET|HEAD http://127.0.0.1:<port>/<token>/api/proxy?url=<enc>&sourceId=<id>[&ua=&referer=&origin=]
GET|HEAD http://127.0.0.1:<port>/<token>/api/recordings/<id>/<name>
GET|HEAD http://127.0.0.1:<port>/<token>/api/files/<id>/<name>
GET      http://127.0.0.1:<image port>/<token>/api/img?url=<enc>&sourceId=<id>
```

`/proxy` is the same handler as the server's `/api/proxy` ([server.md](server.md)): stored source headers plus the `ua`/`referer`/`origin` overrides, Range pass-through, redirect handling, and HLS playlist rewriting (segment and key URIs point back at the proxy). `/recordings` and `/files` are the server's `/api/recordings/{id}` and `/api/files/{id}` handlers: `ServeFile` streams a recording or a completed download from disk and honours Range, `If-Range` and HEAD. `recordings.playSource` and `myvideos.playSource` return these URLs on desktop (`desktop_media_url`), with `<name>` set to `media.<extension>` so the player picks its engine from the URL (`.ts` goes to mpegts.js); the route ignores it. Before, they returned the file path and the UI played it through Tauri's asset protocol, which reads a file requested without a Range header whole into memory: mpegts.js asks for byte 0 without Range, so a 2.7 GB one-hour recording was read whole before the first frame. When the proxy is not running they still return the path. mpv and VLC get the path back (`player::with_local_file`): an external player outlives the app and its proxy, and mpv reads local files itself. `/img` is the image cache (image-cache.md). Chromium opens at most six HTTP/1.1 connections per host and port, and a multiview wall of four MPEG-TS tiles holds four of them for as long as it plays, so the UI loads artwork from the second listener (`app.info.imageBase`); both listeners serve every route. A path without the token answers 403 (see Guards); under the token, every other path, including `/<token>/api/rpc` and `/<token>/api/events`, answers 404. The proxy builds its own `iptv_server::Server` with an empty `RpcRouter`, so nothing but these routes is reachable. DASH manifests pass through unrewritten; the inline player (`proxyRewrite` in `src/features/player/engines.ts`) resolves their segment, key and BaseURL URIs against the upstream manifest URL and sends them back through the same proxy base (web `/api/proxy` or this token base) with the same `sourceId`/`ua`/`referer`/`origin` params.

`open_state` starts the proxy once `AppState` is built and stores the returned base URLs (`http://127.0.0.1:<port>/<token>/api/proxy` and `http://127.0.0.1:<image port>/<token>/api/img`) in AppState (`DesktopInfo.proxy_base`, `DesktopInfo.image_base`), and `app.info` returns them as `proxyBase` and `imageBase` (`null` in server mode). The UI sends one `app.info` request per launch, from `src/api/bootInfo.ts` (`desktopAppInfo`, invoked as soon as the first module loads). `src/api/transport.ts` takes `proxyBase` from that answer, `src/api/images.ts` takes `imageBase` (or derives the image cache base from `proxyBase` when it is missing), and `src/api/query.ts` seeds the `app.info` query cache entry with it, so later `useRpcQuery('app.info')` readers send no second request. On desktop, `proxiedUrl(source)` routes every remote `http(s)` URL through `proxyBase`, headers or not, so the source's request headers apply and a provider that sends no CORS headers still plays in the inline player (hls.js, mpegts.js and Shaka fetch cross-origin from `http://tauri.localhost`). Only `*.localhost` hosts (Tauri's asset files and IPC) and URLs already on the proxy's own origin (recordings and downloads) load directly, and a local `file` path (the proxy did not start) goes through the asset protocol. Measured on a release `iptv-server`'s `/api/proxy` (the same handler), a playlist plus its first segment took 3.3 ms through the proxy against 2.4 ms direct (median of 15). Until the answer arrives, or if the listener cannot bind (the error is logged and `proxyBase` stays `null`), streams play directly, without their headers.

### Guards

Any local program, and any web page open in a browser on the same machine, can reach a loopback port. The proxy therefore checks every request:

- Token: `start` makes a random per-launch token (`new_token`, 160 bits) and serves the route only under `/<token>/api/proxy`, so `proxyBase` is `http://127.0.0.1:<port>/<token>/api/proxy`. `require_token` answers 403 to any other path (no token, a wrong one, a prefix of it), with or without an `Origin`. The proxy's `ServerOptions::proxy_path` is `/<token>/api/proxy`, so the HLS rewriter writes the token into the URIs of rewritten playlists while it streams them line by line, and segment and key requests keep the token. Only `app.info` reveals the token, and it is never logged.
- Host: `iptv_server::guard::api_guard` runs with the default `AllowedHosts`, which accepts only `localhost`, `*.localhost` and IP literals. A DNS-rebinding page, whose requests carry `Host: attacker.example`, gets 403.
- No cross-site refusal: the proxy's `ServerOptions` set `allow_cross_site`, so `api_guard` skips server mode's `Sec-Fetch-Site: cross-site` refusal here. The webview's origin, `http://tauri.localhost`, is a different site from `127.0.0.1`, and Edge (the WebView2 engine) labels every request the app makes to the proxy `cross-site`: plain and `crossorigin` `<img>`, `<video crossorigin>`, `fetch` and XHR alike (measured in Edge 155). With the refusal on, every proxied stream and every cached image would get 403. The token and Origin checks stand in for it.
- Origin: `webview_origin_only` refuses (403) any request whose `Origin` header is not one of the app's own webview origins (`WEBVIEW_ORIGINS`: `http://tauri.localhost`, `https://tauri.localhost`, `tauri://localhost`, and the Vite dev server on port 5173). Requests without an `Origin` (plain media element loads) pass.
- CORS: `Access-Control-Allow-Origin` is sent only to those same origins, for `GET`/`HEAD` with `Range` and `If-Range`, exposing `Content-Range`, `Content-Length`, `Accept-Ranges` and `Content-Type`. Another page cannot read a proxied response even when its request carries no `Origin`.

The unit test `guards_origin_host_and_sends_cors_only_to_the_webview` covers each rule: a foreign Origin, a non-loopback Host, the webview Origin with CORS headers, and the 404 for `/api/rpc`. `local_recordings_stream_with_range_behind_the_token` serves a recording through `/recordings` with and without Range and refuses it without the token. `cross_site_webview_requests_are_served_but_server_mode_refuses_them` checks that a token-bearing `Sec-Fetch-Site: cross-site` request from the webview reaches the image and proxy handlers, and that server mode's router still answers it with 403.

### `allow_private_targets`

The server binary refuses loopback, RFC 1918, link-local and other non-public targets unless the source's own `host:port` or `--allow-private-targets` permits them. The desktop proxy runs with `allow_private_targets: true`, because users play streams from their own LAN (a tvheadend box, a NAS, a local restreamer) exactly as mpv or VLC would. The remaining checks still apply: only `http` and `https` targets, and no credentials in the URL's user-info part. The desktop `AppState` never installs `ServerMode`, so this setting affects only the proxy's own `NetGuard`; the core's downloads and playlist/XMLTV fetches on desktop are unguarded, as before.

Residual risk: before the per-launch token, a local process or a web page that guessed the random port could make the proxy issue a `GET` to a LAN address; now it also needs the token, which only the app's own webview receives. It cannot read the response (no CORS for foreign origins) and cannot reach the RPC surface. That is the trade for playing LAN streams with headers.

## Memory trimming (`memory.rs`, Windows)

Most of the desktop app's memory belongs to WebView2's browser, GPU, renderer and utility processes, not to the Rust process. The shell uses three levers:

- `set_webview_memory_low(window, low)` sets `ICoreWebView2_19::MemoryUsageTargetLevel` (through `webview2-com`, the version wry uses). `on_window_event` sets it to `Low` when the main window is minimized, which asks WebView2 to drop caches and trim its processes, and back to `Normal` on focus. Losing focus alone changes nothing: an unfocused window is often still playing (picture-in-picture, a second monitor), and `Low` there degrades playback and makes the UI fault back in on every alt-tab. If the WebView2 runtime is too old for `ICoreWebView2_19`, the call fails quietly with a debug log.
- `trim_working_set()` calls `SetProcessWorkingSetSize(GetCurrentProcess(), -1, -1)` on the app process 15 s after startup (pages touched only during boot) and again on every minimize. Trimmed pages move to the standby list and fault back in cheaply.
- `set_webview_visible(window, visible)` calls `ICoreWebView2Controller::SetIsVisible`, sending only changes. For the main window, `on_window_event` asks `visibility_after(event, minimized)`: a size change while minimized hides the page, and any other size change (restore from the taskbar, Alt+Tab, the tray) or focus shows it again. Hidden, the page reports `visibilityState = hidden` and Chromium throttles its timers, animation frames and rendering. Chromium cannot find this out by itself, because native occlusion tracking is off (`CalculateNativeWinOcclusion` is disabled in `additionalBrowserArgs`). Embedded mpv is a separate child window of the main window, so it keeps playing. Checked over raw CDP on a debug build: a minimized window used to stay `visible` and draw 176 frames/s; now it is `hidden` with 0 frames/s while mpv plays on, and a restore brings it back.

Static Chromium flags that keep the WebView2 process tree small (`--renderer-process-limit=1`, disabled Edge features, no extensions, no background networking) live in `tauri.conf.json` under `additionalBrowserArgs`. Other platforms do nothing here.
