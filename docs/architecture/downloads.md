# Downloads and My Videos

Code: `crates/iptv-core/src/downloads/`. Tests: `crates/iptv-core/tests/downloads.rs` (check 9 / SC7), `downloads_conn_limit.rs`, `downloads_segments.rs`, `downloads_stress.rs`, `downloads_engine.rs`, `downloads_mirrors.rs`, `downloads_probe.rs`, `downloads_speed.rs`, `dl_panel_selftest.rs` and `w0_contracts.rs`, `crates/iptv-server/tests/downloads_playback.rs`, plus unit tests in `naming.rs`, `segments.rs`, `transfer.rs`, `shared.rs`, `mirrors/tests.rs`, `manager.rs` and `rpc.rs`.

The download manager keeps a FIFO queue of movie, episode and catch-up programme downloads, runs as many transfers per source as the source's account leaves free after playback (two when it reports no limit), resumes partial files over HTTP Range, and never overwrites a file it did not create. A large file goes over up to 8 connections, from its own source and from identical copies on other sources, and the queue can start a row on another source's copy when its own source is full (see [Faster downloads](#faster-downloads)). Completed rows make up My Videos, the offline library.

## Commands (C4)

`downloads.list`, `downloads.get`, `downloads.start`, `downloads.playSource`, `downloads.pause`, `downloads.resume`, `downloads.cancel`, `downloads.retry`, `downloads.remove {id, deleteFile}`, `downloads.reveal`, `downloads.setDir {path}`, `downloads.dir`, `downloads.setPosition {id, positionSeconds}`, `downloads.prioritize {id}`, `downloads.playback {clientId, sourceIds}`, `downloads.setRateLimit {id, bytesPerSecond}`, `downloads.stats {id}` (the running transfer's `TransferStats`, null when it is not running), `downloads.connectionLimits` (`SourceConnectionLimit[]`: every source's reported and learned limit, how its panel answered, when it was tested and is due again, whether a test runs now or the source is excluded), `downloads.resetConnectionLimit {sourceId}` (forgets the learned limit; a blank id is `InvalidInput`), `myvideos.list`, `myvideos.playSource`.

Events: `downloads.update {}` on every state change (queued, started, paused, resumed, canceled, failed, completed, removed) and `downloads.progress {id, bytesDownloaded, totalBytes?, bytesPerSecond, connections?, sources?}`, at most 4 per second per download (`connections` and `sources` only when above 1). `downloads.stats` (payload `TransferStats`) carries a running transfer's breakdown once a second; see [Stats](#stats). The first chunk of every attempt emits at once, so the UI sees a resumed transfer start where it left off. In the UI a `downloads.update` refetches only `downloads.list` and the `myvideos.` queries (`DEFAULT_EVENT_INVALIDATION` in `src/api/query.ts`), never `downloads.dir`. A `downloads.progress` event re-renders only the /downloads row it is about (`useLiveProgress`), and on a movie or series page only the download control that shows that transfer, which reads the same live sample; progress refetches `downloads.list` nowhere ([performance.md](performance.md#progress-clocks-and-formatters)).

## Lifecycle

```
start -> queued -> downloading -> completed
                     |  ^   \-> failed  -- retry/resume --> queued
              pause  v  | resume
                   paused
cancel (any unfinished state) -> canceled -- retry --> queued
completed (file missing) -- retry --> queued
```

- `start` validates the URL (http/https only) and title, then inserts the row or reuses the row for the same `(ref, episodeId)`. Queued, downloading, and paused rows, and completed rows whose file still exists, come back unchanged. Failed, canceled, and completed-but-missing rows lose any retained `.part` and restart under the same id. Before returning, `start` reserves the destination and persists `fileName`/`filePath`.
- The runtime claims a row with a conditional `queued -> downloading` update. A claim that fails (the database busy or briefly unavailable) is retried with backoff up to 3 times; when all fail, the id goes back to the front of the queue after 30 s instead of being dropped, so the row never stays `queued` with no task behind it; that holds when playback asked it to yield during the retries too. A pause or cancel during the retries is saved by the command that asked for it (the row becomes `paused`, or `canceled` with its `.part` deleted), since the run never claimed the row. `downloads::fail_next_claims(state, n, retry)` simulates failing claims for tests. `resume`/`retry` use a conditional `paused|failed|canceled -> queued` claim and the queue rejects duplicate ids, so two rapid clicks can never start two transfers.
- `pause`, `cancel`, and `remove` signal the running task and wait (up to 15 s) until it has persisted its final state, so the RPC returns only after the change is on disk. If the task is still winding down after 15 s (for example a write stuck on a network share), the RPC fails with a retryable `Timeout` instead of reporting a change that has not happened; the stop request stays in force, and `remove` leaves the row and files alone so nothing is deleted under a live task. Until the task finishes, the row stays `downloading`, so a second `pause` or `cancel` either waits again or finds the final status. A repeated request can escalate the stop reason (cancel beats remove beats pause, never the other way), so a `cancel` sent after a timed-out `pause` still ends `canceled` with the `.part` deleted. `downloads::set_stop_timeout(state, Some(d))` shortens the 15 s wait for tests.
- `pause` on a queued row pulls the id out of the queue and marks it `paused`; it never starts until `resume` (or `retry`) puts it back, even when connections free up. That includes a row waiting for playback: an automatic stop never overrides a manual one.
- `retry` on a completed row whose file is gone (deleted, moved, or replaced by something that is not a regular file) clears the recorded path and progress, keeps `fileName`, and queues the same row again; the new transfer reserves that name in the current downloads folder (next free number if taken) and never touches the old path. A completed row whose file is still there gets `Conflict`.
- `prioritize` (Download next) moves a queued row to the front of the queue, so it takes the next free slot; a running row is left alone and other statuses get `Conflict`. `resume` and `retry` also put the row at the front.
- The order (running ids in start order, then the queue) is saved in `app_state` under `downloads_queue` whenever it changes, by one task that writes the latest order, so a burst of changes costs one write.
- `init` (boot): rows left `downloading` become `queued`, and every queued row is scheduled in the saved order: the rows it lists first, in that order (so interrupted transfers, Download next and resumed rows keep their place), then the rest in creation order (`created_at`, then id). A restored row resumes from its `.part`.

## Connections

IPTV panels count every open file request against the account's `max_connections`, and refuse the next one with 401/403 (or close the oldest). So transfers are scheduled per source:

- Budget (`manager::download_budget`): with a limit `L` from the source's cached account status (`AccountStatus.max_connections`, stored by every Xtream sync and account check; the runtime reads it once per source and `account::record` keeps it current), downloads from that source use at most `L - 1` connections, so one stays free for playback, and never more than `L` minus what plays and records from the source. A 1-connection account downloads only while nothing plays or records from it. An unknown or zero limit (M3U, Stalker, unlimited plans) keeps two files at once per source (`MAX_CONCURRENT`), one connection each, whatever plays. A learned limit above the reported one (amendment A1, [Learned connection limits](#learned-connection-limits)) replaces it and keeps no connection free: the budget is `Ll - playing - recording` (`manager::learned_download_budget`), since yield hands playback its connection back. `DownloadManager::effective_limit` says which limit a source follows and where it comes from (`LimitKind`: reported, learned, unknown). Everything a transfer holds counts against its source, mirror connections and the short holds of fingerprints and verification (`try_hold`) included, so other sources' downloads that read from this one never take what playback needs.
- The pump walks the queue in order and starts every id whose source has a free connection, so a source at its limit never holds up another. An id whose source's limit is still being read waits for that read.
- What plays, per source, is the most any one signal reports: the players' `downloads.playback {clientId, sourceIds}` reports (the frontend sends one when the player's source changes, renews it every 30 s, and clears it on stop, `src/features/player/playbackReport.ts`; a report lapses after 90 s unless renewed, so a closed window never holds downloads back for long), the multi-view wall's report (one entry per tile that is not locked, so two tiles on one source count two; sent when the tiles change, renewed every 30 s and cleared when the last tile stops, `src/features/multiview/wallReport.ts`), and the streams the media proxy has open for the source (`open_stream`, called by `/api/proxy` for requests with a `sourceId`; a closed stream still counts for 30 s, the gaps between an HLS player's segment fetches). Recordings count separately (`hold_recording`, held for the life of a recording run).
- Yield: when a source's budget drops below what its downloads hold (playback starts, a recording starts, the limit shrinks), the newest transfers from that source stop with `StopReason::Yield`: the `.part` is kept, the row goes back to `queued` at the front of the queue (a conditional `downloading -> queued`, so a pause that landed first stays), and it resumes with Range once the connection is free. A user's pause, cancel or remove always wins over a yield. `downloads.playback`, `open_stream` and `hold_recording` return once the yielding transfers have let go (at most 2 s) plus 300 ms, since a panel notices a closed connection a moment after the client closed it, so the stream's own request does not meet a full account. The other way round, each stream a player stops reporting (a zap to another source, a stop, one of the wall's two tiles on a source going) and each recording that ends still takes a connection of its source for 3 s (`manager::RELEASE_GRACE`), on top of what else plays or records there: a player that connects itself lets the old stream go only after its new report is answered (mpv loads the next channel then), the recording's connection closed a moment ago, and the panel counts either a little longer, so a download that started at once would be refused and wait 15 s. A released stream counts beside the players' reports, not beside the proxy's streams: a player that played through the proxy is still among those. A stream through the media proxy waits in `open_stream`. A player that connects to the provider itself (embedded mpv, an external player, a stream the browser loads directly without the proxy) waits for the answer to its window's `downloads.playback` report before it asks for the stream, at most 3 s (`reportAnswered` in `playbackReport.ts`, used by `MpvSurface`, the store's external branch and `InlinePlayer`; a wall tile that loads directly waits for the wall's report the same way, `wallReportAnswered`); with nothing to wait for it goes on at once.
- A refusal (401/403) from an Xtream panel can mean wrong credentials or a full account (another device, or playback the app does not see). The transfer asks the panel for the account (`xtream.accountInfo`, at most once per 20 s per source; a good answer is stored like any account check): when the credentials work, the row goes back to `queued` and its source waits 15 s, then 30 s, 1, 2, 5 and 10 min in a row before the next attempt; when they do not, it fails with the credentials advice as before. A row that waits 2 hours without new bytes fails; a run that got new bytes before it yielded to playback starts that clock and its source's backoff over, as one that got new bytes before an outage does. `downloads::set_wait_timing(state, base, limit)` shortens both for tests.
- Outages: when a run's attempts run out on an error the provider or the network causes, not the file (any network error, refused connections and unknown hosts included, timeouts, 429 and 5xx, and an Xtream refusal whose account check could not reach the panel), the row goes back to `queued` and its source waits with the same backoff, so an outage costs one probe per step instead of failing the whole queue. A run that got new bytes before the outage starts the row's 2-hour clock and its source's backoff over. Errors about the file itself still fail at once: 404/410, a disk error, an invalid certificate, a Content-Range mismatch, rejected credentials. Download next on a waiting row lets its source try again now.
- A row that waits for its source (after a refusal or an outage) goes back behind the source's other queued rows, not to the front: one broken file that keeps answering 5xx or timing out does not take the source's connection first each time the wait ends, so the rows behind it run after one backoff step. A row that yielded to playback goes to the front.
- `Download.waiting {reason, until?}` (live, never stored) says why a queued row waits when it is more than its turn: `playback` (playback holds the connection its account allows), `connection` (other downloads, recordings or devices hold the source's connections; with `until` after a refusal), `provider` (the source could not be reached; `until` is the next attempt). `/downloads` shows it on the row.

## Destination policy

This follows the old app's `docs/architecture/download-manager.md`, "Destination collision policy":

- Folder: `settings.downloadsDir` when set, else `<data dir>/downloads` (`AppState::downloads_dir`, amendment A5: inside the Tauri asset scope).
- Name: `fileNameHint` (last path component only) or `title` plus ` - subtitle` when present. The extension comes from the hint, then the URL path, then `mp4`. Sanitizing replaces `<>:"/\|?*` and control characters with `_`, collapses whitespace, strips trailing dots and spaces, prefixes Windows device names (`CON`, `NUL`, `COM1`, `LPT1`, ..., also `con.backup`) with `_`, and caps the stem at 150 characters.
- Reservation: the first `name.ext`, `name (1).ext`, ... whose final path is absent and that no other unfinished row records (`store::held_paths`, compared without regard to case: NTFS and APFS take `Movie.mp4` and `movie.mp4` for one file) gets its `name.ext.part` created with `create_new`. That call is atomic, so concurrent starts can never share a name. The final path stays absent until completion. A paused row whose `.part` was deleted by hand (to free space) keeps its name: another download of the same title gets the next number, and the paused row reserves its own name again when it resumes. A retained `.part` is adopted (or moved to a new downloads folder) only when no other unfinished row records the same path in any case, so two rows that shared a name before reservations checked the rows never write into one `.part`. On a file system that tells case apart, a row whose name differs from another's only in case (reserved before the check ignored case) starts over under a new name instead.
- The `.part` is opened only after `symlink_metadata` confirms a regular file, so a symlink planted while the download was paused is never followed.
- Completion moves the `.part` into place without overwriting. `std::fs::rename` replaces existing files, so the move uses the platform's no-replace rename: `renameat2(RENAME_NOREPLACE)` on Linux, `renamex_np(RENAME_EXCL)` on macOS, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows. It fails atomically when the target exists and also works on FAT/exFAT and network shares, which have no hard links. Where the call is unsupported (an old kernel, a share that rejects the flag), a hard link (also atomic) followed by deleting the `.part` takes over, and file systems without either fall back to copying into a destination opened with `create_new`, then deleting the `.part`, which is equally atomic about the destination but reads and writes the whole file again and needs its size in free space. When the recorded final path got occupied (for example the user created `Movie.mp4` while the download was paused), the next free numbered name wins (`Movie (1).mp4`, with both final and `.part` free) and the row records it.
- Pause keeps the `.part`. Cancel deletes it and clears `fileName`/`filePath`. A failure keeps it when the total size is known and bytes reached disk (retry continues via Range); otherwise it is deleted. A `.part` that cannot be deleted (locked file) keeps its row and path so a later cancel or remove retries the cleanup.
- `remove {deleteFile}` deletes the row's file only when `deleteFile` is true: the `.part` of an unfinished row, or the media file of a completed one (only if it is a regular file). With `deleteFile: false` an unfinished row's `.part` stays on disk; a later download of the same item reserves its own `.part`, so the kept one is never reused or overwritten. A completed row's leftover `.part` is always deleted.
- `fileAvailable` is derived on every read for completed rows: true only for a regular, non-symlink file at `filePath`. `downloads.list` and `myvideos.list` check their files on the blocking pool (`present_all`), so a file on a sleeping disk does not hold up a runtime worker. A missing file never changes the persisted `completed` status. Starting the same item again re-downloads it.

## Transfer

- URL refresh: every run (start, resume, retry, restart after a missing file, boot restore) re-resolves the stream URL from the row's `ref` and `episodeId` before the first request, except for catch-up programmes (live and radio refs): their archive URL cannot be rebuilt from the ref, which would give the live stream, so they keep the stored one. Xtream rows go through `xtream::service::stream_url` (the URL embeds the source's current credentials) and Stalker rows through `stalker::playback::stream_url` (a fresh tokenized `create_link`). The new URL and its headers replace the stored ones (`store::set_source`). M3U/file sources, rows whose source was removed, and resolution failures keep the stored URL, and the transfer then reports whatever the server says. A pause or cancel during resolution stops the run at once. The file name reserved at `start` does not change.
- `GET` through `state.http` with the stored source headers (`headers_json`: User-Agent, Referer, Origin) and `Accept-Encoding: identity`, so byte offsets and `Content-Length` describe the file itself.
- Resume: a non-empty `.part` resumes only with evidence about the representation, meaning a stored `resume_validator` (strong ETag, else Last-Modified) or a recorded `total_bytes`. The request sends `Range: bytes=<offset>-`, plus `If-Range: <validator>` when a validator exists. A `206` must have a `Content-Range` that starts at the offset, and its total must equal the recorded total. A mismatch fails the run and discards the `.part`, because a tail cannot be rewritten in place. Any other `2xx` (Range ignored, or If-Range detected a change) restarts from byte zero over the same `.part`. A `416` truncates and restarts. A `.part` already at the recorded total is finalized without a request. A partial with neither validator nor total restarts from zero.
- Idle limits: the request goes through `http::send_within` with a 15 s limit on the response head (`HEADER_TIMEOUT`), and the copy loop waits at most 20 s (`BODY_IDLE_TIMEOUT`) for the next body chunk. Either becomes a retryable `Timeout`, so a panel that accepts the connection and never answers, or stops sending in the middle of the body, costs 15 or 20 s and a reconnect with Range instead of the shared client's 60 s read timeout. The idle timer starts after the rate-limit sleep, so a speed cap never trips it. `downloads::set_idle_timeout(state, Some(d))` shortens both limits for tests.
- Retry: network and timeout errors, including a body that ends before the advertised size, are retried in the same task with `http::backoff_delay` (300 ms x 2^n plus jitter). After 5 consecutive failures without new bytes the run ends: an outage waits for its source (see Connections), anything else fails the row. Only passing the highest offset this run has written counts as new bytes and resets the counter: an attempt that restarted from zero and re-read what it already had does not, so a run against a server that sends a few bytes and then stalls ends after 5 attempts instead of going on forever. Pausing or canceling interrupts the backoff sleep.
- Progress is written to SQLite every 2 s and when an attempt ends. The periodic write runs in its own task, so the copy loop never waits for it (an import can hold the write lock for seconds), and passes the background gate (`AppState::db_background`, userstate.md) so waiting downloads park one pooled connection between them and the other periodic writers; while one is in flight the next is skipped, and the attempt's final write waits for it, so an older count never lands last. `downloads.list`/`get` overlay the live in-memory byte count for running transfers.
- Every attempt ends with `flush` + `sync_data` before the outcome is recorded. The connection closes first (unless it is handed over to segments), and a segment worker closes its own before its last write and sync, so a connection playback waits for is free at once even while an import holds the database's write lock and the progress write waits for it. For the same reason the file's size and validator, read from the answer's head, are recorded in a task of their own that the attempt waits for only once its stream is gone, and a stream kept for the hand-over to segments is let go when the transfer is asked to stop while the attempt's last progress write waits for the database.
- Several connections per file (`segments.rs`, `segments/engine.rs`): with the source's "Connections per download" on Auto (the default; `settings.downloadSingleConnection` lists the sources set to 1) and no speed cap, a fresh start asks for `Range: bytes=0-`. A `206` with a total is enough to split: a validator is no longer required, since the overlap checks (below) catch a file that changes under a transfer without one, and `If-Range` goes along only when the source has a validator. The rest of the file is split when at least 8 MiB (two `MIN_SEGMENT`s) is left, the `.part` can hold sparse writes, and one of these holds: the transfer may hold 2 or more connections on its source (`DownloadManager::allowance_on`: what its budget leaves after every other holder, and 1 while anything plays from it, a queued row could start there, or its limit is unknown), a mirror plan exists ([Mirrors](#mirrors)), or a connection-limit probe is due (amendment A5: a transfer with at least 32 MiB left, `PROBE_MIN_LEFT`, goes through the engine on one connection so the probe can run beside it). The open answer serves the first segment; each other one is a `GET` with `Range: bytes=a-b`, and the writer thread puts its bytes at their place ([Writer](#writer)). Every 250 ms (the first time after 20 ms) the coordinator reports progress and re-reads each source's allowance, "Connections per download", Max connections per file (`settings.downloadMaxConnections`, 0 = Auto) and the speed cap: it starts free segments, splits the largest remainder in two while both halves keep 4 MiB, or retires its newest workers (their segments stay unfinished, to be picked up again). So it drops to one connection when playback starts on the source and takes the others back when it stops. A transfer that started on one connection checks every second (`SPLIT_CHECK`) and hands its open stream over when connections free up. At most 8 connections per file (`MAX_CONNECTIONS`), reached through the ramp ([Ramp and recycling](#ramp-and-recycling)). `Download.connections` and `Download.sources` (live) say how many connections and sources a running transfer holds when more than one, and the row shows them.
- The sidecar `<name>.part.ranges`, version 2: `{version: 2, total, sources: [{copy, validator}], segments: [{start, end, pos, src, checked}]}`. `sources[0]` is the authority, the source the run downloads from; `copy: null` means the row's own item, otherwise a `CopyRef` (`{ref, episodeId?}`; the ref names the copy's source) of an identical copy. A segment's `src` indexes `sources`, and `checked` says its bytes were compared with another request's. URLs are never stored: a resume resolves every copy again. A version 1 sidecar (`{total, validator, segments: [{start, end, pos}]}`) loads as one source with every segment checked, so a transfer started before this version resumes. A version 2 sidecar reads as `Invalid` in an older build, which deletes it with its `.part` and starts over, never trusting the `.part`'s length. When a resume's authority is not `sources[0]` (queue spreading started the row on another copy), `Ranges::adopt` moves it to index 0 and renumbers the segments. The sidecar is written before any segment writes past what the `.part` already holds, whenever the plan gains a segment, every 2 s and when the attempt ends, with positions only for bytes the writer reports written, and each save syncs the `.part` first (`segments::save_synced`), so after an OS crash or a power cut it never marks bytes as written that the disk does not have. Every save runs beside the workers. One save is in flight at a time (they share the temporary file): the save every 2 s is skipped while another is in flight, and a plan save starts once the one in flight lands. The segments a plan save is for start only once it lands, and only as many as the transfer may still hold then; meanwhile the coordinator keeps retiring workers when playback asks for connections and keeps watching the stop token. `downloads::set_slow_sync(state, d)` makes every save take `d` longer for tests. While it exists the `.part`'s length means nothing: a later run whose total and authority validator match resumes each segment where it got to (one after another when the setting is 1); one that does not match is discarded with its `.part`, and so is one that cannot be read, does not cover the whole file, or records bytes past the end of the `.part` (`segments::Sidecar::Invalid`): such a sidecar is never read as no sidecar, which would trust the `.part`'s length. A mirror whose validator changed since the sidecar was written has its segments reset, the authority's and other mirrors' bytes stay. A fresh reservation deletes any sidecar left under its name, so a `.part` deleted while paused starts over. Pause, cancel, remove, a retry from scratch, a downloads-folder move and a completed transfer all treat the sidecar with its `.part`; every cleanup deletes the `.part` first and the sidecar only once the `.part` is gone (`segments::remove_part`), so a `.part` that could not be deleted (a locked file) keeps its sidecar. A row whose `.part` is deleted (cancel, a failure that cannot resume) also loses its `origin` (`store::clear_destination`).
- Any segment answer that is not exactly the range asked for (a `200` because If-Range saw a change or ranges stopped working, a `416`, another start or total) drops the `.part` and its sidecar, and the file starts over with one connection for the rest of the run, so a changed file is never stitched together. A segment request the provider refuses with an HTTP error status (any answer but a 2xx or a `416`) while another connection of the transfer works means the account has less room than its limit says (amendment A8: only an HTTP status forces one connection): the transfer goes on with one connection for the rest of the run, the sidecar keeps the segment, and an untouched segment that follows the open answer's goes back to it, so that stream reads on without a new request. The segment it leaves empty stays in the plan (workers address segments by index) and covers nothing, so a sidecar that records it is still one a resume trusts. A worker that cut a chunk at its segment's end has dropped bytes its stream sent, so it stops reading that stream even when the end moved on meanwhile (such a hand-back landing while it waited for that chunk), and the rest of the segment gets its own request; read on, the stream's bytes would land shifted by what was dropped. An extra connection that cannot be opened (a connect failure, or no answer headers in time) is asked for again after 1, 2 and 4 s (`RETRY_BASE`, doubling), up to 4 tries (`OPEN_FAILURES`), while the others go on; a dead pinned address is handled as in [Redirect pinning and DNS spreading](#redirect-pinning-and-dns-spreading). A segment's request waits 300 ms after another connection of the transfer closed, since a panel counts a closed connection a moment longer. Other segment errors end the attempt like a single stream's, and the next attempt resumes the segments. A segment write that fails drops what it held: write(2) may have stored part of it and moved the file's position, so writing it again would land it shifted, and none of it was recorded.
- On Windows the `.part` is marked sparse (`FSCTL_SET_SPARSE`) before a split: NTFS otherwise zero-fills everything up to a write far past the end first. On Linux `statfs` rules out the file systems that zero-fill such a gap (FAT, exFAT, HFS, HFS+) and the mounts whose holes depend on a server or a userspace driver (SMB/CIFS, 9p as WSL shares Windows folders, VirtualBox shares, FUSE); on macOS only APFS and ZFS qualify. A file system that cannot leave holes keeps one connection for the rest of the run: it is asked once, before the stream would be handed over, so the transfer never breaks its stream to find out. `downloads::set_no_holes(state, true)` makes every `.part` behave that way for tests.
- Error messages stored in `errorMessage` name the problem and the next action, and never contain the URL (reqwest errors are stripped of URLs in `error.rs`).
- `settings.downloadRateLimitBps` sets the default cap **per download**; zero, the default, is unlimited. It is not a shared aggregate bandwidth budget. `settings.update` persists changes and running transfers read the current setting.
- `downloads.setRateLimit {id, bytesPerSecond}` saves a row override in `downloads.rate_limit_bps`: null inherits the current default, zero explicitly removes the cap, and a positive integer is bytes/s. Both settings accept up to 1 GiB/s. Overrides survive pause, resume, retry and app restart. Existing rows inherit the default. The queue claim and speed update use the serialized DB write gate, so a starting task cannot overwrite a newly saved override with a stale value.
- Running transfers read their effective cap on each chunk and at most every 200 ms while throttled. A cap change restarts the pacing baseline without restarting the HTTP request. No DB queries are made in the pacing loop. `downloads::set_rate_limit` is an in-memory-only test hook that changes the global default to make pause points deterministic.

## Faster downloads

A provider that caps each connection's speed delivers a file N times faster over N connections, and an account's connections can be spread over several sources that carry the same file. Everything below serves that, under one rule: a file never mixes bytes of two versions of itself, and playback and recordings always come before downloads.

### Overlap checks

Every byte of a completed file was either compared with another request's bytes or came from the authority under its validator; a segment records this in the sidecar as `checked`. The engine compares at three points:

- Lead-in: a worker that resumes a segment, or starts right after a finished one, asks for up to `shared::OVERLAP` (64 KiB) before its position and compares those bytes with what is on disk.
- Tail: a worker reads up to 64 KiB past its segment's end and compares them with the start of what the next segment wrote, unless both are confirmed already.
- Final: before the file completes, a segment that is still unchecked gets a short request (up to 64 KiB) compared with what is on disk.

A comparison involving a mirror counts only with at least `MIN_OUTSIDE` (4 KiB) outside the three sample windows (`outside()`), since the mirror was already compared inside them. A mirror is never compared with itself. The authority compared with itself always counts, with or without a validator: it shows the file did not change between the two requests. Mismatches:

- Both sides are the authority: the file changed under the transfer. The `.part` and its sidecar go, and the file restarts on one connection (`OneConnection {reason: changed}`).
- A mirror is involved: that mirror's segments are reset (their bytes discarded), `mirrors::record_mismatch` records it (against the authority's bytes the pair is recorded `Differs`; otherwise the pair's Identical verdict and the mirror's fingerprint are dropped so the next use re-verifies), a `MirrorMismatch` note is pushed, and the mirror leaves the transfer for the rest of the run.
- A mirror whose answer shows its file changed (a range that is not the one asked for, another total or validator) leaves the transfer the same way, and its Identical verdict with this item is dropped (amendment A8), so the next run verifies it again instead of trusting a copy that moved on.

Invariants (amendment A7): a segment's `end` never moves below `queued`, the bytes already handed to the writer, so a split or a hand-back never strands a block in flight; and a running transfer holds at least one connection on its authority, so mirrors never carry a file alone.

### Mirrors

A mirror is an identical copy of the row's title on another source. Only movies and episodes of at least 8 MiB (`MIN_MIRROR_TOTAL`) qualify, never live, radio or catch-up, and only while `settings.downloadUseMirrors` is on (the default). The setting applies live (amendment A8): turned off, running transfers drop their mirrors at once, each one that served with a `mirrorDropped` note of reason `unavailable`, and the pump stops spreading queued rows to other sources.

- Discovery (`mirrors/discover.rs`): movies by title (`catalog::same_title`); episodes by their series' title, then the primary episode's season and episode numbers in each other series. Xtream sources are always searched; Stalker and M3U ones are best effort. At most 4 series' seasons are read at once (`SEASON_READS`), each series within 20 s (`SEASON_LIMIT`). `has_candidates` is a database-only check under 5 ms, so a transfer with no candidate costs nothing.
- Fingerprints (`mirrors/sample.rs`): the total and the SHA-256 of three 64 KiB windows at `[0, align_down(total / 2, 64 KiB), total - 64 KiB]` (`shared::sample_offsets`), read one `Range` request after another on one connection the caller holds. The second and third go to the URL the first was served from, and back to the copy's own URL once when that fails. Every answer must be a `206` for exactly the window, with the first answer's total and validator. The authority's fingerprint is read over the transfer's own connection before its main request, unless a cached one still matches (`mirrors::still_matches`: same total, and same validator when it has one).
- Verification (`mirrors/verify.rs`, `identical_copies`): a candidate is a mirror only with the exact total and all three hashes equal. Each candidate source is checked on its own task, its candidates one after another under at most one connection hold (`DownloadManager::try_hold`, `HoldPurpose::Verify`), taken only when the network is needed; one candidate may take 45 s (`VERIFY_LIMIT`) before it counts as unavailable. A source that refuses the hold (no spare connection) is recorded `Unavailable` marked busy, which stands only 2 minutes (`cache::BUSY_TTL`) instead of an hour (amendment A8): busy is not broken. The first identical copy on a source ends that source's checks. Sources are tried in order of spare connections (most first), then fewest holders, then catalog order.
- Verdicts (amendment A6): a copy with other bytes is recorded `Equivalent` when `mirrors::equivalent` holds (same quality, same container, total within 15% of the larger), else `Differs`; one that could not be checked is `Unavailable`. Equivalent copies are never used as mirrors; only queue spreading reads them.
- The cache (`mirrors/cache.rs`): one `MirrorRecord` per copy in `app_state` under `dl_mirror:<sourceId>:<hash>` (version 1), with the copy's fingerprint and up to 50 verdicts. A fingerprint with a validator stands while the copy's total and validator are unchanged; one without stands for 7 days. Identical and Equivalent stand for 30 days and only while both fingerprints still agree with what was compared; Differs for 30 days; Unavailable for 1 hour, or 2 minutes when the source was only busy. A record that does not parse, or has another version, reads as absent. Deleting a source drops its own mirror records and its `dl_conn_limit:` record, and `mirrors::forget_source` strips every verdict that names one of its copies from the other sources' records, in the same transaction (amendment A8); reads skip any copy whose source is gone, and verification and `record_mismatch` write nothing when either source is gone, so a removed source's keys are never recreated.
- In a transfer: the engine looks for identical copies beside the running transfer and adds each one found (`MirrorAdded`), resolved through `shared::resolve` with its source's client. Mirrors get connections only after the authority has what it may hold (round robin between mirrors), and on a mirror's source only what `allowance_on` leaves: 0 while anything plays or records there, a queued row could start there, or the source refused a mirror connection less than 120 s ago (`MIRROR_COOLDOWN`, `mirror_refused`). A mirror leaves the transfer (`MirrorDropped` with a reason) when it refuses, after 3 stream failures (`MIRROR_FAILURES`), when playback or the queue needs its source, or when it cannot be resolved. A transfer that started with a mirror plan searches again every 60 s (`FIND_EVERY`, amendment A8) while mirrors are allowed, more than `PROBE_MIN_LEFT` (32 MiB) is left and no mirror serves it, so a copy whose source was busy at the start joins once it has room. Nothing about mirrors ever fails a download.

### Learned connection limits

Some panels allow more connections than the account reports. `probe.rs` finds out, at most once a week per source:

- When: `probe::probe_due` holds for an Xtream or Stalker source not in `settings.downloadProbeDisabled`, whose record is missing or due, with nothing playing or recording from it, no probe running on it, no wait after a refusal, a transfer that holds everything its source gives it, and an effective limit below the engine's cap plus one. A transfer whose answer is splittable, with at least 32 MiB left and a probe due, goes through the engine on one connection so the probe runs beside it (amendment A5). A probe runs only when the transfer may split (amendment A8): never under a speed limit, never for a source set to one connection (`downloadSingleConnection`), and never for a run that fell back to one connection (refused, changed, or no holes: each fall-back sets `TaskCtl::set_one_connection`). After a round aborts, the source is not probed again for 10 minutes (`manager::PROBE_ABORT_BACKOFF`); the wait is kept in memory only, and `downloads.resetConnectionLimit` does not clear it.
- A round opens extra `Range` requests near the file's end, one at a time, and holds each for 3 s (`ProbeTiming::step`). It never reads their bodies (amendment A8): a probe connection only shows whether the panel takes it and keeps it. It stops at the first refusal, at a kick (the panel ended the oldest connection to take the new one), or at 9 connections (`MAX_CONNECTIONS` + 1). A refusal is any answer that is not 2xx, a reset, or no answer within the head limit. A kick is seen only from the transfer's own stream dropping (ending with an error) while the round runs; probe connections are never read, so they cannot show one. The outcome: a refusal records mode `refuse` with the number of connections open before the refused one; reaching the cap records `accept` with that number; a kick records `kickOldest` with one less than what was open (at least 1). The count is stored as a `LimitRecord` under `dl_conn_limit:<sourceId>` with the panel's mode (`refuse`, `kickOldest`, `accept`), the reported limit at the time, the last 20 steps, `probedAt` and `nextProbeAt` (7 days later, `ProbeTiming::retest_after`).
- A round never touches the row: no settle, no account check, no wait. It aborts, recording nothing, only when the transfer stops or playback or a recording starts on the source, and it closes every connection it opened before it returns. A refusal within 3 s of a round's end (`AFTER_PROBE`) is the panel still counting the probe's connections, so the engine asks for that segment again instead of dropping to one connection. A segment connection of the transfer that ends with an error while a round runs is read as the kick, and its segment is asked for again.
- Use: a learned limit above the reported one becomes the source's effective limit (amendment A1, see [Connections](#connections)); at or below it, nothing changes, whatever the mode. Settings shows the learned count ("Test found N allowed") when the round ended at the cap, when the account reports no limit, or when the count is above the reported limit; otherwise it says how the round ended ("Test found extra connections refused", "Test found the oldest connection dropped"). Its "Forget result" button calls `downloads.resetConnectionLimit`. A source in `downloadProbeDisabled` is never probed and its learned limit is ignored. `downloads.resetConnectionLimit` deletes the record, so the source follows its reported limit at once and the next eligible transfer tests again.

### Queue spreading

When a queued row's own source has no room, the pump may start it on another copy (`manager/spread.rs`). Only rows that are fresh (no bytes counted, no `.part` content, no sidecar) or that have a version 2 sidecar are placed elsewhere (amendment A8): a v2 sidecar records which copy wrote each segment, while a plain `.part`, or a v1 sidecar, cannot say whose bytes it holds. A plan lists, per queued row, the copies it may run on: copies with a standing Identical verdict (of its origin, when it has one), and, for a row without an origin, copies with an Equivalent verdict. Plans stand for 30 s (`PLAN_TTL`). Equivalent copies are used only while `settings.downloadAllowEquivalent` is on (off by default) and the row is fresh (no bytes counted, no `.part` content, no sidecar); the claim checks freshness again and stores the copy as the row's `origin` (`origin_json`, migration 0030) in the same write. From then on the row is bound to that copy's bytes: a retry or a resume reads the origin, and only clearing its destination (`store::clear_destination`) or starting the row over clears it. A spread run that finds a plain `.part` (no sidecar) starts from byte 0 instead of continuing it (amendment A8), since those bytes came from the row's own copy, and it keeps a v2 sidecar naming the spread copy, also on a single stream, so a later run on another copy compares those bytes instead of taking them for its own. When a spread run's first answer contradicts what the copy was verified as (another total or validator than its verdict or its cached fingerprint records), the pair's Identical verdicts are dropped (`record_mismatch`) and the row goes back to the queue with a provider wait (`WaitReason::Provider`, about 15 s on that source), then runs on its own source or a copy verified again. Identical targets come from `mirrors::cached_identical`, which lists only standing verdicts; an Equivalent target must also still match the copy's cached fingerprint on total and validator. A row running on another source than its own reports it as `Download.servedBy`, and its row says "From <source>".

Before a row claims its own source, the pump fingerprints up to K of that source's queued rows with candidate copies elsewhere (K = 1 + the candidate sources with room, at most 8, `BATCH_MAX`) on the connection the run already holds there, and has each verified on those sources, so rows with identical copies spread at once. Each row is batched once per run of the queue. The pump also resolves the queue's front row ahead (its origin's copy, or its own) and keeps the endpoint for 60 s (`PRERESOLVE_TTL`, `take_preresolved`), so its run starts without waiting for the provider.

### Redirect pinning and DNS spreading

- Many panels answer a file request with a 302 to an edge server. A segment request goes to the URL the connection's last answer was served from (`resp.url()`), not through the redirect again. When the pinned target fails (an edge token can expire), the engine asks the original URL once more, clears the pin and pushes `UrlRefreshed`. Pins get their client from `http::source_client`, so server mode's trust check applies to the edge host.
- A host with several addresses: a connection recycled for being slow reopens on the host's next address (`http::host_addresses`, in DNS order, then `http::pinned_client`, a client bound to that address and kept per host). A pinned address that fails to connect is dead for the rest of the run: it is skipped from then on, and the request is retried once on the normal client (amendment A8). A connect failure is not a refusal; only an HTTP error status drops a transfer to one connection. `pinned_client` returns `None` in server mode, so there connections go through the normal client and DNS spreading is off; the engine also does no slow-connection recycling in server mode (`http::is_server_mode`, checked before each `recycle` pass). `downloads::set_dns_override` (re-exported from `http`) fixes a host's addresses for tests.

### Ramp and recycling

A split starts with 2 connections (`FIRST_TARGET`). Every gain window (`RampTiming::gain_window`, 1 s) the coordinator adds one while the total speed rose by at least 10% (`GAIN` 1.1) since the last one; when an added connection gains less, it gives that one back and adds nothing for 30 s (`LINE_HOLD`): the line, not the provider, is the limit. The ceiling is `min(downloadMaxConnections or 8, 8)` and every source's allowance. A connection running below half the median speed for `recycle_after` (10 s) is closed and reopened on the host's next address: never in its first 5 s (`RECYCLE_MIN_AGE`), never more than once per 30 s per connection (`RECYCLE_EVERY`), and at most one per tick. Final-check requests are left out of the median. Recycling does not run in server mode (`iptv-server`), which has no address pinning to reopen on; the ramp does.

### Writer

Workers gather 1 MiB blocks (`writer::BLOCK`) and hand them to one blocking thread that owns the `.part`'s write handle; at most 16 blocks wait for it, all workers together (`QUEUE`), which bounds memory and slows the network when the disk is slower. A block lands only where its segment's recorded position is, in the segment's current epoch (a segment reset bumps it), and never past the segment's end; its bytes count as written (`pos`) once the write returned, so a sidecar never claims bytes the OS does not have. The thread syncs and closes its handle before the attempt ends, so the transfer can rename or delete the `.part` (on Windows a file open elsewhere cannot be). `downloads_speed`'s `writer_keeps_up` (spec check 15) runs a loopback split over 6 to 8 connections and asserts 100 MB/s only in a release build.

### Stats

`TransferStats` (`segments/stats.rs`) is published once a second (`STATS_EVERY`) by segmented attempts and single streams alike: as the `downloads.stats` event, in `Download.stats` for a running row, and through `downloads.stats {id}`. It holds the total speed over the same window as `downloads.progress`; each open segment connection (`ConnectionStat`: source, the host actually used after pinning, the pinned address, speed, bytes, age); each source (`SourceStat`: role `primary` or `mirror`, connections, speed, bytes, limit and `LimitKind`); what limits the speed; and up to 5 notes from the last 60 s (`TransferNote`: a mirror added, dropped or mismatched, a probe's result, a fall-back to one connection, a refreshed URL). `perConnection` (the connections' median speed) shows when every usable source is at its allowance and the connections run on more than one source, where no single account explains the speed (amendment A8); on one source, `accountLimit` names the limit, and `perConnection` shows there only when nothing else applies. The limiting factor is the first that applies in this order: `speedLimit`, `noRanges`, `smallFile`, `singleConnection`, `maxConnections`, `playback`, `otherDownloads`, `refused`, `line`, `perConnection`, `accountLimit`. The UI's Speed details popover reads it.

### Settings

| Setting | Default | Backed up | Meaning |
| --- | --- | --- | --- |
| `downloadMaxConnections` | 0 (Auto) | no | Most connections per file, 1 to 8; Auto means the engine's 8. |
| `downloadUseMirrors` | true | yes | Read from identical copies on other sources, and spread queued rows to them. Applies live to running transfers. |
| `downloadAllowEquivalent` | false | yes | Let the queue start a fresh row on an equivalent copy. Has no effect, and its switch is disabled, while `downloadUseMirrors` is off. |
| `downloadProbeDisabled` | `[]` | no | Source ids never probed; their learned limits are ignored. Source ids differ between installs. |

Settings validation rejects a `downloadMaxConnections` above 8, and `downloadProbeDisabled` is trimmed and deduplicated like `downloadSingleConnection`.

## Folder, reveal, playback

- `downloads.dir` returns the effective folder. `downloads.setDir` requires an absolute, existing directory and proves it is writable with a `create_new` probe file that it then deletes. It then stores the path in `settings.downloadsDir` through B2's `iptv_core::settings::save`, which validates, writes the settings row, refreshes the `AppState.settings` cache, and emits `settings.changed` (nothing is written and no event fires when the folder is unchanged). An empty path resets to the default. Rows that already have a destination keep it, so switching folders never strands a paused download.
- `downloads.reveal` (desktop only; `Unsupported` on the server) opens the containing folder. On Windows it uses `explorer /select,` so the file, or its `.part`, is highlighted.
- `myvideos.list` lists completed rows, most recently completed first, with `fileAvailable`. `myvideos.playSource` returns `kind: 'file'`. On desktop the URL is the loopback proxy's `.../files/{id}/media.<ext>`, which streams the file with Range support ([desktop.md](desktop.md#what-it-serves)); when the proxy is not running it is the absolute file path, which the UI converts with `convertFileSrc` (amendment A5). mpv and VLC are handed the path either way. On the server it is `/api/files/{id}`. `resumeSeconds` comes from `downloads.setPosition`. A missing file returns `NotFound` with a hint to download again.
- `downloads::completed_file(state, id)` resolves the path of an available completed download. The server's `GET /api/files/{id}` uses it.
- `downloads.playSource` lets an active catch-up download play from its stored provider URL and request headers while the transfer continues. It uses a separate provider request because `.part` may not be seekable or playable until complete. If the transfer finishes before the action is handled, it returns the completed local file source. The download row stores the programme duration for seeking and playback pacing.

### The dl_panel lab

`crates/iptv-core/tests/dl_panel/` is a scriptable provider on loopback. Besides what `downloads_segments` uses (files whose every byte is known, `Range` and `If-Range`, a speed cap per connection, an account limit counted per open body with a panel's lag, random and scripted faults), `Panel::with(PanelOptions)` models what separates real panels: validators (ETag, Last-Modified, both, or none, in which case `If-Range` is ignored), the limit mode (refuse with 403, or accept and end the oldest open body), copies that differ everywhere or only outside the three fingerprint windows (`Variant`), 302 redirects to `/edge/{id}?t=<token>` on the same listener or a second one with tokens that expire (`Redirect`), and one byte budget shared by every panel on a line (`Line`). `cargo test -p iptv-core --test dl_panel_selftest` checks the panel itself (shared line cap, validator modes, same-host and edge redirects, kick-oldest, variants, Xtream info JSON read through the app's own code, `same_title` finding the copies, a second loopback address, open bodies ending with the panel).

`cargo test -p iptv-core --test downloads_speed -- --nocapture` is the speed lab: panels at about 6 MiB/s per connection, accounts that report 1 connection, a 24 MiB/s line shared by every provider, panels without validators, kick-oldest panels. Each scenario prints `SCn: before X.X MB/s, after Y.Y MB/s, ratio Z.ZZ` and asserts the ratio, byte-exact output, and that no panel saw more connections than it allows. SC1: four accounts with identical copies fill the line. SC2: a provider without ETag or Last-Modified still splits. SC3: a copy that differs is never used, one that differs only outside the windows is caught by the overlap checks, and a file that changes under a no-validator split restarts on one connection. SC4a, SC4b, SC4c: probes against a panel that allows 3, a refusing one (once a week), and a kick-oldest one, with no corruption. SC5: a season queued on one account runs on four. SCr: a 302 to an edge host is resolved once, pinned, and split. `mirror_yields_to_playback`: playback starting on a mirror's account takes its connection back within about a second (a `mirrorDropped` note of reason `playback`), and the file still completes byte-exact. `writer_keeps_up` runs over 6 to 8 connections and asserts 100 MB/s only with `--release`. Timings are shortened through the test hooks, and debug builds assert ratios, never absolute rates.
