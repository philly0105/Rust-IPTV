# Guide programme search

Code: `crates/iptv-core/src/epg/search.rs` (core), index upkeep in a refresh's swap in `store.rs` (`commit_staging`), migrations `crates/iptv-core/src/db/migrations/0015_guide.sql`, `0019_guide_search_speed.sql` and `0028_guide_search_feed_index.sql`. Tests: `crates/iptv-core/tests/guide_search.rs` (matching, window, limit, hidden and locked channels, the scan before the index exists, scan and index parity on Greek and Vietnamese titles, index upkeep, query plans, timing on 200k programmes and a 50k-channel source), `crates/iptv-core/tests/l3_search_epg.rs` (two large sources on one guide: hits against an independent model and the scan, query plans, release p95) and unit tests in `search.rs` (the fold's pinned output, the marker), `store.rs` (swaps through both upkeep paths compared term by term with a fresh rebuild through `fts5vocab`, token counts, the totals record and the search rows; a failed upkeep step) and `tmdb/normalize.rs` (the diacritic fold).

## Command

`epg.search {sourceId, query, from?, to?, limit?}` returns `GuideSearchHit[]`:

```
{ ref, channelName, channelNumber?, logoUrl?, categoryId?, program: EpgProgram }
```

- `query`: 2 to 100 characters after trimming. Every word of the query (a run of letters and digits, lowercased, diacritics removed, final sigma read as sigma) must start a word of the title, so `cafe soc` finds "Café Society" and "CAFE SOCIETY" but `afe` finds nothing. Diacritics are removed as Unicode NFD does (`tmdb::normalize::strip_diacritics`, a table generated from the Unicode decomposition data), so `ελληνικα` finds "Ελληνικά" and `thoi su` finds "Thời sự".
- `from` and `to`: RFC 3339. `from` defaults to now, `to` to `from` + 14 days; `to` must be after `from` and at most 16 days later. A programme matches when it overlaps the window (`stop > from` and `start < to`), so the one on air at `from` counts.
- `limit`: 1 to 200, default 50.
- `program.start` and `program.end` are guide times moved by the hit channel's guide shift (its own shift or `tvg-shift`, plus the source's; `query::item_shift`, read once per channel, epg.md), as `epg.programs` and `epg.grid` return them, so a hit shows the same time as the grid cell it opens. The UI applies `epgOffsetMinutes`.
- The window applies to those shifted times. The source's shift moves every channel of the source alike, so the window is read that much earlier on the guide's clock (`candidates`), and the order holds. A channel's own shift or `tvg-shift` differs per channel. `candidates` reads it with the channel as it takes the hits in start and channel-number order, and skips a hit it moves out of the window before the limit counts it; when that leaves fewer than `limit`, it walks on to later starts until the limit is met or the hits run out. Only the skipped channels are read beyond the ones the result needs, so a source without channel shifts costs what it did before. Known gap: the walk and the limit go by the start moved by the source's shift only, so a programme that only the channel's own part moves into the window is not found, and one it moves ahead of others may lose its place to the limit. A full fix needs every channel's shift before the walk (the `tvg-shift` lives in `items.extra_json`, outside the covering index `idx_items_guide`; reading it for 44,000 channels took about 20 ms of SQLite time on an Intel N150), the raw window widened by the source's spread of channel shifts, and the hits cut and sorted by shifted start, checked against `l3_search_epg.rs`'s budget.
- Errors: `invalid` for bad arguments (including an empty `sourceId`), `not_found` for an unknown source.

## Which channels a hit belongs to

Hits are mapped to the live and radio channels of the requested source only. A guide channel maps to an item the way the grid maps it, minus fuzzy matching:

1. A manual mapping in `epg_channel_map` wins. A mapping to NULL means "no guide" and the item gets no hits.
2. Otherwise the item's `epg_channel_id` (tvg-id), compared case-insensitively against the enabled feeds.
3. Otherwise the exact normalised channel name. Similar names ("Channel Threee") never match here, so search does not show programmes from a guessed channel.

A guide channel can map to several items (an HD and an SD copy); each gets its own hit. When two feeds carry the same channel and start, the feed added first wins.

Left out:
- channels hidden with channel edits (`channeledit::scoped` in the channel query); a renamed channel shows its custom name in `channelName`;
- parental-locked channels and channels in locked or adult categories while hide mode is on (`parental::filter::scoped` in the same query). They never become candidates, so any number of hits on locked channels cannot push a visible hit past the limit;
- while the Live TV quality filter is on (`liveMinQuality`), live channels whose name marks a lower quality, and with `liveHideUntagged` those with no quality tag (the quality clause in the same query, catalog.md). Radio channels stay;
- disabled feeds and the staging rows of a refresh in progress.

Order: programme start, then channel number (channels without one last), then channel name, then item id. Because a shift can move a hit past others, the hits are sorted again by their shifted start (a stable sort, so equal starts keep the channel order).

## The index

`epg_programs_fts` is an external-content FTS5 table over `epg_programs.title` (`tokenize='unicode61 remove_diacritics 2'`). It is not kept in step row by row: a refresh writes its programmes through staging and swaps them in with a few bulk statements, and triggers would add their cost to every one of those rows. Instead the swap keeps a matching index in step in bulk, inside its own transaction (`store::commit_staging`), with one of two strategies (`search::SwapUpkeep`):

- Feed: before the feed's old programmes are deleted, an FTS5 `'delete'` of their entries, each title folded again by the same registered `epg_search_fold` it was indexed with (`UNINDEX_FTS_SQL`), and a delete of their `epg_search_rows` by feed (`idx_epg_search_rows_feed`, migration 0028); after the copy, the new programmes are indexed and their search rows written.
- Whole: `'delete-all'` and an emptied `epg_search_rows` before the delete, then every programme indexed after the copy, as `rebuild_index` does.

`SwapUpkeep::choose` takes Feed when the other feeds hold more than old + new/2 programmes (`epg_sources.program_count` and the stage table's last rowid), else Whole. Measured on three feeds of 200k programmes (debug build, SQLite at -O1): removing a feed's entries costs about 2.6 µs per programme (the folded `'delete'` 2.1 µs, the search row 0.5 µs) and adding them about 3.25 µs, while emptying both is almost free and indexing everything costs about 2.2 µs per programme of every feed. So per-feed upkeep wins only from about three feeds of similar size (1.2 s against 1.3 s to index all three, 2.2 s for five). Either way the index ends up exactly as a rebuild would leave it. Before, every refresh rebuilt the whole index after its swap in a second write transaction, so a round of refreshes re-indexed every feed once per feed. With one or two feeds the work is what it was, in one transaction instead of two. On 3 × 200k programmes (debug build) a swap with per-feed upkeep took 2.6-2.7 s in one transaction, where the swap and the rebuild took 1.3-1.5 s and 1.5 s in two. `prune` and `epg.clearAll` still rebuild the whole index.

Each upkeep step runs under a savepoint (`store::index_step`). A step that fails (a corrupt FTS5 index answers the per-row `'delete'` with SQLITE_CORRUPT_VTAB) is rolled back and logged, the swap still commits, and the marker below is removed, so the rebuild after the swap starts over from `'delete-all'`: the index is only a cache of the programme table and never fails a refresh. When SQLite rolled back the whole transaction (a full disk, an I/O error), the error is returned and the refresh fails as before.

A full rebuild is `'delete-all'`, then one `INSERT INTO epg_programs_fts(rowid, title) SELECT rowid, epg_search_fold(title) FROM epg_programs`, which takes about 0.2 s for 200k programmes.

The index holds titles folded by the same Rust function the scan and the query use (`search::fold`, registered as the SQL function `epg_search_fold` for the rebuild and the swap, `register_fold`), not the raw titles a `'rebuild'` would read from the content table. The tokenizer's own diacritic removal covers Latin letters only and keeps the Greek tonos, so with raw titles a Greek query found nothing through the index while the scan found it. Query terms are folded before they reach the tokenizer, so both sides of a match pass through the same fold and then the same tokenizer. The per-feed `'delete'` needs `fold` to return exactly what the build that indexed a title returned, or it silently corrupts the index, so the marker below carries the Unicode version of std's tables (`str::to_lowercase` follows the toolchain's), and `search::tests::fold_output_is_pinned` pins the fold of sample strings in several scripts and a digest over every block the diacritic table covers: a change to `fold` or the `tmdb::normalize` table fails it until `INDEX_VERSION` is bumped.

`epg_search_rows` (migration 0019) holds one narrow row per programme rowid (`id`): `start`, `stop`, `feed` (the `epg_sources` rowid of the programme's feed) and `channel_id` (the guide channel). These are the columns the index path filters and orders each hit by, so a hit does not read the programme's wide row with its description. `rebuild_index` empties it and refills it from `epg_programs` joined to `epg_sources` by url, in the same transaction that rebuilds `epg_programs_fts` and sets the key below, and the swap's upkeep changes both in the swap's transaction, so the two always describe the same programmes.

The `app_state` key `epg_search_index` says whether the index and `epg_search_rows` match the table; its value is `search::index_marker()`, the index version and the Unicode version of std's tables (`folded-2/unicode-<major>.<minor>.<update>`):

- `store::commit_staging` keeps the key while the index was ready and its upkeep held; it removes it in the same transaction when the index was stale already or an upkeep step failed. `clear_all`, `prune`, and the staging cleanups when they deleted rows remove it in their transaction.
- `rebuild_index` rebuilds the index and `epg_search_rows` and sets the key in one transaction. It runs after a refresh whose swap left the index stale (while the import's larger page cache is still set), after `epg.clearAll`, after a prune, and once in the background at startup when the key is missing or holds another value and programmes exist (a database upgraded from before migration 15, an index marked `ready` (raw titles), `folded-1` (no search rows) or a bare `folded-2` (before the Unicode version) by an earlier build, a toolchain with other Unicode tables, or a crash between a swap and its rebuild). So the first start of a build with new tables rebuilds the index once.
- Migrations 0015 and 0019 leave the index and `epg_search_rows` empty so the upgrade stays fast; the startup rebuild fills both. Migration 0028 builds `idx_epg_search_rows_feed` from the rows already stored, about 0.1 s per 600k rows. Migration 0019 does rebuild five `items` indexes once (`idx_items_added_src`, `idx_items_title`, `idx_items_pos`, `idx_items_rating`, `idx_items_year`, catalog.md), about 2.4 s per 220k items, while the database opens.

Search reads the index and `epg_search_rows` only while the key holds the current version. Otherwise it scans the time window (`idx_epg_programs_stop`) and matches titles in Rust with the same word rule. Results are the same either way, only slower (about 1 s for 200k programmes in a debug build), and never stale: a rowid reused by a later insert cannot point a hit at the wrong programme, because the key is gone until the next rebuild. A search reads its hits and their programme details in one read transaction (DEFERRED, on the read-only pool through `AppState::db_read_call`, userstate.md), so a refresh that commits in between cannot hand a hit's rowid to another programme.

The index statement returns every hit in the window with its `epg_search_rows` row, unordered; hits of disabled or staging feeds and of guide channels the source does not have are dropped in Rust. Both paths then sort the hits by start and feed and stop after the start time at which `limit` channel slots are reached (every channel of a guide channel counts; a slot two feeds list counts once), so ties are ordered the same either way. Only the channels that can make the first `limit` hits are then read in full (item id, name, logo, category, guide shift), and only the final hits read their programme row (title, description, category, icon).

## Speed

`guide_search.rs` searches 1,000 guide channels with 200 programmes each (200k) from a source of 50,000 channels, 49,000 of them with guide ids and names the guide does not know. A common word (`news`, thousands of matches), a rare title and two-word queries each answer in about 35 to 60 ms; the test asserts under 150 ms in release builds.

`l3_search_epg.rs` searches two sources that share one guide of 440 channels with 240 hourly programmes each (105,600), plus a second feed repeating some slots and a disabled feed: an M3U source of 44,000 live channels on 400 guide channels and 1,000 radio channels the guide does not know, and an Xtream-like source of 20,000 live channels on 40 guide ids. `news` matches about 15,800 programmes and `the` about 26,400. The budget is a p95 under 50 ms in release; the test asserts 75 ms to leave room for a machine loaded by other builds (300 ms in debug), and a query without hits under 5 ms (40 ms in debug).

The source's channels are read on every search that has hits, so catalog changes, channel edits and locks apply at once. The channel statement is an index-only scan of `idx_items_guide` (migration 0019, `quality` appended by 0022), a partial index on `items(source_id, content_type, epg_channel_id, title, number, category_id, quality)` over live and radio rows; the statement names `content_type IN ('live', 'radio')` literally so the planner can use it, `category_id` is there for hide mode's category filter, and `quality` for the Live TV quality filter. On the index path a query without hits does not read the channels. What depends only on the guide is memoized on the EPG runtime (`SearchMemo`) until its generation moves (a refresh, a clear, a prune, a feed enabled or disabled): whether an unknown `epg_channel_id` has programmes (one `epg_programs` probe each) and which guide channel a name matches exactly. Before the memo, every search repeated both for each unmatched channel, about 140 ms at 50k channels. The memo drops its entries past 500,000. The programme probe behind it is also remembered on the generation's channel directory (`ChannelDirectory::has_programmes`, cleared past 50,000 ids), which the guide's resolution shares (epg.md).

## Query plans

`tests/guide_search.rs` checks with `EXPLAIN QUERY PLAN` that the FTS statement drives from the virtual table index and reads each hit's `epg_search_rows` row by rowid, and that the scan uses `idx_epg_programs_stop`. `tests/l3_search_epg.rs` checks that the channel statement (`CHANNELS_SQL`) uses `idx_items_guide` as a covering index and that the FTS statement reads `epg_search_rows` by its integer primary key. The FTS and scan statements are also in the `db/mod.rs` index test (after every migration); that test accepts a rowid lookup (`USING INTEGER PRIMARY KEY`) as indexed, which the FTS statement's search-row read is.
