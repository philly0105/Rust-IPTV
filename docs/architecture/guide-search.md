# Guide programme search

Code: `crates/iptv-core/src/epg/search.rs` (core), migrations `crates/iptv-core/src/db/migrations/0015_guide.sql`, `0019_guide_search_speed.sql` and `0027_guide_catalog_stamp.sql`. Tests: `crates/iptv-core/tests/guide_search.rs` (matching, window, limit, hidden and locked channels, the scan before the index exists, scan and index parity on Greek and Vietnamese titles, index upkeep, query plans, timing on 200k programmes and a 50k-channel source), `crates/iptv-core/tests/l3_search_epg.rs` (two large sources on one guide: hits against an independent model and the scan, query plans, release p95) and unit tests in `search.rs` and `tmdb/normalize.rs` (the diacritic fold).

## Command

`epg.search {sourceId, query, from?, to?, limit?}` returns `GuideSearchHit[]`:

```
{ ref, channelName, channelNumber?, logoUrl?, categoryId?, program: EpgProgram }
```

- `query`: 2 to 100 characters after trimming. Every word of the query (a run of letters and digits, lowercased, diacritics removed, final sigma read as sigma) must start a word of the title, so `cafe soc` finds "Café Society" and "CAFE SOCIETY" but `afe` finds nothing. Diacritics are removed as Unicode NFD does (`tmdb::normalize::strip_diacritics`, a table generated from the Unicode decomposition data), so `ελληνικα` finds "Ελληνικά" and `thoi su` finds "Thời sự".
- `from` and `to`: RFC 3339. `from` defaults to now, `to` to `from` + 14 days; `to` must be after `from` and at most 16 days later. A programme matches when it overlaps the window (`stop > from` and `start < to`), so the one on air at `from` counts.
- `limit`: 1 to 200, default 50.
- `program.start` and `program.end` are guide times moved by the hit channel's guide shift (its own shift or `tvg-shift`, plus the source's; `query::item_shift`, read once per channel, epg.md), as `epg.programs` and `epg.grid` return them, so a hit shows the same time as the grid cell it opens. The UI applies `epgOffsetMinutes`.
- The window applies to those shifted times. The source's shift moves every channel of the source alike, so the window is read that much earlier on the guide's clock (`candidates`), and the order holds. A channel's own shift or `tvg-shift` differs per channel. `candidates` reads it with the channel as it takes the hits in start and channel-number order, and skips a hit it moves out of the window before the limit counts it; when that leaves fewer than `limit`, it walks on to later starts until the limit is met or the hits run out. Only the skipped channels are read beyond the ones the result needs, so a source without channel shifts costs what it did before. Known gap: the walk and the limit go by the start moved by the source's shift only, so a programme that only the channel's own part moves into the window is not found, and one it moves ahead of others may lose its place to the limit. A full fix needs every channel's shift before the walk (the `tvg-shift` lives in `items.extra_json`, outside the covering index `idx_items_guide`; reading it for 44,000 channels took about 20 ms of SQLite time on an Intel N150), the raw window widened by the source's spread of channel shifts, and the hits cut and sorted by shifted start, checked against `l3_search_epg.rs`'s budget.
- Errors: `invalid` for bad arguments (including an empty `sourceId`), `not_found` for an unknown source.

## Which channels a hit belongs to

Hits are mapped to the live and radio channels of the requested source only. A guide channel maps to an item the way the grid maps it, minus fuzzy matching:

1. A manual mapping in `epg_channel_map` wins. A mapping to NULL means "no guide" and the item gets no hits.
2. Otherwise the item's `epg_channel_id` (tvg-id), compared case-insensitively against the enabled feeds.
3. Otherwise the exact normalised channel name. Similar names ("Channel Threee") never match here, so search does not show programmes from a guessed channel.

A guide channel can map to several items (an HD and an SD copy); each gets its own hit. When two feeds carry the same channel and start, the feed added first wins.

Left out:
- channels hidden with channel edits (`channeledit::scoped` in the channel query); a renamed channel shows its custom name in `channelName`;
- parental-locked channels and channels in locked or adult categories while hide mode is on (`parental::filter::scoped` in the same query). They never become candidates, so any number of hits on locked channels cannot push a visible hit past the limit;
- while the Live TV quality filter is on (`liveMinQuality`), live channels whose name marks a lower quality, and with `liveHideUntagged` those with no quality tag (the quality clause in the same query, catalog.md). Radio channels stay;
- disabled feeds and the staging rows of a refresh in progress.

Order: programme start, then channel number (channels without one last), then channel name, then item id. Because a shift can move a hit past others, the hits are sorted again by their shifted start (a stable sort, so equal starts keep the channel order).

## The index

`epg_programs_fts` is an external-content FTS5 table over `epg_programs.title` (`tokenize='unicode61 remove_diacritics 2'`). It is not kept in step row by row: a refresh writes its programmes through staging and swaps them in with a few bulk statements, and triggers would add their cost to every one of those rows. Instead the whole index is rebuilt: `'delete-all'`, then one `INSERT INTO epg_programs_fts(rowid, title) SELECT rowid, epg_search_fold(title) FROM epg_programs`, which takes about 0.2 s for 200k programmes.

The index holds titles folded by the same Rust function the scan and the query use (`search::fold`, registered as the SQL function `epg_search_fold` for the rebuild), not the raw titles a `'rebuild'` would read from the content table. The tokenizer's own diacritic removal covers Latin letters only and keeps the Greek tonos, so with raw titles a Greek query found nothing through the index while the scan found it. Query terms are folded before they reach the tokenizer, so both sides of a match pass through the same fold and then the same tokenizer.

`epg_search_rows` (migration 0019) holds one narrow row per programme rowid (`id`): `start`, `stop`, `feed` (the `epg_sources` rowid of the programme's feed) and `channel_id` (the guide channel). These are the columns the index path filters and orders each hit by, so a hit does not read the programme's wide row with its description. `rebuild_index` empties it and refills it from `epg_programs` joined to `epg_sources` by url, in the same transaction that rebuilds `epg_programs_fts` and sets the key below, so the two always describe the same programmes.

The `app_state` key `epg_search_index` says whether the index and `epg_search_rows` match the table; its value is the index version (`folded-2`):

- Every statement that deletes or swaps programmes removes the key in the same transaction: `store::commit_staging`, `clear_all`, `prune`, and the staging cleanups when they deleted rows.
- `rebuild_index` rebuilds the index and `epg_search_rows` and sets the key in one transaction. It runs after each refresh (while the import's larger page cache is still set), after `epg.clearAll`, after a prune, and once in the background at startup when the key is missing or holds another version and programmes exist (a database upgraded from before migration 15, an index marked `ready` (raw titles) or `folded-1` (no search rows) by an earlier build, or a crash between a swap and its rebuild).
- Migrations 0015 and 0019 leave the index and `epg_search_rows` empty so the upgrade stays fast; the startup rebuild fills both. Migration 0019 does rebuild five `items` indexes once (`idx_items_added_src`, `idx_items_title`, `idx_items_pos`, `idx_items_rating`, `idx_items_year`, catalog.md), about 2.4 s per 220k items, while the database opens.

Search reads the index and `epg_search_rows` only while the key holds the current version. Otherwise it scans the time window (`idx_epg_programs_stop`) and matches titles in Rust with the same word rule. Results are the same either way, only slower (about 1 s for 200k programmes in a debug build), and never stale: a rowid reused by a later insert cannot point a hit at the wrong programme, because the key is gone until the next rebuild. A search reads its hits and their programme details in one read transaction, so a refresh that commits in between cannot hand a hit's rowid to another programme.

The index statement returns every hit in the window with its `epg_search_rows` row, unordered; hits of disabled or staging feeds and of guide channels the source does not have are dropped in Rust. Both paths then sort the hits by start and feed and stop after the start time at which `limit` channel slots are reached (every channel of a guide channel counts; a slot two feeds list counts once), so ties are ordered the same either way. Only the channels that can make the first `limit` hits are then read in full (item id, name, logo, category, guide shift), and only the final hits read their programme row (title, description, category, icon).

## Speed

`guide_search.rs` searches 1,000 guide channels with 200 programmes each (200k) from a source of 50,000 channels, 49,000 of them with guide ids and names the guide does not know. A common word (`news`, thousands of matches), a rare title and two-word queries each answer in about 35 to 60 ms; the test asserts under 150 ms in release builds.

`l3_search_epg.rs` searches two sources that share one guide of 440 channels with 240 hourly programmes each (105,600), plus a second feed repeating some slots and a disabled feed: an M3U source of 44,000 live channels on 400 guide channels and 1,000 radio channels the guide does not know, and an Xtream-like source of 20,000 live channels on 40 guide ids. `news` matches about 15,800 programmes and `the` about 26,400. The budget is a p95 under 50 ms in release; the test asserts 75 ms to leave room for a machine loaded by other builds (300 ms in debug), and a query without hits under 5 ms (40 ms in debug).

### The channels of the guide channels with hits

On the index path the hits come first, and only the channels of the guide channels among them are read (`channels_on` in `search.rs`). What a channel resolves to depends on its (`epg_channel_id`, title) pair and the guide alone, so the search keeps, per source and channel type, every distinct pair of the catalog (`CatalogKeys`, on the EPG runtime): sorted the way `idx_items_guide` holds them, with the hash of each pair's trimmed, lowercased id and of its normalized title (`normalize_name`) in two sorted lists. For each guide channel with hits it looks up, the other way round from resolving a channel: the lowercased ids the channel directory turns into that channel (`ChannelDirectory::ids_of`), the channel's own id when the directory does not know it (it has programmes, since it has hits; the probe of the forward path), and the normalized names that match it exactly (`names_of`), keeping a name match only for a pair whose id resolves to nothing (that check probes `epg_programs` for an unknown id, remembered per guide generation). Each candidate is checked against its own text, so a hash collision costs a comparison and nothing else. Manual mappings (`epg_channel_map`) are read on every search and win as on the forward path; a mapping to NULL leaves the channel out.

The pairs' channels are then read in one statement (`SEEK_SQL`): the pairs go in as a JSON array (`json_each`), and each is an index-only seek on `idx_items_guide` by (`source_id`, `content_type`, `epg_channel_id IS`, `title =`), with the same visibility clauses as the channel walk (channel edits, hide mode, the quality filter), so those apply at once; channels mapped by hand are read by rowid (`MAPPED_SQL`). When those channels are more than a quarter of the source's (`SEEK_COST`), one walk of the source's channels is cheaper and is taken instead, with each row's pair looked up in the sorted list as the scan goes. Guide channels without a visible channel drop out with their hits.

The list is complete only for the catalog it was read from. Migration 0027 adds `guide_catalog_stamp(source_id, content_type, stamp)`, a random number that every write which adds, removes or re-keys a live or radio row replaces in the same transaction: `CatalogWriter::finish` for the types it rewrote (every importer; its per-row triggers are suspended), `sources::store::delete` (it removes the row), the `items_ai` and `items_ad` triggers for any other insert or delete (their FTS statement and the stamp share the suspend check, so a suspended bulk write pays nothing per row), and `items_guide_au` for an update of `source_id`, `content_type`, `epg_channel_id` or `title`. A search reads the stamp inside its read transaction and loads the list again when it differs, carrying the name hashes of the pairs it already had (normalizing every title is most of a load). The guide's side needs no invalidation of its own: the lists hold no resolutions, and the channel directory and the programme probes follow the runtime generation as before. Events and their tests (`guide_search.rs`, `follows_catalog_and_guide_changes_*`, run once reading by key and once walking the source, each result also compared with the scan that resolves every channel afresh): a catalog rewrite through the writer, rows inserted, re-keyed, renamed and deleted outside it, manual mappings set and cleared, a guide refresh that renames a channel and brings programmes for an id no `<channel>` declares, a feed disabled and enabled, and the source removed and added again; hidden and renamed channels and hide mode in `hidden_renamed_and_locked_channels` and `locked_channels_do_not_starve_visible_hits`, the quality filter in `quality_user_views.rs`. Lists past 1,000,000 pairs in all (`KEYS_CAP`, about 60 bytes each) drop the other sources' lists.

On the 200k-channel benchmark (release, `crates/iptv-core/tests/read_rpc_bench.rs`, 2026-11-10, three alternating rounds on a 4-core machine busy with other builds and browsers, so only large differences count): the first `news` search after the guide changed (`BENCH_COLD=1`) went from 445-744 ms to 145-172 ms at p50, most of what is left being the channel directory's reload, and a warm `news` (84k index hits) from 98-200 ms to 85-124 ms; the channels now take about 19 ms of it (3,000 seeks), the FTS statement and its 84k search rows about 52 ms.

The scan (no index yet) still reads every channel of the source first, as below, and so did the index path until 2026-11. The channel statement is an index-only scan of `idx_items_guide` (migration 0019, `quality` appended by 0022), a partial index on `items(source_id, content_type, epg_channel_id, title, number, category_id, quality)` over live and radio rows; the statement names `content_type IN ('live', 'radio')` literally so the planner can use it, `category_id` is there for hide mode's category filter, and `quality` for the Live TV quality filter. On the index path a query without hits does not read the channels. For the scan, what depends only on the guide is memoized on the EPG runtime (`SearchMemo`) until its generation moves (a refresh, a clear, a prune, a feed enabled or disabled): whether an unknown `epg_channel_id` has programmes (one `epg_programs` probe each) and which guide channel a name matches exactly. Before the memo, every search repeated both for each unmatched channel, about 140 ms at 50k channels. The memo keeps, per source and channel type, each distinct (`epg_channel_id`, title) pair with the guide channel it resolves to, sorted the way the channel statement returns its rows, and the scan walks that list alongside the rows: a channel costs a comparison with the next entries, and a row out of that order or new since the last search falls back to a binary search and then to resolving it afresh, which adds it to the list. Until 2026-11 it was two hash maps (by id, then by title), two lookups in tables of up to the source's size for every channel; at 200k channels on a 3,000-channel, 876k-programme guide, `news` (84k index hits) went from 167-186 ms to 121-128 ms at p50 with a warm memo (release, `crates/iptv-core/tests/read_rpc_bench.rs`, three alternating rounds on an otherwise idle machine); the first search after the guide changed, which resolves every channel afresh, stayed at about 450-530 ms either way. The memo drops its lists past 500,000 entries in all.

## Query plans

`tests/guide_search.rs` checks with `EXPLAIN QUERY PLAN` that the FTS statement drives from the virtual table index and reads each hit's `epg_search_rows` row by rowid, and that the scan uses `idx_epg_programs_stop`; that the channel seek (`SEEK_SQL`) drives from the JSON list and reads `idx_items_guide` as a covering index on all four key columns, and that `MAPPED_SQL` reads its rows by rowid. `tests/l3_search_epg.rs` checks that the channel statement (`CHANNELS_SQL`) uses `idx_items_guide` as a covering index and that the FTS statement reads `epg_search_rows` by its integer primary key. The FTS and scan statements are also in the `db/mod.rs` index test (after every migration); that test accepts a rowid lookup (`USING INTEGER PRIMARY KEY`) as indexed, which the FTS statement's search-row read is.
