This page covers how long query results stay cached, how the VOD pages start loading a detail page before it is clicked, how the main JavaScript chunk is kept under its size budget, what keeps the shell, long lists, the player, Sports, transfers, large catalog imports, filtered pages and search cheap, how the core's two database pools keep reads answering while writers wait, and, at the end, the core-side fixes of the 2026-10-31 performance pass. ## Query cache timing

Every RPC query is keyed `[command, args]`. `queryDefaultsFor(cmd)` in `src/api/query.ts` gives the cache timing for a command: `staleTime` (how long a result counts as fresh, so a remount reads the cache without asking the core again) and `gcTime` (how long a result nobody reads stays in memory). The first matching prefix wins:

| Prefix | staleTime | gcTime | Why |
| --- | --- | --- | --- |
| `settings.get`, `app.info` | never stale | 10 min | Events and `setSettingsCache` keep them current. On desktop the launch's one `app.info` request (`src/api/bootInfo.ts`) seeds the cache, so readers send no second one. |
| `sources.list`, `sources.get`, `catalog.categories` | 5 min | 10 min | Change only through source edits and refreshes, which send `sources.changed`. |
| `catalog.channels`, `catalog.movies`, `catalog.series`, `catalog.yearFacets` | 2 min | 10 min | Grid pages: going back to a grid within 2 min shows the cached page with no request. |
| `epg.grid`, `epg.programs` | 5 min | 5 min | Guide windows stay in memory as long as they count as fresh, so reopening the guide within 5 min shows the cached window. The /epg grid keeps the slices it displays 15 min (`GRID_CACHE_MS`); see Memory below. |
| `tmdb.` | never stale | 30 min | TMDB metadata does not change during a session. |
| `positions.`, `stats.` | 15 s | 10 min | Playback writes these all the time. |
| anything else | 30 s | 10 min | `DEFAULT_QUERY_TIMING`. |

The table applies to every query whose first key part is a command, not only to `useRpcQuery`: `queryClient` is an `RpcQueryClient`, which overrides `getQueryDefaults`, so raw `useQuery` and `prefetchQuery` callers get the same timing. Options are applied in this order, and the later one wins:

1. the client defaults (30 s, 10 min, no refetch on window focus, two retries for retryable errors);
2. the C4 table;
3. anything registered with `queryClient.setQueryDefaults`;
4. the options passed with the query, including `useRpcQuery`'s `staleTime` and `gcTime`.

`useRpcQuery` only sets the options the caller gave. Before Run 3 it passed `staleTime: undefined` when the caller gave none, and TanStack Query read that as 0, so those queries refetched on every mount. They now follow the table.

Event invalidation does not change. `EVENT_INVALIDATION` in `src/shell/effects.ts` and `bindEventInvalidation` mark matching prefixes stale whatever their `staleTime`, so a long stale time only removes refetches that would have returned the same data. A write that sends no event has to invalidate its own prefix. Before Run 3, queries without a stale time refetched on every mount, which covered for such writes. Now the result of a write like that shows only once the stale time has passed.

Events are folded into refetch rounds. The first event that invalidates anything opens a 50 ms burst (`EVENT_BURST_MS` in `src/api/query.ts`). The prefixes of every event in the burst, and of every `invalidate(prefix)` call made while it is open (event handlers in `effects.ts`, for example), are collected, and when the burst closes one `invalidateQueries` call marks them all stale. An `invalidate` inside a burst resolves when that round has refetched. The core sends related events back to back (`import.progress` done, then `sources.changed`); before, each one cancelled and restarted the same refetches. `events.lagged` turns the burst into a refetch of every query. An `import.progress` done with `message: 'unchanged'` (the core kept the catalog) invalidates only `sources.`. The progress feeds leave refetching to the core's change events (F5-5): the guide feed (`handleGuideEvent` in `src/features/sources/lib/epgRefresh.ts`) only updates its store on `done` and `error`, since the core's `epg.changed` follows at once (status-only after a 304, so cached guide windows stay fresh), and the import feed (`handleImportEvent` in `progress.ts`) refreshes `sources.` through `invalidateWithEvents`, which joins the burst, so a failed or cancelled run and the `sources.changed {reason: 'status'}` after it refetch once. In `src/features/sources/test/feedRefetch.test.tsx` a 304 refresh now causes no grid refetch instead of 1 and keeps an inactive cached window fresh, a full refresh or a failed one 1 instead of 2, and a failed or cancelled import 1 `sources.list` refetch instead of 2. `useRpcQuery` passes the query's abort signal to the call, so on the web a refetch that a newer invalidation or an unmount replaced stops transferring; on desktop only a call not yet sent is skipped.

`settings.changed` carries the full settings, as `settings.get` returns them. `bindEventInvalidation` writes that payload into the `settings.get` cache before anything refetches and adds no `settings.` invalidation, so the settings are not asked for again. Only a `settings.changed` without an object payload invalidates `settings.`. `EVENT_INVALIDATION` maps nothing to it: the shell's handler in `effects.ts` invalidates `sources.schedule` only when `sourceRefreshIntervalHours` changed. The `lastRoute` writes that follow navigation send no `settings.changed` at all: the core skips the broadcast when `lastRoute` is the only change, and the writing window puts the reply into its own cache, so no other client re-renders its settings readers.

On the web, events arrive over a WebSocket. How it reconnects, and the full refetch after a reconnect, are in [server.md](server.md) under `GET /api/events`.

Memory: `gcTime` counts from the moment the last component reading a result unmounts. Catalog pages, guide windows and TMDB results are the large ones. Guide windows hold every programme of their channels and hours. They used to get 2 minutes, which dropped windows that still counted as fresh, so reopening the guide refetched them; they now get 5 minutes, equal to their stale time. The /epg grid passes its own: the slices it displays (`gridA`, `gridB` and the quick request) get `GRID_CACHE_MS` (15 min), for a return scroll, and its chunk and outer-slice prefetches get the table's 5 minutes (`GRID_STALE_MS`). TanStack keeps the longest `gcTime` a query was given, so a prefetched slice that is displayed later keeps 15. Every grid query and prefetch used to pass 15 minutes, so the up to six 24 h answers a vertical rest prefetches beside the two it shows stayed three times as long: about 50-65 MB after 30 rests in 15 minutes, two thirds of it never displayed (F3-3). `query.test.ts` checks that `gcTime` is at least `staleTime` for every command it lists with a finite stale time. TMDB results get 30 minutes because they never change and are slow to fetch again.

TMDB results do change with the settings, though. A disabled query still returns what it cached, so the movie and series pages merge TMDB data (and the season's TMDB episodes) only while `settings.tmdb.enabled` is on. `bindTmdbCacheSync` in `src/shell/effects.ts` (mounted by `useShellEvents`) also watches the `settings.get` cache: turning TMDB off removes every `tmdb.` query, and a new effective TMDB language (`tmdb.language`, or the app language when that is blank, as in `iptv-core` `tmdb/config.rs`) resets them, so open pages refetch in the new language. The blank-key check `tmdb.testKey` keeps its answer on a language change.

The VOD hooks in `src/features/vod/hooks/queries.ts` no longer set their own stale times where the table covers them. The grid pages spread `queryDefaultsFor('catalog.movies')`. The detail queries are built by `movieDetailQuery(sourceKind, ref)` and `seriesDetailQuery(sourceKind, ref)` (staleTime `DETAIL_STALE_MS`, 5 min). The detail pages and the prefetch use these same builders, so a prefetched result is exactly the cache entry the page reads. Xtream and Stalker sources ask the provider's detail command (`xtream.vodDetail`, `stalker.seriesDetail` and so on). An m3u playlist has no provider detail: its movie query caches the flat `catalog.item` row under `['catalog.item', { ref }]` and wraps it as a detail with `select` (`toMovieDetail`); an m3u series asks `m3u.seriesDetail`, which answers with the seasons the importer stored (m3u.md, Series). Flat `useRpcQuery('catalog.item')` readers (the player, the live pages) use that same key, so one ref holds one shape: a row a flat reader cached opens the detail page without a second call, and a detail the page cached is a plain row to the flat readers. `afterData` in `prefetch.ts` reads both shapes when it picks the backdrop to preload.

## Hover and focus prefetch

`src/features/vod/hooks/prefetch.ts` starts loading a detail page as soon as the user shows intent:

- `usePrefetchIntent(target)` returns `onPointerEnter`, `onPointerLeave`, `onFocus` and `onBlur` handlers. A pointer that rests on a card for `PREFETCH_REST_MS` (120 ms) counts as intent, and leaving earlier cancels it. Focus needs the same 120 ms rest, so Tab or a held arrow key passing along a rail warms only the card where focus stops. Only one focus rest is pending at a time, blur cancels it, and when it ends it fires only if focus is still inside the card (callers that wire no `onBlur`, such as the dashboard cards, rely on that check). A new target on a recycled virtual card, or unmounting, cancels a pending rest.
- Content that scrolls under a still pointer is not intent. Chromium sends `pointerenter` to each card that scrolls under the pointer, so a pointer rest starts only after the pointer has really moved: a window `pointermove` at new coordinates (a move event at the same spot, as Chromium sends after a scroll, is ignored). A `wheel` or `scroll` anywhere cancels pending pointer rests, and a card entered before the pointer moves again is parked until it does; leaving the card drops it. The grid's keyboard cursor rest and focus rests are not affected by scrolling, because the grid scrolls its cursor into view itself.
- `prefetchVodDetail(queryClient, target, { speculative })` warms four things, five for an Xtream title no cached list holds:
  - the detail query. A hover or focus rest (`speculative`, the default) asks with `retry: false`: a failed prefetch costs nothing, and the page asks again with retries when it opens. A click (`speculative: false`, below) keeps the client's retry policy, since the page mounts while that fetch is out and joins it, and TanStack fixes `retry` when a fetch starts: with `retry: false` one retryable failure showed the page's error state, and now the hero shows after a retry;
  - for an Xtream title that no cached list holds, its local catalog row (`catalog.item` through the `catalog.items` batch), which the page shows as its hero while the provider answers (F4-1, [VOD landing and detail pages](#vod-landing-and-detail-pages));
  - the movie or series route chunk, through `preloadDetailChunk(kind)`, which runs the route's own `import()` (`loadMovieDetailPage` or `loadSeriesDetailPage` in `src/features/vod/routes.tsx`) at most once per kind per session. Hover, focus and cursor prefetch and the grid's idle warm-up share that one load; a failed load is forgotten, so a later call tries again;
  - the poster and backdrop, through `preloadImage` from `src/api/images.ts`. That is the same cache URL the page's `<img>` tries first, decoded at low priority. When the target has no backdrop, the one the detail hero shows first (the item's own, then the provider's first) is preloaded once the data arrives;
  - the TMDB lookup the page sends next (`prefetchTmdb` in `queries.ts`, the key and fn of `useTmdbMovie` and `useTmdbTv`), once the detail data arrives and only while `settings.tmdb.enabled` is on in the cached settings. Before, the page started it only after the provider detail arrived, so the cast and trailer came 0.3 to 1 s after the rest (VD-8). While the page's own lookup is still loading and the provider gave no trailer, the hero's action row holds the trailer button's place with a skeleton (`vod-trailer-slot`).
- Each target fires at most once per session. The key is `sourceKind|sourceId|contentType|itemId`. `preloadImage` keeps its own once-per-session memory per URL, which it shares with the dashboard's idle hero preloads. Live channels and other refs that are not movies or series are ignored.
- Prefetch is skipped when `navigator.connection.saveData` is set, when the primary pointer is coarse (`(pointer: coarse)`, where hover means nothing), and for touch `pointerenter` events on a device whose primary pointer is fine.
- Idle warm-up: touch screens get no hover prefetch, so `CategoryGridPage` calls `preloadDetailChunk(kind)` for its own kind once the grid mounts and the browser is idle (`requestIdleCallback` with a 2 s timeout, or a 500 ms timer where there is none), unless `saveData` is set. The first title opened then does not wait for its code. My List does the same for the kinds it holds.
- Click-time prefetch (F4-1): My List, Recently watched, Favorites and the Watch stats top titles have no hover prefetch, so a title opened there sent its provider detail only once the route chunk had loaded and the page had rendered once. They call `prefetchVodDetail` with the click (`prefetchOnOpen` and `useOpenPrefetch`, which take the source kind from the cached `sources.list`, and `openEntry` in `src/features/library/lib/open.ts`), so the detail, the title's row, the route chunk and the poster start beside the route chunk. It is not speculative, so neither `saveData` nor a coarse pointer skips it.

Where it is used:

| Surface | How |
| --- | --- |
| `PosterCard` (VOD landing rails, grids, search results) | Takes a `prefetch` target, or a ready-made `intent`, and puts the handlers on the card and its link. Its `sourceId` also scopes the poster's cache URL. |
| VOD search results (`SearchPage`) | Each movie or series hit passes its target, using the hit's source kind. |
| VOD grid keyboard cursor (`CategoryGridPage`) | The grid moves `aria-activedescendant`, not focus, so the active cell uses `usePrefetchOnRest(target)`. It fires once the cursor has stayed on a cell for 120 ms, and only while the grid listbox has focus. |
| TMDB rails (`TmdbRail`) | A TMDB card links to a title search, not to a catalog item. `useSearchPrefetchIntent({ title, sourceId })` warms the search route chunk and the first `catalog.search` page with the exact args `SearchPage` sends (`{ query, sourceId?, limit: searchRequestLimit(SEARCH_LIMIT) }`, stale for 30 s like the page's own query). Titles shorter than `MIN_QUERY_LENGTH` after `normalizeQuery` are skipped. |
| Dashboard poster cards | The same hook, in `src/shell/dashboard/` (B2). |

Links to pages (NAV-1) follow the same rest and scroll rules through `useRouteIntent(to)` in `src/shell/routeIntent.ts`: the rail's links (`RailNavLink`), an open source's links, the phone tab bar, and Live's group, pinned view and All channels links (`CategorySidebar`). A rest of `ROUTE_REST_MS` (120 ms) calls `preloadRoute(to)` for the page's chunks (registered by `src/routes.tsx` with `setRouteWarmer`, since the shell cannot import the route table) and `prefetchScreenData(to)` for its first data under the page's keys. On Live a group's rest asks for its first page, its now/next and its favourite flags, so the click shows complete rows: in the group switch test, 0 requests after the click and 2 LivePage commits to titled rows, against 3 requests and 5 commits without a rest. Unlike a poster, a link is not remembered, since a page's data goes stale; a second rest asks again and the query cache answers it while fresh. The links of a group list that scrolls under a still pointer wait for the pointer to move, as posters do.

## Grid cursor shortcuts need grid focus

The VOD grid binds `s` (My List), `w` (watched), `Shift+F10` and the context-menu key to the keyboard cursor. They are registered only while the grid listbox itself has focus: `CategoryGridPage` tracks `gridFocused` from focus and blur events on the listbox. With the grid unfocused, or focus in the page's search field, the keys reach whoever else registered them (the player's `s` screenshot shortcut, for example), and `shortcutRegistry.list()` includes the grid's entries only while they are live. When the grid takes focus, the shortcut registry puts its entries on top again. `pages.test.tsx` checks both sides.

## Entry chunk budget

`dist/assets/index-*.js`, the module script `index.html` loads, may be at most 268,000 bytes. That is about 10 % over the 243,927-byte entry before Run 1 (SC10).

```
pnpm build && pnpm size:check
```

`tools/check-bundle.mjs [distDir]` is plain Node with no dependencies. It lists every JavaScript chunk, largest first, with its size and gzip size, and marks the entry. It exits 1 when there is no build, when there is no `index-*.js`, when `index.html` loads something else, or when an `index-*.js` is over budget.

It also follows the static imports of Home's route chunk (`DashboardPage-*.js`) and prints how many chunks and bytes beyond the boot chunks (the entry, `vendor-*`, `locale-*`) Home loads before its first render. It exits 1 when that set holds a player chunk (`store`, `playback`, `mpvExtras`, `player-index`, the stage, the controls or an engine; performance audit SH-2). A lazy route renders only after its static imports have run, and `DashboardPage.tsx` imported `playItem` from the player barrel and `preloadEngines`, whose module Rollup puts in the player store's chunk, so a cold Home waited for 96.8 kB of player code it needs only after a click (227 kB beyond the boot chunks in all). Home now loads both behind `import()`, as the command palette does, and its closure is 131 kB on the audit build. The check exits 1 too when there is no `DashboardPage-*.js`, so a renamed page cannot switch it off.

The same walk runs for the other route chunks in its `ROUTES` table. Settings may not reach player code either. Search, the category grid and Sports may not reach the player's UI (the barrel, the dock, the stage, the controls, an engine): they play through `import()`. Live and the guide draw `PlayerStage` but may not reach the controls chunk (`Controls-*.js`), which comes with the dock that the shell loads from `@/features/player/dock` (F1-1): while the `@/features/player` barrel exported `PlayerDock`, their static imports reached the dock's whole graph and the controls, about 37 kB gzipped each before their first render. `dock-*.js` counts as player code. Live, the guide, Search and Scheduled may not load Home's cards module (`cards-*.js`, `src/shell/dashboard/cards.tsx`, about 39 kB with My List, the VOD prefetch and the rails it brings): ten feature modules imported `joinList` or `itemPath` from it, so import `joinList` from `@/lib/intl` and `itemPath` from `@/shell/railLinks`. The check exits 1 when there is no controls chunk or no cards chunk, so a moved module cannot switch those guards off either. Measured on the tree after F1-1 and F1-7 (`pnpm build`, check-bundle), Live's static closure beyond the boot chunks went from 62 chunks and 497,498 bytes (192.0 kB gzip) to 53 and 386,651 bytes (151.4 kB gzip), the guide's from 519,660 to 411,656 bytes, and Scheduled's from 304 to 211 kB, the movie detail page's from 414 to 298 kB and the series page's from 426 to 312 kB; neither detail page loads the controls or the cards any more. Home (167,729 bytes), Settings (229,733) and Sports (168,386) changed by a few kB either way, from shared icons and small modules the min-size merge placed differently, while the entry plus closure fell on every route (Live 721 to 592 kB, the guide 744 to 617 kB, Home 392 to 373 kB).

`vite.config.ts` names lazy chunks whose first module is an `index.ts` barrel after their folder (`player-index-*.js`). Without that, `import('@/features/player')` would produce a second `index-*.js` beside the entry.

Three more settings in `vite.config.ts` shape the chunks:

- `experimentalMinChunkSize: 4_000` merges app chunks under 4 kB into a neighbour. With no merging a cold dashboard in server mode made 68 JS requests, 39 of them under 4 kB. Rollup merges a small chunk that several lazy pages share into the entry, because the entry always loads, so a larger setting moves lazy-only code there: at 10 kB the entry was 162.0 kB, at 4 kB 143.0 kB, with no merging 141.0 kB (84, 117 and 160 JS chunks; every route in one session 59 requests at 10 kB, 88 at 4 kB). Cold first paint on loopback was the same within noise at 10 kB and 4 kB.
- Each language is one manual chunk, `locale-<lang>` (`vendorChunk` matches `src/i18n/<lang>/*.json` and the folder's `index.ts`), since `loadLanguage` fetches all of a folder's namespaces at once. A manual chunk stays out of the min-size merge, so no foreign strings end up in app chunks; without these chunks the 10 kB merge cost 11 % more bytes. Each JSON file in them is one `JSON.parse("…")` (`json: { namedExports: false, stringify: true }`, P2-BOOT-2). Vite's default made every key an `export const` and every file an object literal over them, so `locale-en`, which every boot loads before the first render, was 3,140 statements to compile: 217,950 bytes (64.6 kB gzip) and 18.8 ms to load in a fresh Node 24 process, against 150,775 bytes (43.2 kB gzip) and 6.6 ms as strings (German: 13.3 to 5.9 ms).
- `treeshake.manualPureFunctions: ['memo', 'lazy']` marks React's wrappers pure. Rollup cannot prove they have no side effects, so a module with a top-level `memo(...)` reached through the `@/ui` barrel was kept whole in the importer's chunk; that put `VirtualGrid` in the entry.

Fixes from the 2026-10-19 performance audit:

- react-router (BUNDLE-ROUTER): 7.18's exports map has no `production` condition, so every build resolved `dist/development`, which runs with `ENABLE_DEV_WARNINGS = true`. A production build (`vite build`) aliases the bare `react-router` specifier to `node_modules/react-router/dist/production/index.mjs`; `vite` dev keeps the warnings, and vitest (`vitest.config.ts`) and the typecheck resolve the package as before. `vendor-react` lost the dev-only warnings (1.7 kB).
- `vendor-ui` (SH-10) holds only `tailwind-merge`, `clsx` and `zustand`. cmdk, its Radix dialog stack (`@radix-ui/*`, `aria-hidden`, `react-remove-scroll` and the rest) and `lucide-react` left the manual chunk list, so Rollup places them with their users: cmdk with the lazy command palette, each icon with the code that draws it. `index.html` preloads `vendor-ui` on every boot, and it went from 126,172 to 30,335 bytes; the icons the shell draws moved into the entry (about 9 kB). An icon used by several lazy pages and nothing else gets its own small chunk, since lucide's icon modules have top-level calls the min-size merge treats as side effects.

`src/ui/test/bundlePurity.test.ts` checks that `memo` and `lazy` are on the pure list, that every component wrapper called at module top level is on it, that `experimentalMinChunkSize` is between 3,000 and 5,000, that each language has one chunk with no app modules in it, that JSON compiles to one `JSON.parse` per file, that a build aliases react-router to its production files and dev does not, that cmdk, Radix and the icons stay out of `vendor-ui`, and that the build writes its asset list into the service worker.

### What moved out of the entry in Run 3

After Run 2 the entry was 267,003 bytes, under 1 kB from the cap. Most of it was the player: the shell imported `PlayerDock`, `ExternalPlaybackFooter` and `restorePlayback` from the `@/features/player` barrel. The watch-stats reporter and the window-state effect pulled the player store, the engines, subtitles and track handling in too. Run 3 cuts each of those static paths:

- `ShellLayout` imports the player dynamically, and not before the first route is in. Since F1-1 it imports `@/features/player/dock` (`PlayerDock`, `ExternalPlaybackFooter`, `restorePlayback` and the store), not the barrel, which no longer exports the dock: pages import the barrel for the stage, the store and `playItem`, and with the dock in it Live's and the guide's static imports reached the controls chunk. The router renders the shell only after the first route's lazy chunks have loaded (initial hydration), and `usePlayerModule()` then waits `PLAYER_PREFETCH_DELAY_MS` (2.5 s) followed by the first idle moment (`requestIdleCallback`, at most `PLAYER_IDLE_TIMEOUT_MS`, 2 s; a macrotask where the browser has no `requestIdleCallback`), or for the first `pointerdown` or `keydown` from the start, whichever comes first (`schedulePlayerLoad`). Without the delay the player's chunks (about 200 KB) arrived at about 0.4 s on a cold load, among the first route's own chunks and long tasks. It loads at once when `sessionStorage` holds a resume record (`player.resume`), and `restorePlayback` runs only then. Run 3 first started the import when the module ran; under 50 ms of latency the player chunk and its dependencies then competed with the route chunks for the browser's connections and delayed the first paint by about 100 ms. A press starts the load at once, and a play that starts without one (the phone remote, autoplay, a queued next episode) does too: the barrel raises `PLAYER_DOCK_EVENT` (`src/features/player/dockRequest.ts`) when the store first gets a source, and `schedulePlayerLoad` treats it like a press. A failed chunk load leaves the shell usable without the dock.
- The watch-stats reporter (Run 2 C7) starts from an effect that imports `@/features/stats/reporter`, once the player module is in. It reads the player store's state when it starts, so nothing that played before is lost. `RecordingWatcher` imports the player too, so it also mounts with the player module; it picks up reminders that fired before it listened.
- `useWindowStatePersistence` (desktop only) imports `@/features/player/pip` inside its async start-up, next to the Tauri window API it already loaded lazily.
- From the 2026-10-31 pass (F1-7): a kit file the shell imports statically brings every export any lazy page uses into the entry, since Rollup puts a module in one chunk. The phone tab bar loads with `lazy()` only below 640 px, behind the same text-free skeleton bar the shell skeleton draws (`TabBarSkeleton`), and the shell reads its heights from `src/shell/tabBarMetrics.ts`; it imported `TabBar.tsx` for two constants. The header's `SearchInput` brought all of `Field.tsx` (Switch, Select, RadioGroup, Slider, Textarea, Checkbox); it and the field classes now live in `src/ui/SearchInput.tsx`, which `Field.tsx` re-exports. The desktop picture-in-picture geometry (monitors, `placeOnScreen`) moved from `src/api/window.ts` to `src/api/pipWindow.ts`, which `bindWindowFullscreen` loads with `import()` on desktop for the recovery after a reload in PiP; it sat in the web build's entry too. The entry went from 225,380 to 205,525 bytes (Field 7.4 kB, the tab bar 7.5 kB and the PiP code 6.4 kB left it). Pages that draw form fields load them in a chunk of their own, about 8 kB, but the entry plus closure fell by 9 to 23 kB on every route. `Dialog.tsx` stays in the entry for `ContextPanel`'s drawer.

### First render

`src/main.tsx` renders once `Promise.all([initI18n(), imageBaseReady()])` settles. A remembered non-English language loads in one request: `src/i18n/lazyLocales.ts` maps each language to its folder's `index.ts`, which gathers every namespace and sits in the `locale-<lang>` chunk, and the entry carries that 18-entry map. Before, the entry first fetched a 23.5 kB map of every language and namespace pair and only then the language's chunk, an extra round trip before the first paint on remote web (performance audit SH-8). The two run in parallel. On the web `imageBaseReady()` is settled at once, so the web path waits only for the locale, as before. On desktop it waits for the image cache base (`app.info.proxyBase`, from the launch's one `app.info` request, which `src/api/bootInfo.ts` sends as soon as the first module loads and `images.ts`, `transport.ts` and the query cache share), so the first artwork on screen already loads through the cache. The worst case is a desktop core that does not answer `app.info`: the first render then waits 1.5 s (the `imageBaseReady` cap) instead of only for the locale, and pictures load directly until the base arrives.

### Keeping it there

- New pages go in route chunks: use `lazy` in a feature's `routes.tsx`.
- Dialogs and hosts that show on demand load behind `import()`. `ParentalGateHost` and `RecordingWatcher` are examples. `CommandPalette` and `ShortcutOverlay` go further: the shell mounts each the first time it opens (`PaletteHost`, `ShortcutOverlayHost`), and `src/shell/overlayChunks.ts` fetches their chunks at the first idle moment after the player's idle load and on hover or focus of the buttons that open them. The closed palette used to load about 85 kB (cmdk with the Radix dialog stack it carries, programme search, the onboarding strings) right after the shell's first render on every launch (F1-3).
- Do not import the `@/features/player` barrel, or anything that reaches `@/features/player/store`, from a module the shell loads statically. If a shell file needs the player, load it with `import()` the way `ShellLayout` and `effects.ts` do. Keep the dock out of the barrel (`@/features/player/dock`).
- A small helper that several lazy pages share goes in a module that is already in the entry, as `itemBatch.ts`, `progress.ts`, `joinList` and `itemPath` do. A new file under 4 kB is merged by `experimentalMinChunkSize`, and the merge can move it, and other small modules and shared lucide icons with it, into an unrelated chunk: `joinList` and `itemPath` as files of their own grew Settings' closure by 17 kB, and a lazy `EpgMappingDialog` left Live and the guide 0.9 kB and Home 4.6 kB larger, because the merge folded `useAddToList` and the channel-edit menu into the dialog's chunk. The guide mounts that dialog only on its first open, as Live does.
- To find out why a module is in the entry, build with a small Rollup plugin that records `getModuleInfo(id).importers` for the entry's modules, then follow the importers back to `src/main.tsx`.

## Large catalog imports

A large catalog rewrite (at least 20,000 rows touched; the full rule is in catalog.md) drops the secondary indexes of `items` and builds them once before the commit, instead of updating each of them on every row. It changes the schema once per import, so every pooled connection re-prepares its statements once, and the rebuild raises peak memory by about the largest index. Details in [catalog.md](catalog.md#index-rebuild-for-large-rewrites).

From the 2026-10-31 pass (R1-4, R5-4): the drop and rebuild live in `catalog::drop_item_indexes` and `create_item_indexes` (`idx_items_cat` still last), and two more paths use them. `CatalogWriter::begin` skips the per-row FTS `delete` when a bulk rewrite replaces more rows than it keeps and runs the FTS `rebuild` right after its deletes, when `items` holds only the kept rows: `begin` of a 250k-row refresh next to 40k kept rows went from 1.1 s to 0.45 s. Removing a large source does the same around its cascade ([sources.md](sources.md#update-reorder-remove)): 250k rows next to 40k took 3.0-3.7 s before the commit and take 1.1-1.4 s (dev build). All of it runs in the import's `Immediate` transaction under `long_write`, with user writes waiting.

Memory and time inside the write transaction (R3-1, R3-3, R3-5, R3-7): an Xtream row carries its extra as JSON text an importer serialized on the blocking pool (`ItemRow::extra_json`, the same bytes as the old map), not as a `serde_json::Map` the writer serializes and frees inside the transaction: a mapped row holds 534-791 bytes instead of 1,162-1,566, about 160 MB less at 50k channels, 180k movies and 20k series. M3U series rows are built one show at a time with their episodes written straight to text (about 200 bytes an episode instead of 0.9 KB as a tree, which kept about 105 MB alive through `finish` at 120k episodes), the grouper looks a show up by group and raw title before it computes `title_base` and `show_key`, which took 0.8 µs for every episode (about 0.2 s of write lock per 120k episodes on an N100) though a show has 15-20, and the parser and row builder copy only what they keep (406 ns and 12 allocations against 244 ns and 5 per `m3u_plus` line; about 0.3 s and 12 MB per 200k entries on an N100).

## Filtered pages and search

- A movie or series page with a minimum rating or a year range reads its sort's index in order: the page statement writes those filters as `+i.rating` / `+i.year` when the grid is sorted by another key, and migration 0019 puts the rating and the year in every sort index, so the page reads index entries instead of a table row per title it passes. A page at or past the filtered total skips the page statement. Details in [catalog.md](catalog.md#reading).
- `catalog.search` runs its substring pass only when no list has a word-prefix hit, and its ranking pass reads no category row per match. The word-prefix pass ranks on `items_rank` (migration 0020), about 60 bytes per match instead of the item's wide row, and keeps each list's best rows with a bounded top-N per list over one materialized match set instead of a `ROW_NUMBER()` window that sorts every match. On 215k items in a release build that takes "th" (56k matches) from 155 ms to 61-64 ms at p95, "the" from 105 ms to 43-44 ms, "a" from 110 ms to 37-44 ms and hide-mode "th" from 99 ms to 52-61 ms; narrow queries gain too ("news" 20 to 12 ms, "blue" 16 to 10 ms). Details in [catalog.md](catalog.md#reading). `crates/iptv-core/tests/l3_search_perf.rs` holds these on 215k items in release builds: every search under 100 ms at p95, the broad prefixes and hide mode included (only the substring scan, which reads every title, under 250 ms), filtered pages and parental hide mode under 50 ms. `crates/iptv-core/tests/l4_search_rank.rs` checks that the ranking returns the same rows in the same order as the window statement.
- Every pooled connection runs with a 32 MiB page cache (`cache_size` in `db::configure`, and in `db::configure_read` for the read-only pool below; SQLite's default is 2 MiB). Reads of `items` rows by rowid missed the default cache on most reads on a 215k-item library. The larger cache halved "blue", "news" and "zzzz" (p50 25-30 ms to 12-17 ms) for about 40 MB more peak memory in `l3_search_perf.rs`; 16 MiB gained almost nothing and 64 MiB little more. The cache belongs to its connection and fills only as pages are read, so the write pool's 8 connections (`POOL_MAX`) hold at most 256 MiB and the read pool's 6 (`READ_POOL_MAX`) at most 192 MiB more, about 448 MiB in all; r2d2 hands out the most recently returned connection first, so the connections a pool opens only for bursts stay mostly cold. Both pools keep their connections for the life of the app (`idle_timeout` and `max_lifetime` are off): r2d2's defaults closed an idle connection after 10 minutes and replaced every one after 30, each time with a cold cache and no prepared statements. Each connection caches 64 prepared statements (`db::STATEMENT_CACHE`; rusqlite's default is 16, while one Live scroll step uses 10-14 and moving between Live, VOD and Home 40-60), and the catalog page statement binds its OFFSET, so every page of a list reuses one cached statement. LIMIT stays literal, since SQLite uses it in the row estimate. Migrations run on the 2 MiB default (`db::migrate`; a 600k-row guide upgrade would otherwise fill the whole 32 MiB). A memory map (`mmap_size`) measured no gain and is not set. `items_rank` adds about 15 MB per 220k items to the database and, while a broad search reads it, up to that much to a connection's page cache; the materialized match set of a broad search takes about 2 MB of temp memory.

## Database pools

The core holds two r2d2 pools of SQLite connections (`db/mod.rs`, `state.rs`); [userstate.md](userstate.md#pools-and-write-gates) lists which call goes where.

- The write pool, 8 connections (`db::POOL_MAX`), takes every write and the reads that were not moved. Writes pass a gate before they take a connection: user writes go through `AppState::db_write` one at a time, periodic and bookkeeping writes through `AppState::db_background`, and best-effort writes nobody waits for through `AppState::writer`, in the background. While an import's save holds SQLite's write lock (under `long_write` a waiting writer may wait up to 600 s), the writers behind each gate park one connection between them instead of one each. The 2026-10-31 pass gated the writes that still took a connection of their own (R1-1 phase 1, R4-1, R4-2): the Stalker session row and the Xtream server metadata go to the writer and are no longer awaited (a Stalker login while the write lock is held took 13 ms, where the session write could hold the source's session mutex for the rest of the save); account status saves, import outcome rows and `window.setState` pass the background gate, and a forced account check answers before its row is stored (1.4-2.4 ms with the lock held); download cancel, remove and `downloads.setPosition` and `sources.add`, `update` and `reorder` pass the user gate, and a pasted playlist is hashed and written to disk before it ([sources.md](sources.md#add)); the TMDB boot purge goes to the writer. With the lock held, 3 connections busy and 11 newly gated writers waiting, 14 concurrent catalog pages finished in 6.5 ms (`l2_import_pool.rs`, debug build); ungated, those 11 alone outnumbered the 8 connections. The EPG status writes stay ungated, since the EPG semaphore bounds them to 2.
- The read-only pool, at most 6 connections (`db::READ_POOL_MAX`; `db::open_read` with `READ_ONLY | NO_MUTEX | URI`, one kept idle, no idle timeout or lifetime, 15 s checkout), serves the hot pure reads through `AppState::db_read_call` and `db_read`: every `catalog.*` reader (`matchTitles` and `yearFacets` included); `epg.sources`, `nowNext`, `programs`, `grid`, `channelsSearch`, `resolve`, a channel's shift and `epg.search`; the favorites, recent and positions lists and checks; `lists.list`, `items`, `containing` and `neighbors`; `watchlist.list` and `contains`; the parental config, locks, check, adult-category, has-locks and hidden reads; the phone remote's channel fill; and the image cache's index lookup and its server-mode source row read. `db::configure_read` keeps the statement cache, the SQL functions, the temp store and the 32 MiB page cache, sets no write pragmas, and uses SQLite's plain 5 s busy timeout: a WAL reader never waits for the write lock, so `long_write`'s 600 s does not apply. A write sent there fails at once with `SQLITE_READONLY`; temp tables (`hidden_rowids`) and read transactions work. The pool opens after the migrations and the corrupt-file quarantine; when it cannot open, reads fall back to the write pool. Before (R1-1 phase 2) these reads shared the 8 connections with parked writers, and with 8 ungated writers waiting out a save they failed at the 15 s checkout timeout. In `l2_import_pool.rs` (debug build), with a save holding the lock and 8 writers on all 8 write connections, 13 reader RPCs and an image hit answer in 0.1-3.2 ms, and every other moved RPC in 35 µs to 2.6 ms. A few reads still use the write pool, among them `positions.watchedContains`, `sourcePins.get` and `channels.edits`.

The write pool kept its 8 connections and 32 MiB caches when the read pool came: whether either can shrink now has not been measured in release builds (`m3u_perf`, `catalog_perf`, `l3_search_perf`).

## Core changes of the 2026-10-31 pass

The pass's core-side fixes, each with the number that motivated it; the mechanisms and their tests are in the subsystem docs.

- Catalog ([catalog.md](catalog.md#reading)):
  - Unfiltered All channels, the guide's All list and radio lists take their total from the stored category counts, as All movies and All series did (R1-2): `item_count` already leaves out channels a channel edit hides. On 200k live channels the `count(*)` was 4.4 ms of a 4.7 ms first page, and a guide search hit reads up to 12 pages.
  - The list readers skip an M3U series row's episode list (`parse_extra` scans the `episodes` key with `IgnoredAny`), and whatever needs the episodes reads them straight from the row's text (`m3u::series::stored_episodes_of`): a 60-row page of 20-episode shows took 0.85 ms and 14,760 allocations, now 0.1 ms and 120, and 8.6 ms against 1.35 ms at 200 episodes (R1-3, R3-6).
  - `catalog.items` reads per-source data once per batch (R1-6) and `catalog.matchTitles` answers a whole TMDB rail in one call (F4-3), both above.
- Stalker ([stalker.md](stalker.md)):
  - Archive day tables are cached per source, channel and date and shared with catch-up, their pages go out three at a time with at most six day-table requests per source, the table type that answered is asked first next time, and `stalker.epg` takes `to` (R5-1, under Stalker previews above). A table that a failed page cut short is not reused.
  - The bulk `get_epg_info` guide is indexed per channel on the blocking pool instead of being kept as a JSON tree for the session (on the order of 100 MB for a 10k-channel guide), stays fresh 30 minutes instead of 5, is refreshed in the background while rows keep reading the last good one, lets the old one go once a refresh succeeds, and is dropped when no row asked for it in 35 minutes (R5-2).
  - A sync asks its sections together after the session and takes the save slot only after the totals: against a test portal answering in 300 ms a 30-channel sync takes 2.4 s with 7 requests in flight at the start, where the old order was 14 waves, about 4.2 s of waiting alone (estimated; R5-3). Answers over 1 MB and long-timeout calls are parsed on the blocking pool (R5-5), and learned page sizes survive a sync and are seeded by its totals request, so the first 42-row grid page after a sync is one wave of 3 requests (R5-6).
- The guide ([epg.md](epg.md), [guide-search.md](guide-search.md)):
  - now/next stops at the first feed that fixes the programme on air and the next: 120 refs on 3 overlapping feeds read 360 feeds in 13.3 ms, and 120 feeds in 5.8 ms with the early stop (R2-2).
  - `catchup.programs` picks the overlapping programmes before it copies and shifts them, and the archive and short-EPG caches drop expired answers when they store one (R2-3).
  - The channel directory is built before `epg.changed` goes out, with half the regex work (R2-4): the refetch burst after a refresh found none and waited on its lock with a connection each, an estimated 0.1-0.25 s at 30-60k guide channels, a few times a day.
  - Each ref is resolved with one statement (`ITEM_SQL`, `tvgShift` read in SQL), and title results and programme checks are remembered per directory (R2-5): about 540 statements for a 120-ref page, and 2,250 for a 500-ref Sports chunk, before any programme was read.
  - The search index is kept in step inside the swap's transaction, for the refreshed feed alone or for every feed, whichever costs less, instead of a full rebuild in a second transaction after every refresh (R2-1, stage 1): that rebuild took 0.25 s per 200k programmes of all feeds on a desktop and 2-3 times that on an N100, so a cycle of refreshes grew with the square of the feed count. A failed upkeep step rolls back under a savepoint and the swap still commits, and the index marker names the Unicode tables the fold uses.
  - `flate2` inflates and deflates through zlib-rs: 1.3-2 times faster than miniz_oxide, about 0.4-0.8 s of an N100 core saved per 30-40 MB `.xml.gz` (R2-6).
- User state ([userstate.md](userstate.md), [lists.md](lists.md), [watchlist.md](watchlist.md), [channel-edits.md](channel-edits.md), [tmdb.md](tmdb.md)):
  - Continue watching walks unwatched rows newest first through `idx_positions_resume` (migration 0027) and stops at the limit, instead of ranking the whole viewing history: 4.7 ms at 4,283 rows (about 14 ms on an N100) against 0.13 ms (R4-3).
  - `lists.reorderItems`, `watchlist.reorder` and `favorites.reorder` write only the rows whose position changes: 4.8 ms and 3.4 MB of WAL per 30 moves at 2,000 rows, against 1.2 ms and 0.25 MB (R4-5).
  - `channels.setHidden` moves the stored counts by the channels it changed instead of recounting the source: 15 ms per click at 270k items against under 0.1 ms (R4-4).
  - The TMDB boot purge reads expired rows through `idx_tmdb_cache_expires` (0027) in the background: it read the whole cache, 9.3 ms warm for 37 MB and about 1 s cold on eMMC, against 0.15 ms, and server mode's listener waited for it (R4-2).
- Pools, gates and large writes: [Database pools](#database-pools) and [Large catalog imports](#large-catalog-imports) above.
