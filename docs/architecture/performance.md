## Query cache timing

Every RPC query is keyed `[command, args]`. `queryDefaultsFor(cmd)` in `src/api/query.ts` gives the cache timing for a command: `staleTime` (how long a result counts as fresh, so a remount reads the cache without asking the core again) and `gcTime` (how long a result nobody reads stays in memory). The first matching prefix wins:

| Prefix | staleTime | gcTime | Why |
| --- | --- | --- | --- |
| `settings.get`, `app.info` | never stale | 10 min | Events and `setSettingsCache` keep them current. On desktop the launch's one `app.info` request (`src/api/bootInfo.ts`) seeds the cache, so readers send no second one. |
| `sources.list`, `sources.get`, `catalog.categories` | 5 min | 10 min | Change only through source edits and refreshes, which send `sources.changed`. |
| `catalog.channels`, `catalog.movies`, `catalog.series`, `catalog.yearFacets` | 2 min | 10 min | Grid pages: going back to a grid within 2 min shows the cached page with no request. |
| `epg.grid`, `epg.programs` | 5 min | 5 min | Guide windows stay in memory as long as they count as fresh, so reopening the guide within 5 min shows the cached window. The guide page's own grid queries keep 15 min (`GRID_CACHE_MS`), so a return scroll shows the tiles at once; the slices it only asks ahead keep these 5 min (epg.md, Queries). |
| `tmdb.` | never stale | 30 min | TMDB metadata does not change during a session. |
| `positions.`, `stats.` | 15 s | 10 min | Playback writes these all the time. |
| anything else | 30 s | 10 min | `DEFAULT_QUERY_TIMING`. |

The table applies to every query whose first key part is a command, not only to `useRpcQuery`: `queryClient` is an `RpcQueryClient`, which overrides `getQueryDefaults`, so raw `useQuery` and `prefetchQuery` callers get the same timing. Options are applied in this order, and the later one wins:

1. the client defaults (30 s, 10 min, no refetch on window focus, at most two retries for retryable errors; on desktop `networkMode: 'always'`, below);
2. the C4 table;
3. anything registered with `queryClient.setQueryDefaults`;
4. the options passed with the query, including `useRpcQuery`'s `staleTime` and `gcTime`.

Provider commands (`stalker.`, `xtream.`, `tmdb.`) take their retry rule from `getQueryDefaults` too (`retryProviderError`). The core already retries those calls itself (Xtream and Stalker three attempts, TMDB four), so two more rounds in the UI made up to 9-12 requests to a slow or failing panel and tripled the wait before its error showed. A provider failure the core already retried (`network`, `timeout` or `server` without `details.transport`) therefore shows at once, and stays `retryable`, so the page's Retry still works. Everything else retryable is retried twice as for any command: a local failure the core does not retry (a busy database), and a call that never reached the core, which the web transport tags `details.transport` (`unreachable` when the server did not answer, `http` for a proxy's 502 or 503 or another HTTP error without the core's payload; server.md).

On desktop the client runs queries and mutations in `networkMode: 'always'` and keeps `refetchOnReconnect` on (it is read from `window.__TAURI_INTERNALS__` in `query.ts`, as `bootInfo.ts` does, because many tests mock `./transport` partially). IPC needs no network, and with TanStack's default `online` mode every query and mutation paused while the webview thought it was offline, so My videos showed an empty library. The web keeps `online` and its reconnect refetch.

`useRpcQuery` only sets the options the caller gave. Before Run 3 it passed `staleTime: undefined` when the caller gave none, and TanStack Query read that as 0, so those queries refetched on every mount. They now follow the table.

Event invalidation does not change. `EVENT_INVALIDATION` in `src/shell/effects.ts` and `bindEventInvalidation` mark matching prefixes stale whatever their `staleTime`, so a long stale time only removes refetches that would have returned the same data. A write that sends no event has to invalidate its own prefix. Before Run 3, queries without a stale time refetched on every mount, which covered for such writes. Now the result of a write like that shows only once the stale time has passed.

Events are folded into refetch rounds. The first event that invalidates anything opens a 50 ms burst (`EVENT_BURST_MS` in `src/api/query.ts`). The prefixes of every event in the burst, and of every `invalidate(prefix)` call made while it is open (event handlers in `effects.ts`, for example), are collected, and when the burst closes one `invalidateQueries` call marks them all stale. An `invalidate` inside a burst resolves when that round has refetched. The core sends related events back to back (`import.progress` done, then `sources.changed`); before, each one cancelled and restarted the same refetches. `events.lagged` turns the burst into a refetch of every query. An `import.progress` done with `message: 'unchanged'` (the core kept the catalog) invalidates only `sources.`. `useRpcQuery` passes the query's abort signal to the call, so on the web a refetch that a newer invalidation or an unmount replaced stops transferring; on desktop only a call not yet sent is skipped.

`settings.changed` carries the full settings, as `settings.get` returns them. `bindEventInvalidation` writes that payload into the `settings.get` cache before anything refetches and adds no `settings.` invalidation, so the settings are not asked for again. Only a `settings.changed` without an object payload invalidates `settings.`. `EVENT_INVALIDATION` maps nothing to it: the shell's handler in `effects.ts` invalidates `sources.schedule` only when `sourceRefreshIntervalHours` changed. The `lastRoute` writes that follow navigation send no `settings.changed` at all: the core skips the broadcast when `lastRoute` is the only change, so no other client re-renders its settings readers. The writing window keeps the reply out of its own `settings.get` cache too: a new settings object re-rendered every reader of the whole settings (Home's cards, Live, the guide ribbon and grid, the VOD rails, `useRailCardWidth`) 1.2 s after each screen change, for a field only startup reads. `currentLastRoute(settings)` in `effects.ts` gives `StartupRedirect` and Reset's Undo the screen this window saved last while the cache still holds the object the save was made over; any newer settings object carries the core's own value (ui-shell.md). A whole-settings reader's renders across a save went from 2 to 1.

On the web, events arrive over a WebSocket. How it reconnects, and the full refetch after a reconnect, are in [server.md](server.md) under `GET /api/events`.

Memory: `gcTime` counts from the moment the last component reading a result unmounts. Catalog pages, guide windows and TMDB results are the large ones. Guide windows hold every programme of their channels and hours. They used to get 2 minutes, which dropped windows that still counted as fresh, so reopening the guide refetched them; they now get 5 minutes, equal to their stale time. `query.test.ts` checks that `gcTime` is at least `staleTime` for every command it lists with a finite stale time. Per-call overrides must keep the rule too: Home's trending rail (`tmdb.trending`) and its cards' `catalog.search` lookups use `TRENDING_MS` (60 min) for both; before, they were dropped after the 10 and 30 min default gcTimes while they still counted as fresh, so a return to Home after 10 minutes searched every near card again. TMDB results get 30 minutes because they never change and are slow to fetch again.

TMDB results do change with the settings, though. A disabled query still returns what it cached, so the movie and series pages merge TMDB data (and the season's TMDB episodes) only while `settings.tmdb.enabled` is on. `bindTmdbCacheSync` in `src/shell/effects.ts` (mounted by `useShellEvents`) also watches the `settings.get` cache: turning TMDB off removes every `tmdb.` query, and a new effective TMDB language (`tmdb.language`, or the app language when that is blank, as in `iptv-core` `tmdb/config.rs`) resets them, so open pages refetch in the new language. The blank-key check `tmdb.testKey` keeps its answer on a language change.

The VOD hooks in `src/features/vod/hooks/queries.ts` no longer set their own stale times where the table covers them. The grid pages spread `queryDefaultsFor('catalog.movies')`. The detail queries are built by `movieDetailQuery(sourceKind, ref)` and `seriesDetailQuery(sourceKind, ref)` (staleTime `DETAIL_STALE_MS`, 5 min). The detail pages and the prefetch use these same builders, so a prefetched result is exactly the cache entry the page reads. Xtream and Stalker sources ask the provider's detail command (`xtream.vodDetail`, `stalker.seriesDetail` and so on). An m3u playlist has no provider detail: its movie query caches the flat `catalog.item` row under `['catalog.item', { ref }]` and wraps it as a detail with `select` (`toMovieDetail`); an m3u series asks `m3u.seriesDetail`, which answers with the seasons the importer stored (m3u.md, Series). Flat `useRpcQuery('catalog.item')` readers (the player, the live pages) use that same key, so one ref holds one shape: a row a flat reader cached opens the detail page without a second call, and a detail the page cached is a plain row to the flat readers. `afterData` in `prefetch.ts` reads both shapes when it picks the backdrop to preload.

## Hover and focus prefetch

`src/features/vod/hooks/prefetch.ts` starts loading a detail page as soon as the user shows intent:

- `usePrefetchIntent(target)` returns `onPointerEnter`, `onPointerLeave`, `onFocus` and `onBlur` handlers. A pointer that rests on a card for `PREFETCH_REST_MS` (120 ms) counts as intent, and leaving earlier cancels it. Focus needs the same 120 ms rest, so Tab or a held arrow key passing along a rail warms only the card where focus stops. Only one focus rest is pending at a time, blur cancels it, and when it ends it fires only if focus is still inside the card (callers that wire no `onBlur`, such as the dashboard cards, rely on that check). A new target on a recycled virtual card, or unmounting, cancels a pending rest.
- Content that scrolls under a still pointer is not intent. Chromium sends `pointerenter` to each card that scrolls under the pointer, so a pointer rest starts only after the pointer has really moved: a window `pointermove` at new coordinates (a move event at the same spot, as Chromium sends after a scroll, is ignored). A `wheel` or `scroll` anywhere cancels pending pointer rests, and a card entered before the pointer moves again is parked until it does; leaving the card drops it. The grid's keyboard cursor rest and focus rests are not affected by scrolling, because the grid scrolls its cursor into view itself.
- `prefetchVodDetail(queryClient, target)` warms four things:
  - the detail query, with `retry: false`; a failed prefetch costs nothing, and the page asks again with retries when it opens;
  - the movie or series route chunk, through `preloadDetailChunk(kind)`, which runs the route's own `import()` (`loadMovieDetailPage` or `loadSeriesDetailPage` in `src/features/vod/routes.tsx`) at most once per kind per session. Hover, focus and cursor prefetch and the grid's idle warm-up share that one load; a failed load is forgotten, so a later call tries again;
  - the poster and backdrop, through `preloadImage` from `src/api/images.ts`. That is the same cache URL the page's `<img>` tries first, decoded at low priority. When the target has no backdrop, the one the detail hero shows first (the item's own, then the provider's first) is preloaded once the data arrives;
  - the TMDB lookup the page sends next (`prefetchTmdb` in `queries.ts`, the key and fn of `useTmdbMovie` and `useTmdbTv`), once the detail data arrives and only while `settings.tmdb.enabled` is on in the cached settings. Before, the page started it only after the provider detail arrived, so the cast and trailer came 0.3 to 1 s after the rest (VD-8). While the page's own lookup is still loading and the provider gave no trailer, the hero's action row holds the trailer button's place with a skeleton (`vod-trailer-slot`).
- Each target fires at most once per session. The key is `sourceKind|sourceId|contentType|itemId`. `preloadImage` keeps its own once-per-session memory per URL, which it shares with the dashboard's idle hero preloads. Live channels and other refs that are not movies or series are ignored.
- Prefetch is skipped when `navigator.connection.saveData` is set, when the primary pointer is coarse (`(pointer: coarse)`, where hover means nothing), and for touch `pointerenter` events on a device whose primary pointer is fine.
- Idle warm-up: touch screens get no hover prefetch, so `CategoryGridPage` calls `preloadDetailChunk(kind)` for its own kind once the grid mounts and the browser is idle (`requestIdleCallback` with a 2 s timeout, or a 500 ms timer where there is none), unless `saveData` is set. The first title opened then does not wait for its code.

Where it is used:

| Surface | How |
| --- | --- |
| `PosterCard` (VOD landing rails, grids, search results) | Takes a `prefetch` target, or a ready-made `intent`, and puts the handlers on the card and its link. Its `sourceId` also scopes the poster's cache URL. |
| VOD search results (`SearchPage`) | Each movie or series hit passes its target, using the hit's source kind. |
| VOD grid keyboard cursor (`CategoryGridPage`) | The grid moves `aria-activedescendant`, not focus, so the active cell uses `usePrefetchOnRest(target)`. It fires once the cursor has stayed on a cell for 120 ms, and only while the grid listbox has focus. |
| TMDB rails (`TmdbRail`) | A TMDB card links to a title search, not to a catalog item. `useSearchPrefetchIntent({ title, sourceId })` warms the search route chunk and the first `catalog.search` page with the exact args `SearchPage` sends (`{ query, sourceId?, limit: searchRequestLimit(SEARCH_LIMIT) }`, stale for 30 s like the page's own query). Titles shorter than `MIN_QUERY_LENGTH` after `normalizeQuery` are skipped. |
| Dashboard poster cards | The same hook, in `src/shell/dashboard/` (B2). |

Links to pages (NAV-1) follow the same rest and scroll rules through `useRouteIntent(to)` in `src/shell/routeIntent.ts`: the rail's links (`RailNavLink`), an open source's links, the phone tab bar, and Live's group, pinned view and All channels links (`CategorySidebar`). A rest of `ROUTE_REST_MS` (120 ms) calls `preloadRoute(to)` for the page's chunks (registered by `src/routes.tsx` with `setRouteWarmer`, since the shell cannot import the route table) and `prefetchScreenData(to)` for its first data under the page's keys. On Live a group's rest asks for its first page, its now/next and its favourite flags, so the click shows complete rows: in the group switch test, 0 requests after the click and 2 LivePage commits to titled rows, against 3 requests and 5 commits without a rest. Unlike a poster, a link is not remembered, since a page's data goes stale; a second rest asks again and the query cache answers it while fresh. The links of a group list that scrolls under a still pointer wait for the pointer to move, as posters do.

## Grid cursor shortcuts need grid focus

The VOD grid binds `s` (My List), `w` (watched), `Shift+F10` and the context-menu key to the keyboard cursor. They are registered only while the grid listbox itself has focus: `CategoryGridPage` tracks `gridFocused` from focus and blur events on the listbox. With the grid unfocused, or focus in the page's search field, the keys reach whoever else registered them (the player's `s` screenshot shortcut, for example), and `shortcutRegistry.list()` includes the grid's entries only while they are live. When the grid takes focus, the shortcut registry puts its entries on top again. `pages.test.tsx` checks both sides.

## Entry chunk budget

`dist/assets/index-*.js`, the module script `index.html` loads, may be at most 268,000 bytes. That is about 10 % over the 243,927-byte entry before Run 1 (SC10).

```
pnpm build && pnpm size:check
```

`tools/check-bundle.mjs [distDir]` is plain Node with no dependencies. It lists every JavaScript chunk, largest first, with its size and gzip size, marks the entry, and prints the boot size (the entry and the chunks it loads statically, `index.html`'s preloads). It exits 1 when there is no build, when there is no `index-*.js`, when `index.html` loads something else, or when an `index-*.js` is over budget.

It also follows the static imports of 23 lazy route chunks (`ROUTES`) and prints how many chunks and bytes beyond the boot chunks (the entry, `vendor-*`, `locale-*`) each loads before its first render. A lazy route renders only after its static imports have run, so whatever a page's chunk imports statically, the page waits for. It exits 1 when:

- the boot holds code only lazy pages use (`NOT_AT_BOOT`): the Tauri dialog, opener and updater plugins, TanStack Virtual, the form fields (`ui/Field.tsx`), the phone tab bar, and on a web build the Tauri window API (a web build is told by the precompressed `.br` file next to the entry);
- a route chunk statically loads code it must not wait for. Home, Search, Settings, the category grid, the VOD landing, Actor, Sports, Favorites, Downloads, Scheduled, My videos, My List and Sources load no player code at all, the store and the engines included; Recently watched and Stats may load the store but none of the player's UI; Live and the guide draw the stage but load no dock, controls, engines or Home's cards, and the guide no Live channel rows either; Archive, Multi-view, List, Movie, Series and My video load no dock or controls. When `DashboardPage.tsx` imported `playItem` and `preloadEngines`, a cold Home waited for 96.8 kB of player code it needs only after a click; when the `@/features/player` barrel exported `PlayerDock`, Live and the guide waited for the controls chunk, about 25 kB gzipped;
- one of the 9 pages that draw no virtual list (Home, Settings, Actor, Sports, Archive, Movie, Scheduled, Sources, Stats) loads TanStack Virtual;
- Settings, Sports, My List, Sources or Stats go over their byte budget before first render: what each loaded before the 2026-10-31 performance audit, plus the code the boot carried then and the page still draws (the form fields, 7.4 kB; TanStack Virtual, 27 kB). The min-size merge once added 23 to 56 kB to these pages by placing small shared modules differently, which no other check sees.

The check finds the player store, the engines, the dock, the controls, Home's cards, TanStack Virtual and Live's channel rows by a string only each holds (`player.volume`, `player.liveFormats`, `player.mini.pos`, `controls-pane`, `source-card-progress`, `measureElement`, `row-guide-unavailable`), not by chunk name: the min-size merge names a merged chunk after its first module, and the store has sat in `store-*.js`, `format-*.js` and `shareable-*.js`. A marker found in no chunk fails the check, and so does a route chunk that is missing, so a rename cannot switch a guard off. `src/ui/test/routeImports.test.ts` checks the same reachability on the source graph without a build, following the window-state effect's `import()` calls too.

`vite.config.ts` names lazy chunks whose first module is an `index.ts` barrel after their folder (`player-index-*.js`). Without that, `import('@/features/player')` would produce a second `index-*.js` beside the entry.

More settings in `vite.config.ts` shape the chunks:

- `experimentalMinChunkSize: 4_000` merges app chunks under 4 kB into a neighbour. With no merging a cold dashboard in server mode made 68 JS requests, 39 of them under 4 kB. Rollup merges a small chunk that several lazy pages share into the entry, because the entry always loads, so a larger setting moves lazy-only code there: at 10 kB the entry was 162.0 kB, at 4 kB 143.0 kB, with no merging 141.0 kB (84, 117 and 160 JS chunks; every route in one session 59 requests at 10 kB, 88 at 4 kB). Cold first paint on loopback was the same within noise at 10 kB and 4 kB.
- Each language is one manual chunk, `locale-<lang>` (`vendorChunk` matches `src/i18n/<lang>/*.json` and the folder's `index.ts`), since `loadLanguage` fetches all of a folder's namespaces at once. A manual chunk stays out of the min-size merge, so no foreign strings end up in app chunks; without these chunks the 10 kB merge cost 11 % more bytes. Each JSON file in them is one `JSON.parse("…")` (`json: { namedExports: false, stringify: true }`, P2-BOOT-2). Vite's default made every key an `export const` and every file an object literal over them, so `locale-en`, which every boot loads before the first render, was 3,140 statements to compile: 217,950 bytes (64.6 kB gzip) and 18.8 ms to load in a fresh Node 24 process, against 150,775 bytes (43.2 kB gzip) and 6.6 ms as strings (German: 13.3 to 5.9 ms).
- `treeshake.manualPureFunctions: ['memo', 'lazy']` marks React's wrappers pure. Rollup cannot prove they have no side effects, so a module with a top-level `memo(...)` reached through the `@/ui` barrel was kept whole in the importer's chunk; that put `VirtualGrid` in the entry.
- Vendor chunks (`VENDOR_CHUNKS`): `index.html` preloads every `vendor-*` chunk on every boot and a manual chunk loads whole, so only what the boot runs belongs in one. `vendor-react`, `vendor-query` (`@tanstack/query-core` and `react-query` only), `vendor-i18n`, `vendor-ui` and `vendor-tauri` are the boot's. On a web build `vendor-tauri` holds only `@tauri-apps/api`'s `core`, `event` and their tslib helpers (`TAURI_BOOT_FILES`); the window, dpi and image modules go to a lazy `window-*.js` the web never fetches. The desktop build keeps the whole API there, since `main.tsx` syncs the window's fullscreen state at boot. TanStack Virtual (`virtual`, 27 kB) and the Tauri dialog, opener and updater plugins (`tauri-plugins`, 1.9 kB) are lazy manual chunks without the `vendor-` prefix, so they are not preloaded and the size check counts them as route code. They are manual on purpose: left to Rollup, the min-size merge put TanStack Virtual in the parental-locks chunk that Settings, Search and the VOD pages load, and the opener plugin in a chunk Home loaded.
- The virtualizer's boundary (`virtualListBoundary` in `vite.config.ts`): the min-size merge weighs only the modules it merges, not the manual chunks they import, so it joined small helpers (the parental-lock hooks, `useMediaQuery`) to `src/ui/virtualizer.ts`, and every page needing one of them loaded TanStack Virtual before its first render. The plugin appends a statement Rollup counts as a side effect (`new WeakSet().add({});`) and marks the module free of side effects for tree-shaking, so it still loads only where something uses it, while the merge, which never makes a page run a side effect it would not run otherwise, keeps it and every chunk that imports it out of pages without a virtual list. Settings' lock-groups dialog, its only virtual list, loads when it opens.
- Shared icons (`SHARED_ICONS`): the 27 lucide icons that seven or more lazy pages draw go in `vendor-ui` (about 11 kB). Rollup counts an icon module as having a side effect (lucide's `__iconData.node;` statement), so the merge may join an icon only to a chunk every page drawing it also loads; for an icon many pages share that left app code that brought more along (database-backup sat with the library's virtual rows, so Settings, Sources and Stats loaded them and TanStack Virtual; rotate-ccw sat with the channel-edit actions in front of Settings). The other icons stay with their pages.
- Own chunks (`OWN_CHUNKS`): `src/lib/duration.ts` and `features/player/components/glassButton.ts` get chunks of their own, out of the merge. The merge put the first in the player's subtitle chunk (so Settings waited for the player's controls) and paired the second with the engine preloader in the entry (3.2 kB every page loaded at boot).
- `themeBootLocales` writes the locale chunks' URLs into `theme-boot.js`, which preloads a remembered non-English language next to the entry (ui-shell.md).

Fixes from the 2026-10-19 performance audit:

- react-router (BUNDLE-ROUTER): 7.18's exports map has no `production` condition, so every build resolved `dist/development`, which runs with `ENABLE_DEV_WARNINGS = true`. A production build (`vite build`) aliases the bare `react-router` specifier to `node_modules/react-router/dist/production/index.mjs`; `vite` dev keeps the warnings, and vitest (`vitest.config.ts`) and the typecheck resolve the package as before. `vendor-react` lost the dev-only warnings (1.7 kB).
- `vendor-ui` (SH-10) holds `tailwind-merge`, `clsx` and `zustand` (and, since the 2026-10-31 audit, the shared icons above). cmdk, its Radix dialog stack (`@radix-ui/*`, `aria-hidden`, `react-remove-scroll` and the rest) and `lucide-react` left the manual chunk list, so Rollup places them with their users: cmdk with the lazy command palette, each icon with the code that draws it. `index.html` preloads `vendor-ui` on every boot, and it went from 126,172 to 30,335 bytes; the icons the shell draws moved into the entry (about 9 kB). An icon used by several lazy pages and nothing else gets its own small chunk, since lucide's icon modules have top-level calls the min-size merge treats as side effects.

`src/ui/test/bundlePurity.test.ts` checks that `memo` and `lazy` are on the pure list, that every component wrapper called at module top level is on it, that `experimentalMinChunkSize` is between 3,000 and 5,000, that each language has one chunk with no app modules in it, that JSON compiles to one `JSON.parse` per file, that a build aliases react-router to its production files and dev does not, that cmdk, Radix and the icons stay out of `vendor-ui`, and that the build writes its asset list into the service worker. It also checks the vendor chunk assignment for a web and a desktop build, the shared icons, `withLocaleMap`'s output, and that Rollup still counts the virtualizer's boundary statement as a side effect.

### What moved out of the entry in Run 3

After Run 2 the entry was 267,003 bytes, under 1 kB from the cap. Most of it was the player: the shell imported `PlayerDock`, `ExternalPlaybackFooter` and `restorePlayback` from the `@/features/player` barrel. The watch-stats reporter and the window-state effect pulled the player store, the engines, subtitles and track handling in too. Run 3 cuts each of those static paths:

- `ShellLayout` imports the player dynamically (since the 2026-10-31 audit from `@/features/player/dock`, which holds the dock, the external-playback footer and `restorePlayback`; see Keeping it there), and not before the first route is in. The router renders the shell only after the first route's lazy chunks have loaded (initial hydration), and `usePlayerModule()` then waits `PLAYER_PREFETCH_DELAY_MS` (2.5 s) followed by the first idle moment (`requestIdleCallback`, at most `PLAYER_IDLE_TIMEOUT_MS`, 2 s; a macrotask where the browser has no `requestIdleCallback`), or for the first `pointerdown` or `keydown` from the start, whichever comes first (`schedulePlayerLoad`). Without the delay the player's chunks (about 200 KB) arrived at about 0.4 s on a cold load, among the first route's own chunks and long tasks. It loads at once when `sessionStorage` holds a resume record (`player.resume`), and `restorePlayback` runs only then. Run 3 first started the import when the module ran; under 50 ms of latency the player chunk and its dependencies then competed with the route chunks for the browser's connections and delayed the first paint by about 100 ms. A page that plays imports the player itself, so after a click the shell's import usually resolves at once. A failed chunk load leaves the shell usable without the dock.
- The watch-stats reporter (Run 2 C7) starts from an effect that imports `@/features/stats/reporter`, once the player module is in. It reads the player store's state when it starts, so nothing that played before is lost. `RecordingWatcher` imports the player too, so it also mounts with the player module; it picks up reminders that fired before it listened.
- `useWindowStatePersistence` (desktop only) imported `@/features/player/pip` inside its async start-up, next to the Tauri window API it already loaded lazily. Since the 2026-10-31 audit it reads `usePipStore` statically from `features/player/pipState.ts` (zustand only, re-exported by `pip.ts`): the `pip` import had loaded the player store right after the first paint.

### First render

`src/main.tsx` renders once `Promise.all([initI18n(), imageBaseReady()])` settles. A remembered non-English language loads in one request: `src/i18n/lazyLocales.ts` maps each language to its folder's `index.ts`, which gathers every namespace and sits in the `locale-<lang>` chunk, and the entry carries that 18-entry map. ### Keeping it there

- New pages go in route chunks: use `lazy` in a feature's `routes.tsx`.
- Dialogs and hosts that show on demand load behind `import()`. `CommandPalette`, `ShortcutOverlay`, `ParentalGateHost` and `RecordingWatcher` are examples.
- Do not import the `@/features/player` barrel, or anything that reaches `@/features/player/store`, from a module the shell loads statically. If a shell file needs the player, load it with `import()` the way `ShellLayout` and `effects.ts` do.
- The barrel exports only the store calls, `useChannelZap`, `preloadEngines`, `PlayerStage` and `stopExternalPlayback`. It must not export anything that reaches the dock or the controls: pages import it for the stage, and the shell loads the dock and the external-playback footer from `@/features/player/dock`, which re-exports `restorePlayback` and `usePlayerStore` so the dock's module-level subscribers (history, sync, sleep timer, connection limit, stream info, PiP recovery) are in place before a resume runs. `PlayerStage` imports `player.css` itself, so the stage pages preload the stylesheet before the dock loads.
- Pure helpers that pages need live apart from heavy modules: `player/resumeRules.ts` (`MIN_RESUME_SECONDS`, `isWatchedReplay`, re-exported by the store), `player/trackTypes.ts` (`EMPTY_TRACKS` and the track types, re-exported by `engines.ts`, so the store no longer carries the engines: the store chunk went from 72.5 to 51.9 kB and the engines are a 25.7 kB chunk of their own), `player/menuDismiss.ts` (`playerMenuJustClosed`, so the detail pages do not import `Controls.tsx`), `player/pipState.ts`, and `joinList` and `isolate` in `@/lib/intl` (re-exported by `shell/dashboard/cards.tsx`, so Live and the guide do not load Home's cards). The library pages load the player on the press that plays (`features/library/lib/open.ts`, `playDownload.ts`), `library/deps.ts` re-exports nothing from the player, and the recording barrel does not export `RecordingWatcher` (the shell loads it by path). The guide's Stalker notice is `live/components/GuideUnavailableNotice.tsx`, so the guide does not load Live's channel list.
- `pnpm size:check` fails when one of these slips (Entry chunk budget above).
- To find out why a module is in the entry, build with a small Rollup plugin that records `getModuleInfo(id).importers` for the entry's modules, then follow the importers back to `src/main.tsx`.

## Long lists and grids

Fixes from the 2026-10-19 performance audit (SH-5, VD-1, VD-2, LV-1 to LV-8):

- Every virtualized list and grid goes through `useListVirtualizer` (`src/ui/virtualizer.ts`), which wraps react-virtual's `useVirtualizer` with `useFlushSync: false`. react-virtual 3.14 otherwise renders each range change synchronously inside the scroll event. `src/virtualizer-budget.test.ts` fails when any other module imports `useVirtualizer` or `useWindowVirtualizer`.
- Mounting a virtualized list reads no layout (P2-LIVE-1). react-virtual read the scroller's `offsetWidth` and `offsetHeight` as it attached, in a layout effect, and scrolled the scroller to its start offset there, which forces layout as a read does. On Live's cold open that forced the new page's whole layout inside the commit (78 ms at a 4x CPU slowdown), and the rows for the size it found rendered in a second commit before the paint. `useListVirtualizer` now takes the size from the scroller's ResizeObserver (`observeElementRectAfterLayout`), whose first callback comes after the browser's own layout; until then the list uses its `initialRect`, or the window's size without one. When the measured size shows more rows than that, they render inside the callback, before the frame paints; when it shows fewer, the next render drops them. The scroll to the start offset is left out on the first attach when the scroller is already there: a scroller created in that commit is at 0, and the default offset is the one just read from it. Without a ResizeObserver (jsdom without a stub) the size is read at once, as before. A `scrollToIndex` or `scrollToOffset` before the next frame, the first report yet to come, reads the size first (P2-LIVE-5), so the live list opening on the playing channel aligns that row against its own height and not the window's; the scroll lays the page out anyway, so the read costs no extra layout. The Manage lists and Edit channels rows are memoized with stable handlers, so a drag-over re-renders the rows whose drop marker changes, not all 2,000. Edit channels also hands `SortableList` stable `renderRow`, `getKey`, `getLabel`, `rowClassName` and `onMove` (callbacks that read the latest entries through a ref; the row body is `EditItemRow`), rows learn whether they are `last` instead of the count, and a move's optimistic update keeps the entries that kept their place (`reorderEntries`), so an Alt+Arrow move re-renders the two rows it swaps: 2 row renders at 2,000 channels, against 2,000 before (LV-6b). The list page's dropped-channels tray (`UnavailableEntries`) is memoized with a stable `onRemove` and the page's own number formatter, so a page re-render with the same entries (the clock, another channel starting) draws none of its rows again. Edit channels renders `SortableList` with `virtual` (`{ rowHeight, scrollerClassName }`): the list scrolls in a box of its own and mounts only the rows near the screen through `useListVirtualizer`, at a fixed row height (`useRowHeight(46, 11)`), with `aria-setsize` and `aria-posinset` on each row. A plain or Alt arrow scrolls its target row into view (`scrollToIndex`), and the focus waits for that row to mount; a dragged row stays mounted while the list scrolls away from it (a `rangeExtractor`), so its `dragend` still resets the drag, and so does the row with focus in it, so focus does not drop to `<body>`, where the dialog no longer hears Escape or Tab. Near the box's edges the browser scrolls the list during a drag, as it did before. At 2,000 channels the dialog mounts 26 rows instead of 2,000 (jsdom: 1.6 s to 0.37 s to open), and a removal re-renders 26 rows instead of 3,998. Manage lists (at most 50 rows, some of them two lines tall or a rename form) is not virtual. A list write's own refresh joins the event burst (`invalidateWithEvents`), so the write and its `lists.changed` refetch `lists.*` once.

## VOD landing and detail pages

Fixes from the 2026-10-22 speed pass:

- The category filter (VOD-LANDING-RENDERS): the filter field, its text, the filtered entries and the index live in `CategoryIndexSection` (`VodLandingPage.tsx`), so a keystroke re-renders the index and not the page above it. The page hears only when filtering starts or stops, which pauses its scroll memory; that memory stays in the page, because a child's layout effects run before React attaches the page's ref to the scroller, so from the section it found no scroller whenever the landing mounted with the categories cached (Back) and neither restored nor recorded. Before, every keystroke re-rendered every mounted rail card: typing "netflix" with the 12 category rails mounted drew 2,023 cards (`landingRenders.test.tsx`), now none.
- The landing's rails (VOD-LANDING-RENDERS): Top rated and the category rails are a memoized `LandingRail` with plain props (the category, the sort, one memoized set of grid arguments), which builds its `CatalogRail` input itself. Their cards and Recently added's are a memoized `LandingCard`, which builds the My List target, the prefetch target and the language once per title, as the grid's `GridPoster` does, and `ContinueSectionRail` is memoized. A query answer re-renders the cards it changed: a cold landing with every rail mounted drew 1,132 card renders for 289 cards, now 294, and a new resume answer re-rendered 296 cards, now 13 (the card it moves and the Continue watching rail).
- Detail pages from a list (VOD-DETAIL-PLACEHOLDER): `useMovieDetail` and `useSeriesDetail` give an Xtream title's detail query a `placeholderData`, the catalog row a list already holds (`cachedCatalogRow`: the `catalog.movies` or `catalog.series` pages, `catalog.recentlyAdded` and `catalog.search` answers), which the query's `select` wraps as a detail. The panel answers `get_vod_info` and `get_series_info` on every open, so the page waited 0.3 to 1.5 s on a large panel, minus whatever a hover prefetch saved. While `isPlaceholderData` is set, a movie page shows its hero with Play enabled; a series page shows its hero with Play and the series' Watched button disabled and an episode skeleton, since the seasons decide which episode Play starts and which episodes Watched marks. The hero keeps the artwork's room above the poster and the trailer's place in the action row (`pending`, `vod-trailer-slot`), the TMDB lookups, the similar-titles fallback, the scroll memory and a series' focus on open wait for the real answer (it may bring the tmdbId, so an earlier lookup would be a second one), and the "provider details unavailable" notice can only come with it. m3u details are the local row already, and a Stalker page keeps waiting, because its parental gate needs the title's category from the details. In jsdom with an 800 ms provider delay, a movie's hero and Play showed after 1,007 ms and now after 177 ms (`detailPlaceholder.test.tsx`; most of that is the page's first render under test).
- Detail page lookups: `catalog.categories` is read only for an item without `categoryName` (a Stalker portal hit, an Xtream title missing from the catalog), and `sourcePins.get` only once `catalog.sameTitle` found another copy, so with one source a detail open asks for neither.
- Series playback (vod-browsing.md, Series detail): the episode queue resolves only the next episode up front; later ones are placeholders resolved on play. Starting S1E1 of a 22+22-episode Xtream series sent 43 `streamUrl` calls and each auto-advance 42; now 1 each.
- Watched marks: Mark season or series watched is one `userstate.setWatched` call with `episodeIds` and one transaction in the core, where it was one call per episode at once, each a gated write and a scan of every watched row: 200 episodes went from 78 ms to 1.8 ms and 1,000 from 944 ms to 18 ms in a release build (userstate.md).
- My List (watchlist.md): every reader of `watchlist.list` gets a 5-minute stale time, and the staleness link from positions finds the list by its hash instead of an exact-key `invalidateQueries` (69 ms to 0.6 ms with 1,000 cached and 100 positions queries).

## Progress, clocks and formatters

Fixes from the 2026-10-19 performance audit (VD-3 to VD-7, VD-9):

- Download progress: each /downloads row (`DownloadRow`) subscribes to its own sample with `useLiveProgress(download)` (`src/features/library/lib/progress.ts`), so a `downloads.progress` event re-renders that row only, and the row re-renders once more when its sample goes stale (`STALE_MS`), so a stopped transfer reads as stalled. `actionsFor` returns one shared array per answer, so a row's props stay equal. Before, the page re-rendered on every event and every row with it.
- Detail pages: `useItemDownloads` refetches `downloads.list` for `downloads.update` only (a new download of the title, a status change). The hero's download button and an episode row's download control read a running transfer's bytes with `useLiveProgress` (`RoundDownloadState` and `DownloadingLink` in `actions.tsx`), so a progress event re-renders that control and nothing else. VD-3 had kept a refetch twice a second for progress of the page's own rows, and with it a render of the whole page; two seconds of one running download cost 4 list calls and 4 page renders, now none (DL-7, `detailDownloads.test.tsx`). Before VD-3, any transfer refetched the whole list on every open detail page.
- Sources page: `SourceCard` is memoized. It reads its import progress and cancel state from the progress store by source id, and its guide progress through a selector over its own guide URLs (`useSourceGuide`), and the page passes one set of handlers that take the source or its id (`useStable`). An `import.progress` or `epg.progress` event re-renders the card it is about, not the page and every card (VD-5; the core side, a 250 ms gate on row counts, is IN-8).
- Portal search: `SearchPage` sends `stalker.search` only once the query has rested `PORTAL_DEBOUNCE_MS` (450 ms) and has `PORTAL_MIN_CHARS` (3) characters; a query the page opens with goes out at once. The library search keeps its 100 ms pause. Each portal search asks every Stalker source for movies and series, up to 4 portal pages a call, so typing "breaking bad" with two portals sent about 170 portal requests (VD-6).
- /scheduled: the page's clock ticks once a minute, for the day headings; only a row that is recording now runs a one-second clock for its elapsed time and progress (VD-7).
- Intl formatters: `src/lib/intl.ts` caches `Intl.NumberFormat`, `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat` per locale and options (`numberFormat`, `dateTimeFormat`, `relativeTimeFormat`). The download sizes, source card counts and times, import progress seconds, the Scheduled and recordings dates, the open-history and My List relative times and the My List counts use it, so a list row no longer builds its formatters on each render. So does `formatUnit` ("12 hours", P2-BOOT-4), which the Sources page's two source dialogs call on every render while closed and the refresh settings once per choice.
- My List search folds each entry's title once (a WeakMap per entry) and the query once per view, and the "date added" sort parses each date once instead of twice per comparison (VD-9).

## Large catalog imports

A large catalog rewrite (at least 20,000 rows touched; the full rule is in catalog.md) drops the secondary indexes of `items` and builds them once before the commit, instead of updating each of them on every row. It changes the schema once per import, so every pooled connection re-prepares its statements once, and the rebuild raises peak memory by about the largest index. Details in [catalog.md](catalog.md#index-rebuild-for-large-rewrites).

Since the 2026-10-31 audit (release builds with LTO off on a 4-core VM; the numbers in each subsystem's document):

- The Xtream and Stalker syncs tell the writer how many rows will come (`CatalogWriter::begin_with`), so a large refresh drops the indexes before it deletes the old rows: `begin` of a 180k-movie refresh beside 200k channels went from 3.8-5.2 s to 0.85-1.7 s. A rewrite of every row empties the search index and `items_rank` in one statement each (566 ms to 6 ms on 200k channels). Removing a large source drops and rebuilds the indexes the same way (200k channels: 3.3 s and a 101 MB WAL to 0.6 s and 27 MB; sources.md).
- Xtream rows carry their extra fields as serialized text from the mapping step (`ItemRow::extra_json`): heap per mapped row went from 792 / 758 / 1,102 bytes (live / movie / series) to 183 / 144 / 371, about 100 MB less at a 170k-row sync, and each row is freed once written, so the rows are gone before the index build (catalog.md, xtream.md).
- M3U series rows go to the writer one show at a time, and the parser copies only what it keeps: a 96 MB `m3u_plus` list with 300k episodes peaked 422 MB above its start before, about 213 MB now, with the same stored bytes (m3u.md).
- A Stalker channel list is kept as the portal's text and decoded item by item only when it changed: a 20k-channel import's peak heap went from +176 MB to +57 MB (changed) and +33 MB (unchanged), and the longest runtime stall from about 0.5 s to 12 ms (stalker.md).
- After every source import the core hands the freed heap back to the system on Linux with glibc (`malloc_trim`): an Xtream import of 170k items used to stay 278-328 MB above its start, now 46-71 MB (sources.md).

## Filtered pages and search

- A movie or series page with a minimum rating or a year range reads its sort's index in order: the page statement writes those filters as `+i.rating` / `+i.year` when the grid is sorted by another key, and migration 0019 puts the rating and the year in every sort index, so the page reads index entries instead of a table row per title it passes. A page at or past the filtered total skips the page statement. Details in [catalog.md](catalog.md#reading).
- `catalog.search` runs its substring pass only when no list has a word-prefix hit, and its ranking pass reads no category row per match. The word-prefix pass ranks on `items_rank` (migration 0020), about 60 bytes per match instead of the item's wide row, and keeps each list's best rows with a bounded top-N per list over one materialized match set instead of a `ROW_NUMBER()` window that sorts every match. On 215k items in a release build that takes "th" (56k matches) from 155 ms to 61-64 ms at p95, "the" from 105 ms to 43-44 ms, "a" from 110 ms to 37-44 ms and hide-mode "th" from 99 ms to 52-61 ms; narrow queries gain too ("news" 20 to 12 ms, "blue" 16 to 10 ms). Details in [catalog.md](catalog.md#reading). `crates/iptv-core/tests/l3_search_perf.rs` holds these on 215k items in release builds: every search under 100 ms at p95, the broad prefixes and hide mode included (only the substring scan, which reads every title, under 250 ms), filtered pages and parental hide mode under 50 ms. `crates/iptv-core/tests/l4_search_rank.rs` checks that the ranking returns the same rows in the same order as the window statement.
- All channels and all radio take their total from the stored category counts when nothing narrows the list and no channel is hidden by an edit, as All movies and All series did: a page of 200k channels went from 8-20 ms (40-110 ms with 100 of 2,000 groups hidden) to about 1 ms, and the first page of 50k channels from 4.5 to 1.0 ms (`catalog_perf.rs`). List reads skip a series row's stored `episodes`, so an M3U series page went from 5.5-6 ms to under 1 ms. Details in [catalog.md](catalog.md#reading).
- `positions.continueWatching` walks `idx_positions_updated` newest first and stops at the limit, instead of a window over the whole table: 68 ms to 0.46 ms at 42k rows and limit 24 (userstate.md).
- Every pooled connection runs with a 32 MiB page cache (`cache_size` in `db::configure`; SQLite's default is 2 MiB). Reads of `items` rows by rowid missed the default cache on most reads on a 215k-item library. The larger cache halved "blue", "news" and "zzzz" (p50 25-30 ms to 12-17 ms) for about 40 MB more peak memory in `l3_search_perf.rs`; 16 MiB gained almost nothing and 64 MiB little more. The cache belongs to its connection (since the 2026-10-31 audit really so: see SQLite build flags below) and fills only as pages are read, so the pool's 8 connections (`POOL_MAX`) hold at most 256 MiB. The pool keeps its connections for the life of the app (`idle_timeout` and `max_lifetime` are off): r2d2's defaults closed an idle connection after 10 minutes and replaced every one after 30, each time with a cold cache and no prepared statements. Each connection caches 64 prepared statements (`db::STATEMENT_CACHE`; rusqlite's default is 16, while one Live scroll step uses 10-14 and moving between Live, VOD and Home 40-60), and the catalog page statement binds its OFFSET, so every page of a list reuses one cached statement. LIMIT stays literal, since SQLite uses it in the row estimate. Migrations run on the 2 MiB default (`db::migrate`; a 600k-row guide upgrade would otherwise fill the whole 32 MiB). A memory map (`mmap_size`) measured no gain and is not set. `items_rank` adds about 15 MB per 220k items to the database and, while a broad search reads it, up to that much to a connection's page cache; the materialized match set of a broad search takes about 2 MB of temp memory.

## SQLite build flags

The repository's `.cargo/config.toml` (tracked, and copied by the Dockerfile) sets `LIBSQLITE3_FLAGS = "-USQLITE_ENABLE_MEMORY_MANAGEMENT"` for the bundled SQLite. With that define, which libsqlite3-sys sets by default, the page caches of all connections share one process-wide LRU behind a global mutex taken on every page fetch, so pooled queries running at the same time waited on each other and the "32 MiB per connection" above was not really per connection. Without it each connection keeps its own cache and takes no shared lock. With `tests/db_concurrency_perf.rs` (ignored; 150k items, a fixed mix of four catalog RPCs, each call on its own pooled connection) on a loaded box: 1 task 87 and 76 calls/s (noise), 2 tasks 70 to 110 calls/s, 4 tasks 76 to 133 calls/s, and search "blue" p50 with 4 tasks 108 to 60 ms. On a quiet box the branch's build scales 118, 245 and 351 calls/s from 1, 2 and 4 tasks. A side effect: after a 120 MB guide ingest RSS settled about 30 MB lower. `SQLITE_DEFAULT_MEMSTATUS` stays on: it measured no gain, and `migration_perf` reads `sqlite3_memory_used`. In WAL mode any commit by another connection resets a connection's cache at its next read, whatever the cache mode, so warm caches never survive a write.

An environment `LIBSQLITE3_FLAGS` wins over the file's value, and a build run from outside the repository does not see it; `tests/sqlite_compile_options.rs` fails on a build that lost the flag. Machine-local cargo settings, such as a target dir elsewhere, belong in `CARGO_HOME`'s `config.toml` or in `CARGO_TARGET_DIR` (CONTRIBUTING.md).

## Release profile

`opt-level = "s"` with fat LTO and one codegen unit stays. Measured against 2 and 3 with that profile (libsqlite3-sys at 3) on the release perf tests and `tests/resize_perf.rs` (ignored), 4 rounds on a loaded 4-core VM: at 2, a 600x900 poster resize went from 21.0 to 18.9 ms p50, a 2000x3000 one from 119 to 105 ms, an 800x800 PNG logo from 20.1 to 17.0 ms, the 120 MB guide ingest from 2.73 to 2.51 s and the 50k-entry M3U parse from 89 to 67 ms; imports moved about 5 % and searches and page queries not at all (they run in SQLite, already at 3). 3 was no better overall. Either level grew `iptv-server` by 32 % (18.5 to 24.4 MB). The earlier micro-benchmark's 2x gain on resizing did not reproduce in the real LTO build. Under fat LTO the merged module is optimized at the binary crate's level, so a package override that raises one Rust crate above it (iptv-core, image or serde_json) changes next to nothing; only the global level matters, and C code built by cc (SQLite) is the exception. `resize_perf` numbers taken with LTO off and 16 codegen units come out 1.6-1.9x slower on JPEG than the shipped build.

## Guides, background work and housekeeping

- A guide refresh replaces only the programmes that changed and updates the search index in place (epg.md, Storage; guide-search.md, The index): for a 176k-programme feed, the time under the write lock went from 1.28 s to 0.39 s for an unchanged refresh and from 1.30 s to 0.39 s 12 h later, and the WAL it wrote from about 63 MB to 0.3 and 6.6 MB. Migration 0027 dropped two programme indexes: a first ingest of a 120 MB guide went from 2.34 to 1.87 s and its peak RSS delta from 72 to 64 MB (`epg_perf.rs`), and a two-feed database from 95 to 84 MB.
- A guide whose body is the one its stored data came from is kept as on a 304 (an unchanged 120 MB local guide: 1.45 s to 1 ms), with a status-only `epg.changed`. The channel directory is built at boot and right after a refresh that stored data, before `epg.changed` goes out (first now/next of 120 refs after a refresh: 210 ms to 1.6 ms), and a refresh that kept the guide's channels keeps the fuzzy name results (120 unmatched titles: 1,455 ms to 0.9 ms). Guides that already have data wait until 30 s after boot, with the source startup pass.
- The provider guide caches are bounded: Xtream answers past their TTL are dropped when one is stored and on the guide scheduler's 30 s tick, and the archive cache holds at most 60,000 programmes (xtream.md). The UI keeps at most 200 Xtream archive tables per source.
- Stalker day tables are cached and the bulk guide is kept as mapped programmes, not JSON (stalker.md): catch-up after the ribbon went from 6 table requests and 2.1 s to none and 0.3 s, and the bulk guide's held memory from 232 MB to 38 MB.
- A provider request outside an import that ran out its deadline in silence is not sent again (xtream.md, stalker.md), and the UI does not retry provider failures the core already retried (Query cache timing).
- The TMDB cache's expired rows are purged in the background a minute after launch and then daily, 500 rows per step of the background gate, not at boot (tmdb.md).

## Images, the service worker and recording

- Images (image-cache.md): when every gate slot is waiting on upstream fetches, the gate names the pictures waiting in view to `images.warm`, and the core fetches them in parallel under per-host and global slot caps; a cold 30-poster wall behind 300 ms of latency went from 2.42 to 0.76 s in server mode across three hosts and from 1.51 to 1.21 s on one host on desktop. A second width of one image is made from a cached wider copy, with no upstream request. A width variant's fetch asks for JPEG or PNG, so a host that would answer WebP sends a picture the resizer can shrink. In server mode over HTTP/2 or HTTP/3 the gate allows 12 pictures at once instead of 4.
- The service worker (server.md, PWA): Chromium routes `/api/*` and the requests the worker ignores to the network without a fetch event (5-6 ms instead of 16-19 ms right after the worker went idle), and a first-time asset streams to the page while its copy is cached in the background (first byte of a 2 MB chunk after 5-11 ms instead of about 1 s).
- Recording (recording.md): the HTTP copy writes through a 128 KiB buffer flushed every 2 s (799 to 25 writes in 5 s at 6.5 Mbit/s), and a recording mpv keeps no back buffer (about 150-200 MiB less per recorder).
- Embedded mpv's cursor poll in fullscreen and picture-in-picture reads only the cursor while it rests (5 IPC calls a second instead of 15), and none on a focused macOS window (players.md).
