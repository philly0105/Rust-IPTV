## Detection

The first existing file wins. mpv and VLC are searched separately:

1. The configured path (`settings.mpvPath` or `settings.vlcPath`). Surrounding quotes are tolerated. A directory is accepted, and the exe is looked up inside it. A configured path that does not exist falls through to the search.
2. mpv only: `vendor/mpv/mpv.exe` beside the running exe, then under the working directory, then under up to four ancestors of each. The ancestor step lets `pnpm tauri dev`, whose exe lives in `target/debug`, find the repo's `vendor/`.
3. Every `PATH` entry, like `where`. Only `mpv.exe` matches; `mpv.com` is skipped because it is the console wrapper.
4. Well-known locations:
   - Program Files and Program Files (x86): `VideoLAN\VLC\vlc.exe`, `mpv\mpv.exe`.
   - scoop: `~/scoop/apps/<name>/current`, `~/scoop/shims`, `$SCOOP`, and the global `ProgramData\scoop`.
   - choco: `C:\ProgramData\chocolatey\bin`.
   - WinGet: `%LOCALAPPDATA%\Microsoft\WinGet\Links`, then `...\WinGet\Packages\<id containing the name>\`.
   - Other OSes: `/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin`, `/opt/local/bin`, `/snap/bin`, and `/Applications/{mpv,VLC}.app/Contents/MacOS/*` (also under `~/Applications`).

`settings.detectPlayers` (B2) and `player.detect` both call `player::detect(&settings)`, and both are desktop only.

## External players

`player.openExternal {player, source}` resolves the player through detection and builds argv as in C4:

- mpv: `--title=<t> [--user-agent=<ua>] [--referrer=<ref>] [--http-header-fields=Origin:<o>] --force-media-title=<t> [--demuxer-lavf-analyzeduration=2] <mpvArgs...> -- <url>` (the analyze flag for live sources only, before `mpvArgs` so the user's own value wins, from the flag itself or a `--profile` or `--include`; a value in `mpv.conf` loses to it, because mpv reads its config before the command line; see `mpv.load` below)
- VLC: `--meta-title=<t> [--http-user-agent=<ua>] [--http-referrer=<ref>] [--one-instance --playlist-enqueue] <vlcArgs...> -- <url>` (VLC has no Origin option)

`--` ends option parsing in both players, so a playlist URL such as `--script=...` stays a URL. Before anything is spawned, `args::validate_play_url` checks the URL for `player.openExternal` and `mpv.load` (through `player::with_local_file`). It rejects with `Invalid` a URL that is empty, starts with `-`, contains control characters, or has a scheme outside `http`, `https`, `rtmp`, `rtmps`, `rtsp`, `udp`, `rtp` and `mms`. Sources of kind `file` may also be local absolute paths (`C:\...`, `C:/...`, or `/...` on Unix). A network path (`\\server\share\...`, `//server/share/...`) and a `file:` URL are refused: Windows opens one by logging in to that server with the user's credentials, and the UI marks a playlist line without a scheme as `kind: file`. On desktop, `recordings.playSource` and `myvideos.playSource` point the inline player at the loopback proxy's file routes ([desktop.md](desktop.md#what-it-serves)); `player.openExternal` and `mpv.load` turn such a URL back into the file's path first (`player::with_local_file`), because an external player outlives the app and its proxy and mpv reads local files itself. That path skips the check because the core chose it, so a download or recording on a network share still opens. When the proxy is not running, `playSource` returns the path itself, which has to pass the check like any other source.

`settings.playerReuseInstance` (default true): before spawning, the app closes the external player it started last (if that player is still running, it is killed and the app waits up to 3 s for it to exit). VLC also gets `--one-instance --playlist-enqueue`. The kill stays even for VLC: with `--playlist-enqueue` the running instance only appends the new channel to its playlist, and a launch handed to a running instance exits at once, which the watcher would report as the player exiting while the old one, no longer tracked, plays on. `player.stopExternal` (no args, returns `{stopped}`) ends that player on demand. Players the user started outside the app are never touched.

Header flags appear only when they are set and not blank. Each flag is a single argv element, and `std::process::Command` quotes it for the platform, so titles that contain quotes or spaces arrive intact. The `Origin` value is escaped for mpv's string-list syntax (`,` becomes `\,` and `\` becomes `\\`), which is what the old app did for the MAG user agent `(KHTML, like Gecko)`.

`settings.mpvArgs` and `settings.vlcArgs` are split by `args::split_shell_args`:

- Whitespace separates arguments.
- `"..."` groups. Inside it, `\"` is a literal quote and every other backslash is kept.
- `'...'` groups with no escapes at all.
- Outside quotes, a backslash escapes only whitespace or a quote. `C:\path` and `\\server\share` stay intact.
- Quotes can appear mid-argument (`--title="A B"`), and `""` produces an empty argument.

The process runs with null stdio, `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` on Windows (its own process group on Unix), its working directory set to the player's folder, and no kill-on-drop, so it outlives the app. `player.external {state: 'started', player, title, pid}` is emitted right away, and the pid is kept for reuse and `player.stopExternal`. A watcher task then emits `{state: 'exited', ..., exitCode}`. The URL is never logged because it can contain Xtream credentials.

## Embedded mpv (Windows)

### Why mpv.exe and not libmpv

The old Electron app loaded `libmpv-2.dll` through a native Node addon and passed the HWND through mpv's `wid` option (`embedded_mpv_win32.cc`). On Linux it ran `mpv --wid` out of process over JSON IPC (`embedded_mpv_wid_common.h`). Here the Windows build uses that out-of-process design too:

- A crash inside mpv or a GPU driver cannot take the app down.
- There is no FFI or DLL basename matching. The old app had to keep `libmpv-2.dll` under its exact import name.
- The installer stays small, because mpv is optional and drop-in.
- The whole protocol layer is plain async Rust and runs under `cargo test`.

### Window (HWND) approach

1. `iptv-tauri` registers `MpvWindowFactory` at boot through `iptv_core::player::set_window_factory(&state, Arc::new(MpvWindowFactory::new(handle)))`. This only happens in the desktop shell, so in server mode `player.capabilities` reports `embeddedMpv: false` with a reason.
2. `mpv.attach {bounds}` calls `factory.create(bounds)` from `spawn_blocking`. The factory marshals to the main thread with `AppHandle::run_on_main_thread` and gets the result back over a channel with a 5 s timeout. Tauri runs the closure inline when the caller already is the main thread, so this cannot deadlock. On the main thread the factory:
   - registers the window class `TsrustIptvMpvHost` once (black stock brush, arrow cursor);
   - calls `CreateWindowExW(WS_EX_NOPARENTNOTIFY, ..., WS_CHILD | WS_VISIBLE | WS_CLIPSIBLINGS | WS_CLIPCHILDREN, parent = main window HWND)`;
   - calls `SetWindowPos(HWND_TOP, SWP_NOACTIVATE | SWP_SHOWWINDOW)` so the window sits above the WebView2 child without taking focus.

   Its window procedure returns `HTTRANSPARENT` for `WM_NCHITTEST` and lets `DefWindowProc` paint the black brush.
3. Bounds arrive in CSS px relative to the webview, which fills the client area. The factory multiplies them by `window.scale_factor()`, rounds, and clamps width and height to at least 1.
4. mpv is started with the user's `mpvArgs` first, then the C4 flags, so the C4 flags always win. The exception is `--hwdec`: `--hwdec=auto-safe` is added only when `mpvArgs` has no `--hwdec`/`--no-hwdec` of its own, so a decoder the user picked is kept:
   `--wid=<hwnd> --input-ipc-server=\\.\pipe\tsrust-iptv-mpv-<our pid>-<session> --idle=yes --keep-open=yes --no-osc --no-input-default-bindings --force-window=yes --hwdec=auto-safe --input-vo-keyboard=no --no-terminal --volume=<last volume>`
   mpv creates its own video window inside ours, so moving or destroying our window moves or removes the video. The process runs with `CREATE_NO_WINDOW`, null stdio, and kill-on-drop. It is also assigned to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; the job handle is never closed, so Windows ends mpv when the app process dies, even after a crash or a Task Manager kill.
5. The video window is native and sits above the web content. HTML cannot draw on top of it, so player controls sit outside the reported bounds, and the UI cuts anything that floats over the video out of the window as holes (a window region, see Overlays over the video). The old app used a fixed dock for the same reason.

Verified on Windows 11 with a scratch Tauri app that hosts the real factory and plays a 60 s test clip encoded with mpv: the video covered the requested 640x360 CSS rect above the web content, followed `mpv.setBounds`, and disappeared on `mpv.detach`.

### Overlays over the video (UI)

`MpvSurface` (`src/features/player/components/MpvSurface.tsx`) measures its placeholder with `measureMpvLayout` (`src/features/player/mpvBounds.ts`) and sends `mpv.setBounds {bounds, holes}`:

- Reserved chrome inside the player host (`RESERVED_SELECTOR`: the controls and `data-mpv-reserved`) shrinks the docked video. The toast stack and `data-mpv-reserved-global` count as reserved too, wherever they are.
- Floating overlays anywhere in the document (`OVERLAY_SELECTOR`: the player's own `data-mpv-overlay` popovers, every `role="menu"`, `tooltip`, `dialog` and `alertdialog`, `aria-modal="true"`, `dialog[open]`) are holes: the video keeps its size and place and the DOM under the hole shows through. That includes the command palette and menus inside the player host, such as the Playback options menu and its subtitle, audio and sleep views. A menu laid out hidden for its first pass is skipped.
- A full-window scrim (`SCRIM_SELECTOR`, the backdrop of a modal dialog such as the command palette, a drawer or a sheet) cannot darken the native video, so mpv dims itself to match: `measureScrim` reads the topmost visible scrim's colour (in fullscreen and picture-in-picture only one inside that layer), and `dimOverlayCommand` sends an `osd-overlay` (id 63) that draws an ASS rectangle in that colour and alpha over the whole mpv window, or removes it when the scrim goes. The dim is sent only on change, and a new session starts without one. In fullscreen and picture-in-picture the video keeps the whole surface and all chrome over it, reserved included, becomes holes; chrome outside the fullscreen element is ignored, since it cannot be seen.
- The video is hidden (moved off screen to `HIDDEN_BOUNDS`) only when modal dialogs (`MODAL_SELECTOR`) cover at least `MODAL_HIDE_SHARE` (0.5) of it, or when nothing of the surface is visible. A smaller dialog is just a hole.
- It re-measures in the next frame on resize, scroll, fullscreen and DPR changes, when a `MutationObserver` on `document.body` sees a node matching `LAYOUT_WATCH_SELECTOR` come or go (or an `aria-modal`, `open`, `hidden` or `role` change), when the content of an overlay changes (a menu switching views, so its hole resizes), and on `animationend` or `transitionend` inside an overlay, so a popover is measured where it settles. A 400 ms poll covers moves without a resize.
- `VideoContextMenu` portals to the fullscreen element, else the open picture-in-picture layer (`[data-pip-layer]`), else `document.body`, at `z-[60]`. Inside the player it would stay in the stage's stacking context, under the page strips that follow it (the guide strip below the video).

### JSON IPC

The client is `ipc::MpvClient` and the wire format is newline-delimited JSON:

- request: `{"command": [...], "request_id": n}`
- reply: `{"request_id": n, "error": "success" | "<reason>", "data": ...}`
- event: `{"event": "...", ...}`

Behaviour:

- A reader task matches replies to callers by `request_id`, so callers may run concurrently. A reply that is not `success` becomes `Invalid("mpv rejected <cmd>: <reason>")`. No reply within 5 s becomes `Timeout`. When the pipe closes, every pending and future call fails with `Conflict("embedded mpv is not running...")`.
- After the connection opens, the client runs `observe_property` on ids 1..7: `pause`, `time-pos`, `duration`, `volume`, `mute`, `track-list`, `fullscreen`. `property-change` events go through `mpv_state::apply_property`; `track-list` becomes `MpvTrack[]` with blank lang and title set to `None`, and unknown track types dropped.
- `start-file` clears the error. `file-loaded` sets `loaded`. `end-file` with `reason: "error"` sets a user-facing error that includes mpv's `file_error`. `end-file` with `reason: "eof"` on a loaded item sets `mpv_state::LIVE_ENDED` ("The live stream stopped: the provider closed the connection."). Only a live item can end that way (it loads with `keep-open=no`; everything else pauses on its last frame), so the end is a dropped stream: `MpvSurface` reports it as a player error and recovery reconnects, then fails over ([failover.md](failover.md)). The end of a file that a new load just replaced is not reported, because the load clears `loaded` first.
- `mpv.state` events are throttled to 4/s: a leading emit, then a 250 ms cooldown, then a trailing emit, so the last state is always delivered. The emitter stops when the pipe closes.
- Connecting: `ClientOptions::new().open(pipe)` is retried every 50 ms for up to 5 s, treating `NotFound` and `ERROR_PIPE_BUSY` as "not yet". It fails early if mpv exits during startup. If a stale mpv of ours still owns the pipe name, it is asked to quit before the new process starts.

### Commands

- `mpv.attach {bounds, volume?, muted?}`: idempotent. With a live session it only moves the window. The optional volume (clamped to 0..100) and mute are passed as `--volume` and `--mute` and stored before mpv starts, so the first `mpv.state` already carries them.
- `mpv.load {source}`: sends `["loadfile", url, "replace", -1, {pause: "no", force-media-title, user-agent, referrer, http-header-fields: "Origin:<o>", start: "+<resumeSeconds>"}]` (`args::loadfile_options`). Every load sends `pause=no`: mpv's `pause` is global, so a user pause, or `keep-open` pausing at the end of an episode, would otherwise carry over to the next channel or the Up next episode. Live sources never seek; they add the timeshift cache options (`LIVE_TIMESHIFT_OPTIONS`: `cache`, `demuxer-seekable-cache`, `force-seekable` and `demuxer-max-back-bytes=256MiB`) and `keep-open: "no"`, so a live stream the provider drops ends instead of freezing on its last frame. They also cut FFmpeg's stream analysis short (`LIVE_PROBE_OPTIONS`: `demuxer-lavf-analyzeduration=2` and `fpsprobesize=0` in `demuxer-lavf-o`): with FFmpeg's defaults the lavf demuxer waits for codec parameters of every PID the panel lists, so a channel with a silent second audio track or a data PID held each zap for up to 7 s of stream. In the sandbox (mpv 0.37 over IPC, 1080p TS at 6 Mbit/s with a 2 s GOP, 150 ms first byte, a 2.5 s connect burst, 16 loads each) a channel with a second audio PID that goes silent started in a median 0.19 s instead of 4.2 s, and a plain channel stayed at 0.19 s; with a 1 s burst the silent-PID channel took 1.2 s instead of 5.7 s. `fpsprobesize=0` goes in as `demuxer-lavf-o-append`, which adds it to the user's list for that file; a per-file `demuxer-lavf-o` would replace the whole list. A per-file value replaces the global one for that file, so each option is left out when the user's configuration already sets it. Right after the observers are registered, `mpv.attach` reads mpv's global `demuxer-lavf-analyzeduration` and `demuxer-lavf-o` (`UserProbeOptions`), so `mpvArgs`, a `--profile` or `--include` in them and `mpv.conf` all count: an analyze duration other than mpv's default 0 keeps the user's, and an `fpsprobesize` entry in their list keeps theirs. It reads them once, while mpv is idle, because during playback mpv reports the per-file values. A value it can't read counts as set. The rewind buffer lives in mpv's memory, which is why it is capped: 256 MiB holds about 6 minutes of a 6 Mbit/s channel and about 1.5 minutes at 25 Mbit/s, and mpv drops the oldest data beyond that (the old 1 GiB cap let one channel grow mpv by about 45 MB a minute up to a gigabyte). If mpv older than 0.38 rejects the 5-argument form, the command is retried as `["loadfile", url, "replace", "k=%len%v,..."]`, where `%len%` quoting keeps commas safe.
- `mpv.command {cmd}`: passes a raw command through, but only from an allowlist (`ALLOWED_COMMANDS`): `seek` (what the player UI sends), the read-only `get_property` and `get_property_string`, `osd-overlay` for the dim under a scrim, and the property commands below. `osd-overlay` is accepted only as an id from 0 to 63, `ass-events` or `none`, one line of ASS of at most 512 bytes, and up to three integer sizes from 0 to 16384 (`validate_osd_overlay`). Any other first element is Invalid, including mpv's command prefixes (`no-osd`, the other `osd-*` prefixes, `raw`, `expand-properties`, `async`, `sync`, `repeatable`, `nonrepeatable`, `nonscalable`), `keybind`/`keypress`, `script-*`, `run`, `loadfile`, `dump-cache` and `screenshot-to-file`. Object or array arguments are rejected.
- `mpv.setProperty {name, value}`: `set_property`, limited to `SETTABLE_PROPERTIES` (pause, volume, mute, speed, aid, sid, vid, audio-delay, sub-delay, sub-visibility, time-pos, the subtitle style properties, and the picture controls video-aspect-override, keepaspect, panscan, video-zoom and deinterlace); any other name, such as `stream-record`, is Invalid. `mpv.command` applies the same allowlist to its property commands (`set`, `set_property`, `set_property_string`, `add`, `multiply`, `cycle`, `cycle-values`).
- `mpv.setBounds {bounds, holes?}`: `factory.set_bounds`, then `factory.set_holes`, which cuts the `holes` (rects inside `bounds`, relative to its top-left, CSS px) out of the window with `SetWindowRgn`; no holes restores the full window.
- `mpv.detach`: sends `quit`, waits 2 s, kills the process if it is still running, destroys the window, and emits a final `{attached: false}` state. It is idempotent.
- `mpv.record {start}`: sets mpv's `stream-record` property to `<dir>/<title>-YYYYMMDD-HHMM.ts` (characters invalid in Windows file names replaced with `_`, the title cut to 80 characters, `recording` when nothing is left, a ` (n)` suffix when the name is taken), or to `""` to stop. `<dir>` is `settings.recordingsDir`, else `<downloadsDir>/recordings`, and is created when missing. Returns `{recording, path}` and updates `MpvState.recording` and `recordPath`. Loading another source or detaching stops the recording. mpv copies packets without re-encoding and starts writing at the next keyframe.
- `mpv.state`: returns the live state, or the last detached state, which keeps volume, mute, and the last error.
- `mpv.stats`: the stream info snapshot (`player/stats.rs`). It reads `STATS_PROPERTIES` (video-format, width, height, estimated-vf-fps then container-fps, video-bitrate, audio-codec-name, audio-params/channel-count, audio-bitrate, hwdec-current, frame-drop-count + decoder-frame-drop-count, demuxer-cache-duration, file-format) with concurrent `get_property` calls under a 2 s timeout. A property mpv cannot answer is left out. `hwdecKnown` tells "software decoding" (`hwdec-current` is `no`) apart from "no answer". The stream URL is never part of the reply. Errors like the other commands without a session.
- Crash handling: a watcher notices when mpv exits or the pipe closes without a detach. It waits up to 1 s for the exit code, then sets `error: "mpv stopped unexpectedly (exit code N). Start playback again to restart it."`, tears the session down, destroys the window, and emits the result.
- On other OSes every `mpv.*` command returns `Unsupported`, and the external players still work.
- Server mode (`iptv-server`): `player.detect`, `settings.detectPlayers`, `player.openExternal`, `player.stopExternal` and every `mpv.*` command return `Unsupported` ("Players run only in the desktop app"), because a browser client must not start processes on the server or learn its player paths. `player.capabilities` still answers. The browser UI therefore offers only the built-in player: Settings > Playback lists neither MPV nor VLC, there is no External players section, and a saved `mpv` or `vlc` (for example from a desktop backup) plays in the built-in player.
- App exit: call `player::shutdown(&state).await` (graceful) or `player::kill_embedded(&state)` (synchronous) from the Tauri exit hook, so mpv never outlives the app.

## Dropping mpv into vendor/mpv

1. Download a Windows x86_64 build from shinchiro's mpv-winbuild-cmake releases (<https://github.com/shinchiro/mpv-winbuild-cmake/releases>), for example `mpv-x86_64-v3-<date>-git-<hash>.7z`. Use the `x86_64` build instead of `-v3` on CPUs without AVX2. Do not use the `mpv-dev-*` archive, which is libmpv for developers.
2. Extract it so that `mpv.exe` sits directly in `vendor/mpv/`, next to the DLLs and folders shipped with it (`d3dcompiler_43.dll`, `vulkan-1.dll` where present, `mpv.com`, `doc/`). Keep the files together, because mpv loads its DLLs from its own folder and the process starts with that folder as its working directory.

   ```
   vendor/mpv/
     mpv.exe
     mpv.com
     d3dcompiler_43.dll
     ...
   ```
3. Everything in `vendor/mpv/` is gitignored except `LICENSE.txt`, the GPL licence and source notice that ships beside `mpv.exe`. That file names one specific build (mpv version and commit, FFmpeg commit, libplacebo version), so when you swap in a different build, update those lines to match it and keep the source links pointing at the same commits. `pnpm tauri:build:mpv` merges `crates/iptv-tauri/tauri.mpv.conf.json`, which bundles the whole folder, notice included, as resources beside the installed exe.
4. Check it: Settings > Players should show the detected path, and `player.capabilities` should return `embeddedMpv: true` in the desktop app.

A system mpv works too (WinGet, scoop, choco, or `PATH`), and so does a path set in Settings > Players.

## Built-in engines (UI)

Code: `src/features/player/engines.ts` (`createEngine`), used by `components/InlinePlayer.tsx` and by each multi-view tile (`src/features/multiview/useTilePlayback.ts`). Tests: `engines.test.ts`, `components/InlinePlayerHold.test.tsx`, `src/features/multiview/test/tilePlayback.test.tsx`, `src/features/multiview/test/tileReconnect.test.tsx`.

- Choice: hls.js for `hls`, Shaka for `dash`, mpegts.js for a `direct` or `file` URL that says MPEG-TS (`.ts`, `?output=ts`) when Media Source Extensions exist, and the `<video>` element for the rest.
- Extensionless live TV: a live, non-radio stream whose URL names no container (`/live/u/p/123`, `isUnlabelledLive`) starts in mpegts.js, because most of them are raw MPEG-TS and Chromium's element can't play it. Before, the element went first and downloaded until its probe gave up, which cost 0.3-5 s and a second connection on every zap. If mpegts.js reports a format error before any media plays, the element gets the stream once instead (`Engine.fellBack`, so an element error then gets no second mpegts.js try). The first media of either path is remembered per source and host in localStorage `player.liveFormats` (`{"<sourceId>|<host>": "ts" | "native"}`, the 200 most recent hosts). A host remembered as `native` starts in the element; when the element then rejects a stream, the player and the tile retry it through mpegts.js (`forceMpegts`), and media there marks the host `ts` again. Radio stays on the element first.
- hls.js transmuxes in a Web Worker. Its ESM build only starts one from a script URL, so `engines.ts` imports `hls.js/dist/hls.worker.js?url` and passes it as `workerPath` (both CSPs allow `worker-src 'self'`). All hls.js players share that worker.
- hls.js loads segments progressively (`progressive: true`): its fetch loader hands each segment to the transmuxer in 128 KB chunks as it downloads, so a live tune shows its first frame after the segment's first GOP instead of after the whole segment (6-10 s of video on many Xtream panels). The fetch loader never calls `xhrSetup`, so the proxy rewrite (`proxyRewrite`) is applied in `fetchSetup` as well; `xhrSetup` stays for browsers without fetch streams, where hls.js keeps XHR. In a sandbox panel emulation (6 s segments sent at 20 Mbit/s, 150 ms first byte) the median HLS zap fell from 2.47 s to 0.81 s.
- hls.js bandwidth: each zap builds a new `Hls`. The main player's last `bandwidthEstimate` becomes the next instance's `abrEwmaDefaultEstimate`, so multi-rendition streams don't start from hls.js's 500 kbps default. Tiles read it but don't write theirs back, since four tiles split the link.
- Multi-view tiles use the `tile` profile (`createEngine(..., {profile: 'tile'})`): mpegts.js cleans up the buffer behind the playhead at 10 s, down to 5 s (the main player keeps 30-60 s), and hls.js uses `backBufferLength: 5`, `maxBufferLength: 10` and `capLevelToPlayerSize: true`. A tile can't seek, so the main player's back buffer only held memory. A tile leaves the `ended` of a live MPEG-TS stream to mpegts.js's reconnect, as the main player does, and fails only when the engine reports (multiview.md).
- Shaka's `destroy()` is async and clears the element's `src` when it is done. The next engine on that element waits for it, at most `SHAKA_TEARDOWN_WAIT_MS` (300 ms), so Shaka can't empty the element under the new engine.
- mpegts.js 1.8.2 is patched through `pnpm.patchedDependencies`. The committed `patches/mpegts.js@1.8.2.patch` changes both the package source and `dist/mpegts.js`, which is the bundle the app actually loads. Its finite MPEG-TS archive path preserves the supplied programme duration, supports byte-range seeking, and feeds the worker in bounded chunks so pause messages can interrupt a fast or cached response. Seek estimates use observed TS byte positions; corrections use the closest positions on either side of the target to avoid oscillation, and a short undershoot scans forward on the same response instead of opening another provider connection. After a range jump, the transmuxer waits for a video keyframe before appending media to a fresh decoder. Live streams do not use the archive chunking path. The patch also revokes the worker blob URL on destroy. `node tools/prepare-mpegts.mjs` clones upstream at `vendor/mpegts.js` (gitignored) and applies the committed patch for development. After editing that checkout, rebuild its bundle, regenerate the source and bundle hunks in the patch, update the patch hash in `pnpm-lock.yaml`, and reinstall so `node_modules/mpegts.js/dist/mpegts.js` matches. Vite includes the patch hash in its optimized dependency cache key, preventing WebKit from retaining an older development bundle. When upgrading mpegts.js, rebase the fork changes and regenerate the patch against the new package version.
- Catch-up sources carry `catchupProgramStart`. Each committed seek in an Xtream `/timeshift/` archive opens a new request starting at the target minute, keeping the provider's duration field intact as observed in TiviMate, and begins playback at that minute boundary. The seek bar reports the minute reached. The player sets its own expected duration to the remaining programme time. Catch-up disables the adaptive MPEG-TS stash, which otherwise holds up to 8 MiB and can starve a short opening buffer before the next chunk reaches the decoder. The original provider timestamp is shifted by whole minutes so its server clock convention is preserved; the element clock is offset back to the programme timeline. Other archive URL formats retain the byte-range seek path. For catch-up, `engines.ts` sets the patched MPEG-TS archive chunk gap to 45 s and limits a forward seek scan to a 30 s timestamp undershoot; larger misses open a corrected byte range. If a provider resets its TS clock within an archive, seek validation reuses the estimated byte range and anchors its MP4 timestamps near the requested programme position instead of correcting toward EOF. The player waits 150 s for the first frame, and reconnect waits 60 s without position movement before retrying. MPEG-TS reports incoming archive bytes through `STATISTICS_INFO`; while they keep arriving, reconnect treats a seek scan as progress even if no new frame is buffered yet. When video sample timestamps reveal a gap, the player seeks to the next buffered keyframe as playback reaches its start. A second check skips to a future buffered keyframe when the catch-up playback clock advances at least 1.5 s over 2 s without decoding video, including when corrupt inter frames leave a frozen image without a timestamp hole. Each catch-up retry gets 150 s to start, within a 180 s recovery window. These limits do not apply to ordinary live or VOD playback. In development, the MPEG-TS archive trace and player recovery decisions go to `scratch/timeshift-debug.log` through a local Vite endpoint; stream URLs are not recorded.
- Loads: the inline player builds an engine per media (`kind` and URL), per play and per Retry, and embedded mpv sends `mpv.load` on the same three. "Per play" is the store's `playGeneration`, which `play()` raises each time it commits a source. A play of the URL already playing therefore loads it again: Start over on the movie playing (Xtream answers the same link) starts from 0 instead of carrying on where it was, and a recovery that resolves the same link reloads it. Updates that only describe the item (a channel's new name, the programme now airing) set `source` without a play, so they never reload the stream.
- Control bar renders: `Controls` doesn't subscribe to the position, buffer or live window. The seek bar, the VOD time and the live-edge readout (`PositionSeekBar`, `TimeReadout`, `LiveEdge`) subscribe on their own through `useWhileShown`, which stops following the stores while the overlay is hidden and reads the current value when it shows again. `Controls` and `InlinePlayer` are memoized, and the stall dial (`LoadingDial` in `PlayerSurface.tsx`) follows the media store's `waiting` itself, so a live stream that stalls and resumes at its edge, the pointer resting on the bar and the chrome's idle timer re-render neither the bar nor the media element (P2-PLAYER-3). The bar's icons are made once (`ICON`), so a render of the bar does not build them again (P2-PLAYER-4). A narrow bar measures the room for its spare buttons in its row's ResizeObserver callback, after layout; a render asks for one by observing the row again, where a read in the next frame forced that layout itself (P2-PLAYER-1). The position comes from the element's `timeupdate` (and `durationchange`); its `progress` events only refresh the buffered ranges (P2-PLAYER-2). `reportProgress` returns early when the position and duration haven't changed, which mpv state events often repeat. Store subscribers that follow the item (smart reconnect, the startup and stall watchdog, the watch-stats reporter, the sync offsets, the zap banner and the live programme) return early on a progress update instead of building item keys several times a second (P2-PLAYER-6). With embedded mpv, `MpvSurface` keeps the tracks object when an `mpv.state` event lists the same tracks, and builds its `Intl.DisplayNames` once.

## Seeking in MPEG-TS (UI)

Code: `src/features/player/tsSeek.ts` (`tsSeekerFor`), used by `mpegtsEngine` in `engines.ts` through `createEngine(..., {seeker})`. Tests: `tsSeek.test.ts`, `engines.test.ts`.

- mpegts.js can't seek in MPEG-TS (its README; `TransmuxingController.seek` does nothing without a keyframe index, which only FLV gets) and reports no duration. A seek past what the element held made it wait while mpegts.js loaded everything before the target, a resume started at 0 and did the same, and past 12 s the stall rule reloaded from 0. Recordings, downloads, catch-up and TS movies all play there. Embedded mpv seeks in TS itself and is unaffected.
- A non-live MPEG-TS source gets a `TsSeeker`. On a seek outside the buffered range (`Engine.seek`), on a resume (`Engine.resumes`: the engine starts there, so InlinePlayer's `loadedmetadata` resume leaves it alone) and when the connection drops (it comes back where it was, no longer at 0), the engine tears its pipeline down first, so a one-connection account has the stream free before the next request, asks the seeker where to start, loads that in a new mpegts.js player and, once it has metadata, seeks the seconds left inside it. Until then `timeOffset()` holds the shown position at the target; afterwards it is the item time the new stream starts at, the same rebasing a live reconnect uses. A seek inside the buffer stays the element's own. A seek while a restart resolves replaces it, and a paused player stays paused. A pause or play while the seeker is still answering goes to the engine (`Engine.setPaused`, from InlinePlayer's controller): the torn-down element reads as paused and fires no `pause`, and attaching the new stream would undo a `play()`, so the engine applies it when the new stream is attached and the status follows at once.
- Xtream catch-up (`PlayerSource.catchup`, set by `catchupSource`): the archive link again from the target's whole minute, `xtream.catchupUrl` with the programme's start plus floor(T/60) minutes and the minutes left, never past the last minute that aired. The panel starts archives on whole minutes, so less than a minute is left to seek.
- Recordings and downloads (the app's `/api/recordings` and `/api/files` routes, on desktop the loopback proxy's): the byte where the target is, from the PTS. The seeker reads the first, last and middle 128 KB up front (packet size 188 or 192, the first video PID and its first and last PTS, which give the length; the middle's PTS must lie between a fifth and four fifths of that length, since the recorder joins a reconnect's part to the one before and a stream whose clock restarted there gives a last PTS unrelated to the first, a length of up to 26.5 h), then searches with 128 KB Range probes, at most 12, each guess interpolated between the two closest known points (secant on the last two), until it is within a second before the target. It loads the same URL with `?from=<byte>` (server.md). A recording can be played while it is still being written: when the length is read or a seek needs it, at most every 10 s (`GROW_CHECK_MS`), the seeker asks for one byte to learn the file's size, and reads the end again when it grew. Without that the length would stay where it was when playback started, and playback that went on past it would read as ended.
- A remote file through the proxy (TS movies, and Stalker and M3U catch-up, whose links can't be asked for from a later minute: Stalker's `create_link` names a whole programme): the same search with at most 3 probes, to within 3 s. It learns the file only at the first seek or resume, never while the stream plays, which would be a second connection to the provider. The proxy refuses a 200 to a `from` request (502).
- A probe answered with the whole file (200: no byte ranges) or with a part that doesn't give the file's size (`Content-Range: bytes a-b/*`, a stream still going), bytes that aren't MPEG-TS, or a file with no length (no PES in its last 128 KB, or a middle that doesn't fit) end seeking by restart for that item: from then on its seeks are the element's own, as before. A local file learns this at the start; a remote one at its first seek or resume, which has already torn the pipeline down, so that one loads from 0 and seeks there. Any other failed probe (a refused request, a network error) leaves the item seekable, but the pipeline that seek tore down is gone: the engine reports a fatal network error, the smart reconnect (`reconnect.ts`) reloads the item at the position it dropped at, and when its retries give up the error shows.
- mpegts.js loads non-live MPEG-TS lazily (`lazyLoadMaxDuration` 60 s): it lets go of the request once it holds 60 s ahead and asks for the rest with a Range after 30 s of playback. The engine asks the proxy to park the reader in between (`park=1` on its non-live proxied loads, restarts at a seek included; live streams, the seeker's probes and failure-reason requests go without), so that resume reuses the provider's connection (server.md, `/api/proxy`). The engine's `destroy()` sends `release=1` for a proxied URL so a stopped player frees it at once, and so does a `pagehide` while it plays, since React unmounts nothing when a tab closes or reloads; both go with `keepalive`, so a navigation does not cancel them. Turning lazy loading off is no alternative: mpegts.js then loads until the SourceBuffer is full, about 150 MB in Chromium, and suspends on BUFFER_FULL without the listener that resumes it, so playback stalls.
- Length: `PlayerSource.durationSeconds` (catch-up: the programme's length, set by `catchupSource` only for an archive that ends with the programme: Xtream, Stalker, and the M3U forms `m3uCatchupEnds` accepts; `shift`, a template without an end and Flussonic's MPEG-TS form play on into the following programmes, and a fixed length would read as their end) or, for a file, its last PTS, through `Engine.duration()`. InlinePlayer reports it instead of the element's, which after a restart covers only the new stream. A remote TS movie has no length until its first seek or resume.
- Measured on `tsSeek.test.ts`'s 30-minute virtual file (60 MB, the bitrate doubling halfway), seeking to minute 10, 20, 25 and 29.8: a local file took its 3 up-front reads and 2-3 probes (0.52-0.66 MB) and started 0.4-0.7 s before the target; a remote one with a known length took 1 head read and 2-3 probes (0.39-0.52 MB) and started 1.3-1.8 s before it. The old path read the 13-60 MB before the target first; at 3 Mbit/s, 20 minutes in, that is about 450 MB. In headless Chrome on a 10-minute 720p recording (3 Mbit/s, served by a release `iptv-server` from `/api/recordings`), the seek bar showed 599 s, each pointer seek (to 60, 300, 359 and 510 s) made one probe and one `from` request (measured before the size check for recordings being written, which adds a one-byte request at most every 10 s) and played at the target about 0.1 s after the click, and a resume at 6:00 after a reload played there 0.4-1 s after the reload. The master build, given the same restore record, started at 0:00: its `loadedmetadata` resume never applied.

## Sync, stream info and channel history (UI)

Code: `src/features/player/` (`sync.ts`, `textDelay.ts`, `streamInfo.ts`, `inlineExtras.ts`, `mpvExtras.ts`, `history.ts`, and `components/SyncMenu.tsx`, `StreamInfoPanel.tsx`, `ChannelHistory.tsx`).

- Delays: `useSyncStore` holds `audioMs` and `subMs` (100 ms steps, clamped to +/-10 s). Both go back to zero when the item (its catalog ref, or the URL for ref-less sources) or episode changes; a reconnect that swaps in a fresh Stalker link keeps them. With embedded mpv, `mpvExtras.ts` writes them as `audio-delay` / `sub-delay` (seconds) through `mpv.setProperty`, and again after each attach. Built-in engines (hls.js, Shaka, mpegts.js, native) have no audio delay, so that row is disabled with the reason as its tooltip and the shortcut shows it in the OSD. Subtitle delay shifts the cue times of the showing or hidden text tracks (`textDelay.ts`). Original times live in a WeakMap, so stepping never accumulates error, and cues added later (live WebVTT) are shifted by a 500 ms recheck that only runs while the delay is non-zero. A positive delay shows subtitles later, as in mpv.
- Stream info: `useStreamInfoStore.open` gates everything. The open panel polls the registered stats provider once a second; closed, there is no timer and no RPC. Embedded mpv provides `mpv.stats`; the inline player merges the engine's own numbers (hls.js level, Shaka variant and stats, mpegts.js media info) with the video element's size, dropped frames and buffer ahead. The panel shows the URL host only (no path, query, user or password), or "Local file" for file paths. Over embedded mpv the panel carries `data-mpv-overlay` and `data-mpv-reserved`, so the native window is cut around it, and opening or closing it remeasures the mpv layout.
- History: `history.ts` records each live source that has a catalog ref (live TV and radio, never VOD) when it starts, newest first, deduplicated, capped at 10, in memory only. B plays the most recent entry that is not the current channel. A failover hop or pin redirect replaces the channel's entry instead of adding one. The popover and the stream info panel close when playback stops or turns to radio, and Shift+B and I do nothing in radio mode, which shows neither. The popover (Shift+B or the history button) fetches now/next for the listed refs once per list, with `settings.epgOffsetMinutes`.
- Picture: the player menu's Picture view (`picture.ts`, `Controls.tsx`) sets the aspect ratio (Original, 16:9, 4:3, Stretch), zoom or crop (None, Crop to fill, 110 %, 125 %, 150 %) and, with embedded mpv only, deinterlacing (browsers decide that themselves). The choice is global, not per channel: it describes the screen and how the person likes to watch, so it carries from channel to channel and across restarts (localStorage `player.picture`) until Original and None set it back. The built-in player applies it with CSS on the `<video>` (`pictureStyle`): a forced aspect is the largest box of that shape in the frame, sized from container units (`containerType: size` on the frame) with the picture stretched into it, or with crop the smallest box that covers the frame; Stretch is `object-fit: fill`, crop alone `object-fit: cover`, zoom a centred `scale()`. Embedded mpv gets `video-aspect-override` (`-1` for the stream's own), `keepaspect` (`no` for Stretch), `panscan` (1 for crop), `video-zoom` (log2 of the factor) and `deinterlace`, all of them on each change and after each attach (`mpvExtras.ts`), so going back to the defaults resets mpv too.
- Previous episode: Shift+P calls the queue's `prev()`. The series page offers the previous episode by `previousEpisode()` in `vod/lib/merge.ts`, which never crosses between specials and regular seasons.

## Playback keys (UI)

`usePlaybackShortcuts` (registered once by `PlayerDock`) binds the playback keys while something plays in the app. Space, the arrows (with and without Shift) and Page Up/Down are also how a page scrolls and how radio groups, lists and tabs move, so they carry `when: playerOwnsPageKeys`: they drive the player only when it is expanded (a page's `PlayerStage`, `dock === 'stage'`), fullscreen, in picture-in-picture, or when focus is inside it (`[data-player-mini]`, the mini frame; `[data-player-host]`; `[data-pip-layer]`). With only the mini dock showing and focus on the page, the registry skips them and the key keeps its default. Letter keys (K, M, F, J, L and the rest) and the media keys stay app-wide.

Step seeks are coalesced (`seekBy`, and `seekTo` with `step`: the arrows, J/L, the skip buttons, a double tap, the remote's seek and the seek bar's arrow and Page keys). A held key repeats about 30 times a second, and each seek past what the surface holds is a request to the provider: a new Range request for a native MP4, a new fragment for hls.js, a restart for MPEG-TS (Seeking in MPEG-TS). A step whose target the surface holds (`PlaybackController.holds`: the element's buffered ranges, mpv's demuxer cache) goes out at once. Any other waits in the store's `pendingSeek` and goes out when the key comes up or after `SEEK_SETTLE_MS` (250 ms) without another step; a direct seek (pointer release, Home, End, Jump to live), a play or a stop replaces it. The position and the OSD show the pending target, `reportProgress` keeps it until the seek goes out (the element's time would pull it back, and the next step would count from there), and each step moves the position, so the stall rule never sees a pending seek as a stall. A two-second hold of the right arrow past the buffer is one seek instead of 60 (`store.test.ts`).

## Sleep timer, zap banner and glass (UI, C5)

Code: `src/features/player/` (`sleepTimer.ts`, `sleepReadout.ts`, `zapBanner.ts`, `nowNext.ts`, `parentalHook.ts`, `parentalGuard.ts`, `parentalLocks.ts`, `player.css`, and `components/SleepTimer.tsx`, `ZapBanner.tsx`, `zapHooks.ts`).

- Sleep timer: `sleepTimer.ts` is a zustand store `{target, endsAt, fading}` plus extras `{warning, resolving}`. `target` is `minutes`, `programmeEnd` (the airing programme's end, looked up through `nowNext.ts`) or `episodeEnd` (the remaining duration divided by the playback speed). One `setTimeout` clock wakes for the warning (T-60 s) and the fade (T-30 s); each fade step calls `usePlayerStore.setVolume(base * remaining / span)`. `subscribeVolumeIntent` in `store.ts` tells a person's volume or mute change apart from the fade's own. A person changing the level during the fade takes the volume over: the ramp stops there and nothing is restored. A mute during the fade only silences it: the ramp holds while muted (an unmute carries on from the faded level), and the earlier level returns at the end or on Cancel with the mute kept. Expiry stops live TV, or pauses VOD and cancels Up next, then restores the base volume and toasts. Stopping playback or switching to an external player cancels the timer; an episode timer turns off when live TV replaces the item. Minute timers count wall-clock time even while paused, like a TV's; an episode timer recomputes its end from position and speed, so while paused it does not expire.
- `Z` cycles off, 15, 30, 45, 60, 90 minutes, off (`cycleSleepTimer`). From a programme or episode end, or from a countdown made by Keep watching or a zap off another timer, the next press turns the timer off. The readout after a change (`announceSleep`, `sleepTargetLabel`, `sleepLeftText`) lives in `sleepReadout.ts`, so the shortcut works without loading the timer's UI.
- Sleep UI (`components/SleepTimer.tsx`): `SleepChip` (the countdown in the control bar), `SleepMenu` and `SleepRowValue` (the options menu's submenu and row), `SleepTimerHost` (mounted once by `PlayerDock`; raises the one-minute toast with Keep watching and Cancel) and `SleepPrompt` (fullscreen and picture-in-picture only, where the top layer hides toasts).
- Zap banner: `zapBanner.ts` shows it for `ZAP_BANNER_MS` (5 s) on each live channel change. Radio, VOD and external playback are excluded, and `settings.zapBanner` (Settings > Playback) turns it off. `holdZapBanner` counts hovers on the channel title and on the banner; it lingers `ZAP_HOVER_GRACE_MS` (600 ms) after the pointer leaves. A hover hold also ends when its element stops being hoverable (`useZapHover(active)` turning false, or an unmount), since no pointerleave arrives then, and any hold ends `ZAP_HOLD_MAX_MS` (30 s) after the last pointer enter, so a lost leave cannot pin the banner. The channel number and logo come from `catalog.item`, cached for the session; now and next come from `epg.nowNext` with a 60 s cache in `nowNext.ts`, which the sleep menu shares. The live programme follower (`bindLiveProgramme`, which keeps a channel's subtitle on what airs) reads that cache every 30 s but keeps an answer past the 60 s while a programme in it still airs, or its next has yet to start, so a channel left playing asks once per programme; a guide with nothing for the channel is asked again every `LIVE_PROGRAMME_IDLE_MS` (5 min). The request goes through the shared query cache under the Live page's key (`rpcKey('epg.nowNext', {refs: [ref]})`), and a current answer another view already holds there (the Live list's pages) is used without asking. In a zap burst only the channel the burst stops on is asked, once it stays on screen `ZAP_SETTLE_MS` (250 ms); the channels it passes ask nothing. A player under 360 px tall (`SHORT_PLAYER_PX`), whatever its width, shows the one-line chip instead: logo, number, name and what airs now, with its progress. On the Live page's stage beside the list (586x330 at 1440x900) the full banner covered about a third of the picture and repeated the guide ribbon right below it; there the chip sits in the title's corner, as wide as its line, and the bar stays up. A player both short and under 480 px wide (a phone's dock) spans the chip across its top and keeps the bar down while the chip is up. Fullscreen and stages taller than that keep the full banner, PiP the two-line one. Over embedded mpv the banner carries `data-mpv-overlay`, so the native video is cut out under it, and the title bar dims while it is up. `useZapHover` and `useZapBannerShown` live in `components/zapHooks.ts` for the surfaces and the dock.
- Loading: `ZapBanner` and the five sleep components load through `lazyPart` (`components/lazyParts.tsx`) like the other on-demand player parts, outside the main chunk. The first player part that mounts preloads them at idle time, so they render at once when needed.
- Glass: `player-glass`, `player-glass-strong`, `player-glass-edge`, `player-on-glass-muted`, `player-scrim-top`, `player-scrim-bottom` and `player-sleep-fading` in `player.css` read the C8 glass and scrim tokens (with fallbacks) and keep animation behind the reduced-motion checks.
- Parental gate: `parentalHook.ts` `ensurePlaybackAllowed({ref, title, categoryId?})` is the one gate point. With controls off or an unlock running it lets the item through. In Ask mode it calls `ensureUnlocked` from `src/features/parental/gate.ts` (PIN prompt; see `parental.md`). In Hide mode it refuses an item the core hides, without a prompt, and `parentalLocks.ts` `notifyPlaybackHidden` drops it from the B history and the resume record and shows a toast saying why. `store.ts` `passGate` calls it before anything about the item shows and remembers the last allowed ref, so resuming or reloading the same item does not ask again. Callers pass `categoryId` when they know it (the live list, search, and the movie and series pages), so a locked category is checked without another lookup. `parentalGuard.ts` (bound by `PlayerDock`) forgets that pass on `parental.changed` with controls locked, and re-checks what is playing: Ask pauses and asks for the PIN (cancel stops), Hide stops. A zap whose neighbour is refused steps on in the same direction, skipping further locked channels without another prompt (`ZAP_SKIP_LIMIT` 50). In Ask mode a zap onto a locked channel shows its number and name behind the PIN prompt, with a lock on the tuner OSD and, on the banner, a lock in place of the logo and "Locked" in place of the guide, which is not asked until the PIN lets the channel play (`isLockedZap`). Hide mode never names it. A channel tuned any other way shows its tuner OSD only after the gate passes. A core `not_found` saying "locked by parental controls" shows the parental copy, not "stream no longer exists".
