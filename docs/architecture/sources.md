# Sources

Code: `crates/iptv-core/src/sources/`. Tests: `crates/iptv-core/tests/sources_crud.rs`, `sources_lifecycle.rs`, `sources_epg.rs`, `sources_last_error.rs`, `l2_import_dup.rs` (duplicate addresses), `l3_import_events.rs` (saving steps, `sources.changed` reasons, the short connect timeout) plus unit tests in `mod.rs`.

A source is one playlist provider: an m3u playlist (URL, file or pasted text), an Xtream account or a Stalker portal. Rows live in `sources` (C3). Kind-specific settings are in `config_json`, and EPG links are in `epg_json`.

## Layout

| File | Role |
| --- | --- |
| `mod.rs` | Importer registry and progress (A1), arg types, validation, the service functions (`list`, `get`, `add`, `update`, `remove`, `remove_all`, `reorder`, `refresh`, `refresh_all`, `counts`, `run_import`) and `init`. |
| `store.rs` | SQL for `sources`: `SourceConfig`, `list`, `find`, `get`, `insert`, `record_import`, `move_to`, `reorder`, `delete`. |
| `rpc.rs` | Every `sources.*` command in C4. |

## Importers

Each kind registers an `Importer` from its module `init`:

```rust
sources::register_importer(&state, Arc::new(MyImporter));
```

m3u registers in `m3u::init`, xtream in B3's init and stalker in B4's init. An importer only builds the catalog. It may emit `import.progress` phases `fetching`, `parsing` and `saving` through `sources::progress` (row counts at most every 2000 rows and every 250 ms through `sources::ProgressGate`, plus the final count), and the two long stretches of a save through `sources::progress_step`: `{phase: "saving", step: "replacing", done: 0}` with no total before the writer deletes the previous catalog (only when the source already has rows), and `{phase: "saving", step: "indexing"}` with `done` and `total` both the rows written, once every row is in and before the writer rebuilds the indexes, the search index and the counts. The Sources progress view (`ImportProgressView`) and the shell's import toast (`importPhaseLabel` and `importProgressText` in `src/shell/effects.ts`) show these steps as "Replacing the old catalog" and "Building the search index", with no counts and an indeterminate bar (`progressFraction` gives no fraction for a step, so the dashboard card's bar is indeterminate too). A `saving` event without `step` shows "Saving" with its counts. It does not touch `last_refresh_at` or `last_error` and does not emit `connecting`, `done`, `error` or `sources.changed`. `run_import` does all of that. An importer that kept the catalog because the source had not changed (the m3u sha256 shortcut, see m3u.md, or the Xtream and Stalker fingerprints, see xtream.md and stalker.md) sets `ImportSummary.unchanged`. An importer that kept the previous rows of one content type because it could not load them calls `sources::note_import_warning(message, code)`; the run still succeeds.

`run_import(state, id)`:

1. Takes a per-source async lock, so concurrent refreshes and a remove of the same source run one after another.
2. Emits `import.progress {phase: "connecting", done: 0}` (`sources::progress_connecting`), then calls the importer. Every run opens with this event, before its first request, so a client shows "Connecting to <host>" with the seconds waited until the first `fetching` progress arrives. `run_import_with` emits it too.
3. On success it sets `last_refresh_at`, clears `last_error`, refreshes `source_counts` (for stalker, the movie and series totals come from the importer's `ImportSummary`; see Counts), and then stores the run's first `note_import_warning`, if any, as `last_error`, `last_error_code` and `last_error_at` in the same database call, so a source whose movies kept their previous rows says so instead of looking fully refreshed. It then releases the per-source lock and applies user state a backup import parked for this source (`backup::apply_pending_restore`, so restored favorites and positions appear right away rather than on the next start; a failure there is logged and never fails the refresh). The global backup import lock is only taken when a `backup_pending:<id>` row exists, so adding or refreshing an unrelated source never waits behind a running `backup.import`, and that lock is never acquired while a source lock is held, and emits `import.progress {phase: "done"}` and `sources.changed {sourceId, reason: "catalog"}`. When the summary is `unchanged` it emits `import.progress {phase: "done", message: "unchanged"}` (`sources::UNCHANGED_MESSAGE`) and no `sources.changed` (unless a parked backup was applied): only the source's import time moved, so clients refetch `sources.*` and keep their catalog, list and guide queries (`invalidationPrefixes` in `src/api/query.ts`). The scheduled refresh skips its extra `sources.changed` for such a run too. It then starts the source's guides in the background (see Guides after import).
4. On failure it stores the error text in `last_error` and its classified code in `last_error_code` (C10; returned as `lastErrorCode`), and emits `import.progress {phase: "error", message, code}` and `sources.changed {sourceId, reason: "status"}`. The UI (`src/features/sources/lib/sourceError.ts`) classifies by `lastErrorCode` first; the text only refines that (refused or DNS for a network code, a host to name) and is matched by pattern only for rows stored without a code. It shows a translated message and keeps the raw text in a details disclosure.
5. On a cancel (`sources.cancelImport`, a remove, or a settings change; C8) it emits `import.progress {phase: "cancelled"}` and `sources.changed {sourceId, reason: "status"}`, keeps the previous catalog and records no `last_error`. The importer must leave the previous catalog in place, and both catalog write paths do (see catalog.md).

`sources.changed` carries `{sourceId?, reason}` (`sources::emit_changed`). `sourceId` is left out when the change spans every source. The reasons:

- `added`: `sources.add` inserted the row, before its first import. The source has no catalog yet.
- `catalog`: the source's catalog, or the user state tied to it, was rewritten: a successful `run_import` (or an unchanged one that applied parked backup state), a successful subset `xtream.sync`, and `backup.import` (once at the end of the call and after a `replace` that rolled back, both without `sourceId`; after each background load, with it).
- `config`: `sources.update` (with `sourceId`) and `sources.reorder` (without).
- `removed`: `sources.remove` (with `sourceId`) and `sources.removeAll` (without).
- `status`: only the import status moved and the catalog is as it was: a failed or cancelled run, a failed subset `xtream.sync`, and the scheduler's extra event after a scheduled run.

`invalidationPrefixes` in `src/api/query.ts` refetches only `sources.` queries for `added` and `status`, and skips the shell's extra prefixes (`EVENT_INVALIDATION` in `src/shell/effects.ts`) for them too. `catalog`, `config`, `removed` and a payload without a reason refetch `catalog.`, `sources.` and `lists.` plus those extra prefixes.

### Guides after import

A successful `run_import` takes the source's guide URLs (`sources::guide_urls`: `detectedUrls` then `manualUrls`, trimmed, blanks and `disabledUrls` dropped, first occurrence kept) and, in a spawned task, calls `epg::spawn_refresh` for each one that needs data. A URL is skipped when its `epg_sources` row is switched off globally (`epg.setEnabled false`) or has status `ok` with a `last_fetch_at` younger than `epg::ingest::STALE_AFTER` (12 h). Never-fetched, failed and stale URLs are queued. This covers every way a source gets imported (`sources.add`, `sources.refresh`, `refreshAll`, the startup auto-refresh, `backup.import`, deep links), so a new source has a guide without waiting for the EPG scheduler or a UI call.

The import never waits for or fails on a guide. Fetch errors land in `epg_sources.error` and the log, with the URL passed through `epg::fetch::log_url`, which redacts credentials (Xtream `xmltv.php` URLs carry the password). A URL that is already refreshing, from the UI's `epg.refresh` or the scheduler, is coalesced by the EPG runtime: `spawn_refresh` returns false and nothing extra runs.

`run_import_with(state, id, fut)` runs any future under the same per-source lock. A partial sync (for example `xtream.sync` with a `contentTypes` subset) uses it so it never interleaves with a full refresh of that source. The lock is not reentrant: the future must not call `run_import` or `remove` for the same source.

## add

`sources.add` checks the arguments before anything is written:

- m3u URL: `http`, `https` or `file`.
- m3u file: must exist.
- m3u text: must not be blank.
- Xtream: the server URL loses a trailing `/` and a pasted `/player_api.php`, `/get.php` or `/panel_api.php`; username and password are required. Optional `headers` (User-Agent, Referer, Origin) are trimmed; the client sends them with every `player_api.php` request, and without a User-Agent it sends VLC's (xtream.md). The add and edit forms show them under Request headers, as for M3U and Stalker.
- Stalker: the MAC is normalized to `AA:BB:CC:DD:EE:FF`.
- The kind must have a registered importer, otherwise `Unsupported`.

The add dialog starts with auto refresh on for a playlist URL, an Xtream account and a Stalker portal (`emptyDraft` in `src/features/sources/lib/draft.ts`); a pasted or uploaded playlist has nothing to refetch, so its toggle is off and disabled, and `sources.add` gets `autoRefresh: false`. The core's own default for a missing `autoRefresh` stays false.

A blank name follows the add dialog's `suggestName` (`src/features/sources/lib/validate.ts`): the percent-decoded last URL path segment without `.m3u`, `.m3u8`, `.php` or `.txt`, or the host without `www.` when that segment is empty or a generic endpoint (`get`, `playlist`, `index`, `player_api`, `c`, `stalker_portal`, `portal`, `server`, `load`, `panel`, any case). A file source takes its file name without `.m3u`, `.m3u8` or `.txt`, and pasted text "Pasted playlist". The new source goes last in the list. Pasted text is stored in `m3u_raw` in the same transaction.

A source whose address another source of the same kind already uses is refused before anything is created or fetched. The address is `store::identity`: the playlist URL, the playlist file's resolved path (on Windows without case or separator differences), the Xtream server and username, or the Stalker portal and MAC, normalised like the backup merge fingerprints. Pasted text has no address and is never a duplicate. The check and the insert run under one process-wide lock (`identity_lock`), so two concurrent adds cannot both claim one address. The error is `Conflict` ("this source already exists: "<name>" uses the same server and username") with `details: {existingSourceId}`, the id of the source that has the address. It never carries `sourceId`, because `details.sourceId` always names a source this call created: the add dialog retries that id, and removes it when the user cancels.

Once the row is inserted, `sources.add` emits `sources.changed {sourceId, reason: "added"}`. The importer then runs. If it fails, the source is kept with `last_error` set, and the rpc error carries `details: {sourceId}` so the UI can open the source for editing.

The user waits on this first import, so it runs inside `http::interactive`, as `xtream.test` and `stalker.test` do. In that scope the clients from `http::guarded_client` and `http::trusted_client` connect with `INTERACTIVE_CONNECT_TIMEOUT` (3 s) instead of `CONNECT_TIMEOUT` (10 s), and a connect timeout becomes a Network error at once: "Could not reach <host>. The server did not answer. Check the address and port, and that the server is online, then try again." (a Stalker portal says "Could not reach the portal at <host>. ..." with the same next step). That next step counts as a permanent transport failure, so the M3U, Xtream and Stalker retry loops stop on it. The rpc error is still `network` with `retryable: true`, so the user can fix the address and try again. `sources.refresh` (a source card's Refresh, the add dialog's Try again) runs inside `http::interactive` the same way. The scope is task-local: tasks the import spawns, `refreshAll`, the startup refresh and the scheduler keep the 10 s connect timeout and their retries.

The add dialog shows "Connecting to <host>…" until the first data arrives, and after 2 s (`STILL_TRYING_S` in `ImportProgressView.tsx`) "Still trying to reach <host>…" next to Cancel import. Cancel import calls `sources.cancelImport` for the new source; when the add then fails as cancelled, the dialog removes the source it created with `sources.remove` (a retry of an earlier failed source keeps it). The connection test (`ConnectionTest.tsx`, in the Xtream and Stalker forms) shows the same line after 2 s with a Cancel button that stops waiting: the test returns to idle, focus goes back to Test connection, and the answer, when it comes, is ignored. The core call itself runs until it ends.

## update, reorder, remove

- `sources.update {id, patch}` validates a config patch the same way. `patch.text` gives a pasted or uploaded playlist (m3u origin `text`) new text: it must have at least one channel (`m3u::rpc::preview`), any other source is `Invalid`. The update cancels a running import of the source, takes its import lock, and stores the text as `sources.add` does (inline up to 8 MB, else the disk copy, which an inline text then deletes; large text is written to `playlists/<id>.update.m3u` first and renamed over the copy only after the transaction commits, so a refused or failed update leaves the stored playlist as it was. The transaction also writes the mark `m3u_staged:<id>` in `app_state`, dropped once the rename is done and by `sources.remove`. From the commit on, the staged file is the source's text: a rename that fails, or a crash before it, does not fail the update or lose the text, and the next import of the source (whatever its origin is by then), the next `sources.update` with new text or the next start (`m3u::init`) moves it into place first. Only a staged file without a mark, from an update that never committed, is deleted), keeping the old `m3u_raw.sha256`, so the next `sources.refresh` sees new text and re-imports it under the same source id. That import's id remapping (m3u.md) keeps favorites, history, positions, edits and locks on the channels still in the new text. The edit dialog takes new text or a file (read in the page) and starts that refresh itself, and it also starts one after new connection details (an address, credentials, a MAC, request headers; `patchNeedsRefresh`), so a fixed password loads at once instead of waiting for Refresh. The patch must match the source's kind. `position` moves the source and renumbers the rest. `epg` lists are trimmed and de-duplicated, and only the given lists change. Config changes do not re-import; the UI calls `sources.refresh` for that. A patch that only sets `autoRefresh` emits `sources.changed {reason: "status"}`, so clients refetch only `sources.*`; any other patch (new text included) sends `"config"`. When the stored config actually changes (URL, MAC, credentials, headers), the cached portal session `stalker_token:<id>` in `app_state` is deleted in the same transaction, so the next portal call handshakes with the new settings. A rename or an identical config keeps it. A config that gives the source an address another source already uses (the check under `add`) is refused with `Conflict`, without `details`, and nothing changes.
- `sources.reorder {ids}` puts the listed ids first in the given order. Unknown ids are ignored, and unlisted sources keep their relative order after them. Positions are renumbered from 0.
- `sources.remove {id}` cancels a running import of that source (and any queued one), waits for it to stop, then deletes it. The delete holds `db::long_write()`, so writes made meanwhile wait for it instead of failing after the 5 s busy timeout, and it removes the source's search-index (`items_fts`) and `items_rank` rows in bulk with their triggers suspended (`fts_suspend`), as `CatalogWriter::begin` does, before the items cascade. After the commit it runs `db::checkpoint_truncate`, as an import does, so the WAL does not keep the size of the deleted catalog. `removeAll` and a backup Replace go through the same path. Items, categories, `m3u_raw`, `source_counts`, favorites, recent entries, positions, EPG mappings, per-channel guide shifts (`epg_channel_shift`, migration 0021), My List rows (`watchlist`, migration 0012) and parental locks (`parental_locks`, migration 0011) cascade. The `stalker_token:<id>`, `backup_pending:<id>`, `account_status:<id>`, `xtream_fp:<id>`, `stalker_fp:<id>`, `m3u_validators:<id>`, `m3u_import_version:<id>` and `m3u_staged:<id>` keys in `app_state` are removed too, and so is the on-disk playlist copy of a large m3u (`data_dir/playlists/<id>.m3u`). `sources.add` stores pasted text over `RAW_INLINE_MAX` (8 MB) in that copy with `m3u_raw.raw = ''` (`store::insert` through `m3u::place_raw_text`), so neither the add nor later refreshes keep it in SQLite.
- `sources.removeAll` removes every source through the same path as `sources.remove` (one at a time, each cancelling its import), then emits `sources.changed {reason: "removed"}` without `sourceId`. Returns null.

## refresh

- `sources.refresh {id}` re-imports one source and returns it. It works for any source, whatever its `autoRefresh` setting. When a full import of that source is already running (`sources.add`, another refresh, the schedule, a backup load), the refresh waits for it and returns its result instead of importing again (`run_import` registers each run in `sources.inflight`). A refresh joins or reserves its entry in one step before it waits for the import lock (`Inflight::admit`), so refreshes queued behind a partial sync, a remove or another import also share one import. A run that was already cancelled, or that an edit or a remove stops, is not joined: the refresh then reserves again and imports, as before. A run the user cancelled ends the joined refresh with the same cancel error. A partial sync (`run_import_with`) is never joined.
- Imports of several sources may download at the same time, but only one decodes its answers and writes its catalog (`sources::save_slot`, one permit per app state): M3U from its parse to its commit, Xtream from its first changed list to its commit (a list is hashed before the wait, and one that matches the last write is not decoded, so an unchanged refresh never waits), Stalker from its row mapping to its commit. Two large syncs never hold their rows in memory together. A cancel ends the wait for the slot.
- The Sources page's Refresh all calls `sources.refresh` one source at a time, pasted and uploaded playlists included (they re-import their stored text, without the network), and skips a source whose import is running (its progress phase is not final). A pasted or uploaded playlist's card offers the same as Re-import.
- `sources.refreshAll` re-imports every `autoRefresh` source, one at a time, and returns `{refreshed: [id], failed: [{id, error}]}`.
- `init` spawns a background task that runs the startup pass (`schedule::startup`) `STARTUP_REFRESH_DELAY` (30 s) after boot, then starts the scheduled refresh (below), whose first pass is 10 minutes later. Boot does not wait for it. A second `init` call on the same state does nothing. The startup pass uses the scheduler's rules (`next_due`) planned against `sourceRefreshIntervalHours` capped at 24 h, and against 24 h when the interval is 0, so an `autoRefresh` source is re-imported at startup only when it was never refreshed, or its last good refresh is more than a day old (or older than a shorter interval), as the setting's hint says. Before (ST-1 in the 2026-10-19 performance audit) every `autoRefresh` source was re-imported 3 s after every launch, while WebView2 was still loading on a slow machine. The 30 s delay leaves the window, the first screen's queries and the first stream to finish before an import downloads and takes the write lock. A source busy with another import is skipped, and sources run `STAGGER` apart. The startup pass also re-imports, once, every M3U source whose catalog an older `IMPORT_VERSION` wrote (the version each import records, see m3u.md), whatever its `autoRefresh` and age; pasted and uploaded text re-imports from the stored text, without the network. These follow the due sources, and each is checked again right before its import, so a manual refresh during the stagger is not repeated. A failed or cancelled attempt is tried again at the next launch.
- `try_run_import(state, id)` is `run_import` unless an import, refresh, partial sync or remove of that source holds its lock right now; then it returns `None` and runs nothing.
- A failed import stores `lastError`, `lastErrorCode` and `lastErrorAt` (RFC 3339, migration 0009); a successful one clears all three.

### Scheduled refresh

`sources::schedule` refreshes `autoRefresh` sources every `sourceRefreshIntervalHours` (0..168, default 12; 0 = only the startup pass, which then refreshes sources more than a day old). The loop holds a `Weak` app state and ends when the state is dropped. It keeps running while the window is hidden in the tray.

- A tick (every `TICK`, 10 min) plans the due sources, longest overdue first: never refreshed, or `lastRefreshAt + interval` passed. Pasted-text M3U sources and sources with `autoRefresh` off are never scheduled.
- Each source is re-read right before it runs (it may have been removed or switched off) and runs through `try_run_import`, so a manual import or refresh of the same source is skipped, never queued behind or repeated. Sources run one at a time with `STAGGER` (20 s) between them.
- A failure is recorded exactly like a manual refresh (`record_import_error`) and backs off: 30 min, doubling per consecutive failure, capped at the interval. Backoff state is in memory; after a restart a stored `lastErrorAt` still delays the next try by 30 min. A cancelled scheduled run is not a failure and waits a full interval.
- Decisions take a `Clock`, so tests drive time with a fixed clock.
- `sources.schedule` returns `{intervalHours, sources: [{sourceId, nextRefreshAt, retrying}]}` for the scheduled sources; the Sources page shows "Next refresh in ..." and "Retrying in ..." from it, and "Failed 2 hours ago" from `lastErrorAt`. A `settings.changed` that changes `sourceRefreshIntervalHours` invalidates it, and the scheduler emits one more `sources.changed {sourceId, reason: "status"}` after each scheduled run once its backoff is stored (the import's own event fires before that).

## Counts

`sources.list` and `sources.get` return `channelCount` (live only), `radioCount`, `movieCount` and `seriesCount`. All but `radioCount` come from the `source_counts` cache; `radioCount` is counted from `items`, leaving out stations hidden with channel edits (channel-edits.md). `sources.counts {id}` returns the same four numbers.

Stalker portals serve VOD and series live; only their categories are stored. For stalker sources `catalog::update_counts` therefore refreshes only `channelCount`, and `run_import` records the portal's movie and series totals from the importer's `ImportSummary` with `catalog::set_remote_counts`. A direct `stalker.sync` (not through `run_import`) must call `set_remote_counts` itself to refresh those two numbers.

## The Sources page

`src/features/sources/SourcesPage.tsx`. The shell header says "Sources" with the count as a bare number beside it (none while the list is empty). Each source is a card: its monogram (the kit's `SourceMonogram`, the same mark as in the rail), name, kind, subscription badges, where it comes from and when it last and next refreshes, its counts, and its actions. Refresh (Re-import for a pasted or uploaded playlist) and Edit are buttons; subscription details, hidden and renamed channels, and Remove are in the card's More actions menu. On a phone every action is in that menu.

The counts are columns the cards share (`statColumnsOf`): every count any listed source has (channels, radio, movies, series, in that order), each a fixed slot right-aligned against the actions, so a column holds one kind of count down the list; a source that lacks one shows a quiet dash there (a screen reader hears 0). A narrow card instead lists the counts it has as a line of text, with its address on a line of its own and its refresh times on one line after it that wraps as a `MetaLine`; those lines take the card's full width, beside a smaller monogram (`size-9` below @3xl), so on a phone the two times fit on one line.

With three or more sources the page offers sort and filter (by kind and by status) behind one View button (`ViewPopover`) in a toolbar of small controls with Refresh all, Add and More; the toolbar's More lines up with the cards' More buttons. Three bordered selects, each as wide as its longest option, had been the heaviest chrome on the page. The View button names the current sort and counts the choices that differ from the default, and opens a panel under it with the three labelled selects. The panel is not modal and follows the button in the DOM, so Tab goes on through it; Escape closes it and gives focus back to the button, and a press outside it or focus moving elsewhere closes it too. On a phone the page's actions are header buttons instead (Sort and filter, which opens a bottom sheet and shows how many choices differ from the default; Add; More, with Refresh all), so the cards start right under the header; a running Refresh all comes onto the page with its progress and Stop. Order changes (drag, Alt+Up/Down) work only in the default view. The Add and Edit dialogs are bottom sheets on a phone too (the kit Dialog's `sheet`).

The add dialog lists the kinds as the empty page's tiles do, Xtream first. A bare Add (`?add=1`, the toolbar, the header) opens on Xtream, the most common kind; a tile or `&kind=` opens on its kind, and a deep link with an address and no kind opens it as a playlist URL (an Xtream `get.php` link fills the Xtream fields). The fields run address and credentials, the optional name, auto refresh, and last the request headers, an advanced option (the forms take `showHeaders={false}` there; the edit dialog keeps them inside each form).

With no sources the page is the first-run empty state (`Onboarding`): the heading at the headline size, the three kinds as tiles (Xtream first, marked as the most common) and a way to restore a backup; on a wide page the block sits in the middle of the window's height. From `@3xl` the tiles are three cards (icon, name, what the kind is, and a ruled "You need" footer). In one column (a phone, a narrow window, a tablet held upright) each is a list row about 64 px tall: the icon, the name with the Most common badge beside it, and what the user needs as one quiet line; the sentence on what the kind is stays for screen readers. As cards on a phone they were 160 to 186 px each and pushed the privacy line and Import a backup under the tab bar. Home's welcome uses the same tiles.

Every other page that has nothing to show without a source (the TV guide, Favorites, Recently watched, My List, Multi-view, Watch stats, and Downloads and My Videos through the library's `BrowseAction`) draws one shared state, `NoSourcesState` (`components/NoSourcesState.tsx`): the page's own icon, title and one line on what it shows once a source exists, then the same two actions everywhere (`NoSourcesActions`). Add a source opens the add dialog right on the page, loaded with `import()` on the press, as Home's welcome does, so Cancel leaves the user where they were; the first source added then opens on its channels (`sourceHomePath`), except on the guide, Multi-view and Sports (`stay`), which fill in with it. Import a backup, a ghost button beside it, opens Settings > Backup. Sports still lists the day's games without a source, so it draws the state as one short row in a dashed frame above them (`layout="banner"`). The pages keep their own test ids on the Add button.

Wording: "source" names the thing the user adds, of any kind; "playlist" is only the M3U kind's own word (a playlist URL, a pasted playlist).
